**② javac 必须用 JDK 11/17，不能用 21+。**

| javac 来自 | d8（R8 8.2.2 / build-tools 34） |
|---|---|
| JDK 11 | ✅ |
| JDK 21 | ❌ 内部 NPE |
| JDK 24 | ❌ 内部 NPE |

--boot-class-path」）⇒ 「改成 target 11 绕开」这条路是堵死的。
最小复现：`android/tools/repro-d8-javac/`。

`build.sh` 第 1b 步把仓库根的 `../fonts/` 整个拷进 `assets/fonts/`。
**产品一个字都没改** —— `@font-face` 用的是相对路径 `./fonts/…`，页面跑在

- APK **1 083 285 → 5 036 342 字节**

- `myFont.ttf` 与 `ttf/Cubic_11_1.100_R.ttf` 是**同一份文件的两个副本**（crc32 `733b9c8b`）

### 坑三：`zipalign WARNING: header mismatch` 是假警报，而且**退出码是 0**

加完字体，构建日志多出 5 行警告，**正好等于字体个数**。查清过程：

| 阶段 | 项数 | 「本地头名字 ≠ 中央目录名字」 | zipalign 警告 |
|---|---|---|---|
| `base.apk`（aapt2 输出） | 26 | **5**（就是那 5 个字体） | **5 条** |
| `aligned.apk`（zipalign 输出） | 26 | 0 | **0 条** |
| 出货 APK（签名后） | 29 | 0 | **0 条** |

**根因**：aapt2 在 Windows 上给**带子目录的资产**写本地文件头(LFH)时用平台分隔符 `\`，
中央目录(CD)里是 `/`。zipalign 的 `ZipEntry::compareHeaders()` 最后一条正是
`strcmp(CD 名字, LFH 名字)`：

```
LFH: assets\fonts\web\Cubic_11_1.100_R.woff2
CD : assets/fonts/web/Cubic_11_1.100_R.woff2
```

`assets/index.html` 路径里没有分隔符 ⇒ **加字体之前从来没报过**。

**为什么无害**：① zipalign 是**从中央目录重建本地头**的，顺手把反斜杠归一了；
② apksigner 直接拒绝这种 APK（`ZipFormatException: Name mismatch between Local File
Header and Central Directory`，rc=1）⇒ **结构上进不了出货产物**。

⚠⚠ **但 zipalign 只打警告、退出码照样 0** ⇒ 判据必须落在**出货的那一份**上。
`verify.sh` 加断言 + `tools/reverse-lfhname.py` 反向测试。

**怎么定位的**（值得记）：从 `raw.githubusercontent.com` 拉
`aosp-mirror/platform_build` 的 `ZipEntry.cpp` / `ZipFile.cpp` / `ZipAlign.cpp` 读
`compareHeaders()`；写 `bisect.py` 把每条条目**单独重打包并保留原始 LFH+CD 字节**
（只改 4 字节的本地头偏移）再喂给 zipalign ⇒ 5 个命中**正好是那 5 个字体**；
再用 `hexdiff.py` 打出原始字节，才看见 `\` vs `/`。

## APK：让页面能直连 Google Vertex AI（`65c797f`）

用户要「把 `G:\saki\fonts` 的字体也封装进去，然后找一个能运行 Google Vertex AI 的开源
后端一同封装进去」。三个卡点问过用户：**网络 = 能直连**；**后端方案 = 「1 和 3 互为保底」**
（App 内原生转发 + 本机开源网关）；**凭据 = API key 与 Service Account 两种都有**。

### 结论：问题只有一条 —— CORS

**页面本身已经是完整的 Vertex 客户端**（express 用 `x-goog-api-key`；完整模式用
`crypto.subtle` 签 RSASSA-PKCS1-v1_5 → `oauth2.googleapis.com` 换 token）。
缺的只有「浏览器 origin 读不回响应」。

### 为什么选注入 `fetch` 垫片，而不是 `shouldInterceptRequest`

后者的正确性取决于三条**本机验不了**的行为：合成响应要不要手工写 CORS 头、
preflight 会不会也被拦、流式要不要在后台线程同步返回。
垫片的语义是**浏览器自己的**（`Response` / `ReadableStream` / `AbortSignal` 都是真的）
⇒ **能脱离 WebView 用 Node 验证**。

⚠ 注入安全性先核过：产品里**从来没有**把 `fetch` 赋给变量
（`window.fetch =` / `= fetch` / `const fetch` / `fetch.bind` 全 grep 不到）。

### ⚠⚠ 「把核心写成不依赖 `android.*` 的类」是这一整轮可验证的前提

`AiProxy.java` / `JsEvent.java` **刻意不 import `android.*`** ⇒ 能在**桌面 JVM** 上
真编译真运行。`tools/test-aiproxy/run.sh` 于是能用**真 javac + 真 JVM** 跑**同一份实现**，
而不是在测试里再抄一份近似品。`run.sh` 里的 `[ "$NCLASS" -ge 4 ]` 就是这条性质的守门人。

### 三件特意写对的事（都是**静默**失败型）

- **`Accept-Encoding: identity`** —— 否则 `HttpURLConnection` 的透明 gzip 会把整个 SSE
  **缓冲成一整块**再吐出来，「流式」没了且**不报错**。
- **非 2xx 不抛异常** —— 用 `getErrorStream()` 把错误正文也转发回去。
- **`onHead` 先于正文** —— 状态行一到 `fetch` 就 resolve。

### 两条路的接缝 = `AiProxy.upstream()` **一个方法**

```java
public static String upstream(String url) { return url; }   // 默认直连
// 要转给本机网关（nodejs-mobile 之类）只改这一行
```

⇒ 这正是「App 内原生转发」与「本机开源网关」能**互为保底**的原因：接缝同一条，
区别只在接缝下游换成谁。白名单里那两条 `127.0.0.1` / `localhost` 就是为这条路留的。

### ⚠⚠ 针④：一条**子串**断言，差点让我得出「反向测试很成功」的假结论

`verify.sh` 原来那条是 `b'aiAbort' in dex` —— 一个**子串**搜索。

### ⚠⚠ 坑四：`rm -rf` 静默失败，根因是**顺序竞态**、不是删除机制

`tools/test-aiproxy/run.sh` 收尾删 `.work` 时报
`SAFE_DELETE_FAIL_CLOSED … Some operations were aborted`，rc=1，目录原样留着。
但**过几秒再删就成功** ⇒ 是竞态。

两层成因：

1. **顺序**：收尾那句 purge 写在 `exit 0` **之前**，而停服务器的 `trap cleanup EXIT`
   要到退出时才跑 ⇒ **删的时候服务器还活着**，`server.log` 还被占着 ⇒ Windows 拒绝删。
2. **静默**：`run.sh` 用的是 `set -uo pipefail`（**没有 `-e`**）⇒ `rm -rf` 失败不影响继续跑。
   同一句 `rm -rf` 在 `build.sh` 里是**响的**（那边有 `-e`）。

⚠ 我为这个坑先后去查了 genie-trash、加了 `shutil.rmtree` 兜底、加了 `wait` ——
**全都没用，因为问题不在删法上**。教训：读数可疑时先怀疑**顺序/时序**，
别一头扎进「机制坏了」。

**为什么必须修**：清不掉就留着**上一轮**的 `expected/*.bin`，而 `contract.test.js`
是拿它当**真值**比的 ⇒ 这一轮 server 没写出 `sse.bin` 时，测试会拿**上一轮的录制**
比对然后**通过**。**拿旧数据当真值比直接报错难查得多。**

**修法**：先停服务器（并 `wait` 到真的退出）→ 再删 → 回读确认 → 删不掉就拒跑。
闸门反向测过（用另一个进程占住目录里的文件）：
`❌ 清不掉 … 上一轮的 expected/*.bin 会冒充这一轮的录制，拒绝继续`，rc=1。
