# 2026-09-19 · 工作日志

## 待办调研 · 「把 skill 作为工具写入」能不能让调用变流畅

用户提问，**明确说「先别动手」，只要分析**。所以这一节全是查代码得到的**硬事实**，没改任何产品文件。

### 四个关键数字（放在一起看就出问题了）

| 常量 | 值 | 含义 |
|---|---|---|
| `ST_CODE_SKILL_CHARS` | **40000** | 导入时 skill 正文的上限 |
| `ST_CODE_AUTO_CHARS` | **24000** | 触发词命中后自动注入 system 的总预算 |
| `ST_CODE_TOOL_CHARS` | **12000** | **任何**工具结果喂给模型的上限 |
| `ST_CODE_THINK` | 4 / 8 / 12 / 20 | 每轮用户消息的工具调用步数上限 |

### ⚠ 发现的三个真问题（**都还没修**）

**① 大 skill 两条路都读不全。** 一份 30 000 字的 skill：自动注入装不下（>24 000）→
退回「要用就先 `read_skill`」→ 而 `read_skill` 只能给 12 000 字 + 「…（结果太长，已截断）」。
模型拿到 **40%**，而且**不知道自己少了什么**，也没有任何办法拿到剩下的。
这三个数字本该是同一条链上的，现在差了 3.3 倍。

**② 纯读工具也吃步数。** `read_skill` / `read_card` / `read_doc` 每调一次算一步
（`stCodeSend` 里 `used++` 在 `for (const c of calls)` 里，不分读写），而最低档只有 4 步。
**「读」不该和「改」抢同一个预算。**

**③ 优先级最高：`read_doc` + `write_doc` 撞上 12 000 截断会静默删数据。**
状态栏 HTML 很容易过 12 000 字（一个块的内联样式就两三百字，三四十个块就到顶）。
模型 `read_doc({kind:"statusbar"})` 拿到**截断版** → 照着它 `write_doc` 回去 →
`stSbParseDoc` 照样解析成功（DOMParser 对残缺 HTML 很宽容）→ **尾部块静默消失**。
这是我上一轮刚加的功能里的隐患。`read_doc` 没有像 `read_card` 那样走 `stCodeBrief`，
所以只有截断这一道限制，而且截断是**永久**的（写进 `sess.msgs` 的就是截断后的文本）。

### 结论（建议顺序，供用户决定）

1. **先修上面三条**（不改架构，都是几行）—— 尤其第 ③ 条。
2. 「skill 工具化」治的是**执行**（步数），不是**发现** —— 发现那半边上一轮的
   触发词自动注入已经解决了（确定性的）。
3. 三种工具化的代价差一个数量级：
   - **换皮**（每个 skill 一个工具）：基本没用。工具表 19 → 19+N，模型选择变差，一步没省。
   - **声明式组合**（skill 声明一串已有工具的调用序列）：安全、省步数，但**不能按结果分支**，
     而那套 DSL 会长成一个难用十倍的半吊子 JS。
   - **可执行**（skill 带 JS，沙盒里跑，postMessage RPC 调工具）：最强。
     ✅ 页面里**已经有现成的安全沙盒原语** —— 状态栏真机预览那个 iframe 就是
     `sandbox="allow-scripts allow-forms allow-popups"`，**没有 `allow-same-origin`**，
     读不到父页面 DOM / localStorage。
     ⚠ 但页面现在**一个 `eval` / `new Function` 都没有**，skill 是**纯数据**
     （`{name, desc, body, triggers}`）。一旦可执行，「从 GitHub 链接导入一个 skill」
     就等于「运行陌生人写的代码」。沙盒挡得住它碰页面，挡不住它用 `fetch_url`
     把用户的卡（私密角色设定）发到任意公网地址。**要做就得配权限模型，这一块不能省。**
4. **先看用户导入的 skill 是「资料」还是「流程」再决定** —— 资料型（格式规范 / 字段表 /
   坑列表）的话工具化帮不上忙，「自动注入 + 读得全」就够了；流程型才值得工具化。

## 调研② · 用户给了一份「skill 即工具」的原型，问能不能照它改

文件：`G:/gemini-code-1789810394640.html`（Gemini 出的原型，17 KB / 362 行）。
它做的正是上一条里的**「可执行」方案**：`/*!MANIFEST {...} !*/` 注释里放 JSON Schema，
skill = manifest + JS 源码 → 存 IndexedDB → manifest 直接变成 LLM 的 `tools[]`
→ `tool_choice:'auto'` → 命中后 `new Worker(blobURL)` 跑，`postMessage` 传参。

### 它做对的

- **manifest 直接变 tool 定义** —— 「skill 即工具」的正确形态。`/*!MANIFEST*/` 放在源码头部
  很干净：一份文件既是可执行体又是自己的说明书，不用旁挂 JSON。
- URL 安装 → 本地库，和 saki.html 现有的「从链接导入」同构（那套可以直接复用）。
- 有 Key 走 LLM 路由 / 没 Key 走本地降级的意识。

### ⚠ 7 处不能照抄

1. **`new Worker(blobUrl)` 不是沙盒** —— Worker 是**并发**边界不是**安全**边界。
   它有 `fetch` / `XMLHttpRequest` / `importScripts` / `IndexedDB` / `WebSocket`，
   而且 `blob:` 继承页面源 → 从 URL 装进来的 skill 可以把任何东西发到公网，
   原型里**没有任何东西挡这个**。唯一挡住的是 DOM，而 skill 改卡**本来就得** postMessage
   回父页面 —— **真正的边界是 RPC 暴露了哪些方法，不是 Worker。**
   正解：用页面**已有的**那个原语 —— 状态栏预览的 iframe（`sandbox="allow-scripts"`，
   **无 `allow-same-origin`** → 不透明源），再往 `srcdoc` 里塞
   `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'unsafe-inline'">`
   → **连网络都断掉**，这是 Worker 做不到的。
2. **没有超时** → `while(true)` 永久泄漏一个 worker 一个核。`terminate()` 只在
   `onmessage`/`onerror` 里调，死循环两个都不触发。
3. **skill 名字直接当 tool name** → 两套协议都要求 `^[a-zA-Z0-9_-]{1,64}$`。
   一个叫 `我的技能 v2.0` 的 skill 会让**整个请求**挂掉，报错还跟 skill 毫无关系。
4. **启发式兜底等于「永远选第一个」**：`userPrompt.split('').some(c => desc.includes(c))`
   —— 中文输入里随便一个字就命中。**「单字触发词」的极端版**（项目已为此吃过亏）。
5. **manifest 解析失败被 `catch(e) {}` 静默吞掉** → 退回 `custom_skill_<ts>`，
   名字和 parameters 全丢。**不报错，只是安静地给你一个坏的**。
6. **GitHub 链接转换写死 `main`**，且 `tree` 目录链接会被拼坏。
   项目里**已经有**正确的那套（`stCodeGhParts` + 先问 `default_branch`）。
7. **`innerHTML` 直接塞远程内容 → XSS**（skill 名字 + skill 输出两处）。

### 搬进来的改动点（比想象的小）

| 改动点 | 现状 | 改法 |
|---|---|---|
| `stCodeToolsFor(proto)` | `ST_CODE_TOOLS.map(...)` | 换成 `stCodeToolDefs()` = 静态 19 + 动态 N |
| `stCodeToolRun` | `if (name === '...')` 链 | 链**最前面**插 registry 查表分支 |
| skill 存储 | `localStorage['stCodeSkills']` 纯文本 | 加 `kind:'tool'` + `manifest` + `code` |
| 沙盒 | 只有状态栏预览那个 iframe | 新增 helper（srcdoc + postMessage RPC） |

**IndexedDB 建议先别加**：`ST_CODE_SKILL_CHARS = 40000` → 一个 skill 约 80 KB，
10 个 800 KB，localStorage 5 MB 够用。等真撞上再搬。（顺手给 `stCodeSaveSkills`
失败时补个「配额满了」的人话提示。）

### 关键设计判断：**不是替换，是并存**

knowledge 型 skill（字段映射表 / 格式规范 / 坑列表）**没法变成函数**，强行工具化是降级。
所以 `kind: 'knowledge'`（正文注入，照旧）和 `kind: 'tool'`（注册成工具）要并存。
导入时自动判：`.js` 或带 `/*!MANIFEST*/` → tool；`.md` → knowledge。

### 落地顺序（建议）

1. **先修调研① 的三条**（尤其 `read_doc` 截断 → `write_doc` 静默删数据）—— 已在丢数据。
2. skill-as-tool 第一步**只放一个只读工具**（`read_card`）跑通链路。
3. 补权限白名单 + 超时 + 输出转义。
4. 再放开写工具。

### ⚠ 沙盒：四条**实测**行为（Chrome，2026-09；不是推测，写进注释了）

| 试的 | 结果 |
|---|---|
| 沙盒文档里 `fetch` | 被 CSP 挡（TypeError）✓ |
| `new Worker(blob:)` | **也被挡** —— `worker-src` 回退到 `default-src 'none'` |
| 加 `worker-src blob:` 后 | worker 起得来，但**它自己的 `fetch` 还是被挡**（blob worker 继承 CSP） |
| 沙盒里 `while(true)` | **不冻父页面** —— 不透明源 = 跨源 → Chrome 把它放**另一个进程**，父页面 `setInterval` 照跳（59→161），沙盒里 5e8 次循环跑了 548 ms |

**第 4 条是超时能真正生效的原因** —— 靠的是**进程隔离**，不是事件循环。
所以 `ST_CODE_SANDBOX_MS = 5000` 是硬闸门，不是「尽力而为」。
⚠ 这条第一版探针给出了**假的「父页面冻住」**读数：探针页自己在
`target="_blank"` 的锚点里引用了一个**已被删掉的变量**，整段脚本压根没跑。
用 `<script type="text/plain">` 重写探针才拿到真数据。**探针本身也是代码，也会错。**

### C. skill 落盘换 IndexedDB

`ST_CODE_IDB_NAME = 'saki-code'` / `ST_CODE_IDB_STORE = 'kv'` / `ST_CODE_IDB_MS = 3000`。
三条铁律：

1. **只写一处** —— 后端记在 `stCodeSkillBackend`，写 IDB 成功就**清掉** localStorage 老键。
   两边都写迟早分叉，而分叉之后**没人知道该信哪边**。
2. **降级要打脏标记**（`stCodeSkillsLsDirty`）—— 不然后果是：某次 IDB 抽风 → 写进 LS →
   下次 IDB 又好了 → 读到**旧的那份**，新的悄无声息地没了。
3. **迁移顺序不能反** —— 先写成功**再**删老键。反过来写失败就等于把用户的 skill 全删了。

另外：「启动读」和「导入写」排成**一条串行链**（`stCodeSkillChain`），且写之前**先拍 payload 快照**
—— 不排的话读回来的旧列表会盖掉刚导入的，**两边都不报错**。

`stCodeLoad()` **不再读 skill**（注释写了为什么）：内存里的 `stCode.skills` 是同步真相，
存储层是异步的，读进 `stCodeLoad` 会跟后面的写抢。改由 `openStEditor()` 和 `stCodeSend()` 各自 `await`。

## 落地 · D 权限白名单 + 顺手修的静默清空（用户原话：「做吧」）

### 设计：两层能力 + 三个「不给」

沙盒原来把 skill 关得**太死** —— 它连自己刚被调起来要干什么都读不到。给一条**反向通道**：
skill 里 `await host.call('read_card', {})`，父页面执行完回信。

但「能给」和「该给」是两件事。按危险程度分两层：

| 能力 | 能调的工具 | 危险在哪 |
|---|---|---|
| `card.read` | `read_card` / `read_doc` / `read_regex` / `read_th` / `list_world_entries` / `read_world_entry` | 低 —— 读到的东西**出不去**（CSP 断网），只能回给模型 |
| `card.write` | `write_text` / `write_list` / 世界书增删改 / `write_doc` / `write_regex` / `write_th` | **高 —— 真的会改用户的卡** |

**三个不给：**

1. ⚠ **`fetch_url` 永远不给**（任何层都没有）。它是唯一出网通道，给了就等于把 CSP 断网的
   意义抹掉一半 —— skill 能把刚读到的卡（私密设定）**拼进 URL 发到公网**。
   地址闸门挡的是「访问内网」，挡不住「把内容发出去」。**整套设计里最硬的一条。**
2. ⚠ **`set_tasks` / `remember` 不给** —— 会话级状态，skill 用不上，给了只会污染。
3. ⚠ **`read_skill` / `list_skills` 不给** —— 它们读的是用户的 skill 库不是卡，
   **是设计判断不是漏登记**（套件里为此专门排除了它们，并单独断言「确实不在表里」）。

### 闸门三层，且**不在沙盒里判断**

| 层 | 判断 |
|---|---|
| 导入（`stCodeManifestOf`） | 声明了宿主不认识的能力 → **拒收**（硬装进去只会给模型一堆失败） |
| 运行时（`stCodeSkillRun` 的 `onHost`） | ① 工具名在不在「能力 → 工具」表里 ② 申请到没有 ③ 次数上限 |
| 底下 | 走**同一个 `stCodeToolRun`** —— 另写一条写路径 = 把写白名单 / 回收站 / 安全开关全绕过去 |

⚠ **不在沙盒里做判断** —— 沙盒里的判断等于没判断（skill 能改自己的代码）。
⚠ **权限在导入那一刻定死**，运行时不会临时给；所以面板上要**一直**标 `✏️ 能改卡`（警示色）。
⚠ **一次 run 最多 20 次宿主调用**（`ST_CODE_SANDBOX_RPC_MAX`）—— 不给上限的话
`while (1) { await host.call(...) }` 能在这 5 秒里把卡读上千遍。
**沙盒超时掐得掉沙盒，掐不掉父页面正在跑的那一串。**
⚠ 单次另有 `ST_CODE_SANDBOX_RPC_MS = 4000`（比总超时短），让 skill 有机会 catch 到。
⚠ `host` 的 `onmessage` **必须先认 `__hostRet` 再认 `__call`** —— 反了的话回信被当成新调用，
**不报错，只是每个 `host.call` 都超时**。
⚠ 父页面收 RPC **也要验 `e.source === frame.contentWindow`** —— 页面上还有状态栏预览那个 iframe。

新常量：`ST_CODE_SANDBOX_PERM`（两层）、`ST_CODE_PERM_TOOLS`（能力→工具白名单）、
`ST_CODE_SANDBOX_RPC_MAX`、`ST_CODE_SANDBOX_RPC_MS`。
新函数：`stCodePermOfTool` / `stCodeSkillPermsOf`（**求交集**，不直接信 manifest ——
老草稿里可能存着已下线的能力名）/ `stCodePermToolNames`。

### 顺手修的一条静默清空（**探针撞出来的**）

`write_text` 原来是 `String(a.value == null ? '' : a.value)` —— 参数名少写一个、
或者把 `text` 当成参数名（`write_doc` 用的就是 `text`），**那个字段当场变成空串**，
而返回的是「已写入 description（现在 0 字）」这种**成功回执**。
同一族（空值不覆盖）在 `write_list` 的 `items` 和 `update` 的「没传的字段不动」上都防住了，
只有这里漏了。修法：`value` 为 `undefined`/`null` 时**拒收**并说清要放在 `value` 里；
⚠ **空串 `""` 仍是合法值** —— 那是「故意清空」，和「忘了给」必须分开。

**发现过程本身就说明问题**：探针里把参数名写错了，断言 `卡真的被改了` 拿到的是 `""`。

## 落地 · D 的收尾：两个「隔了两层」的漏子（594 → 604 条）

权限通了之后 skill 能在沙盒里真的改卡了，于是冒出两个**只有读代码才看得见**的问题。

**① 改了卡，右侧那份卡 JSON 不重画。** Agent 循环是看 `r.touched` 才决定要不要
`stCodePaintJson()` 的。skill 走「沙盒 → RPC → `stCodeToolRun`」，`touched` 到 dyn 分支就断了
→ 外层拿到 `''` → 不重画。表现是「skill 说改好了、卡里**真的**改了、用户右边还是**没更新的卡**」，
而**所有断言都是绿的**。修法：`stCodeSkillRun` 在 `onHost` 里记 `touchedAny`，
`finish()` 一起 resolve，dyn 分支原样返回。

⚠ **教训：中间隔了两层的返回值，每一层都要显式往上带。** 少带一个字段不报错，
只是下游少做一件事。这类 bug 的共性是「功能是对的，只是某个副作用没触发」。

**② 失败信息里那句「卡没有动」是假话。** skill 完全可能**先写成功、再自己抛异常**
（`host.call('write_text', …).then(() => { throw … })`）—— 卡里**留着它的改动**。
说成「卡没有动」是**最坏的那种假话**：用户以为没动就不会去检查，改动就那么留在卡里。
修法：按 `touched` 分流。

⚠ **教训：凡是「失败 ⇒ 什么都没发生」的推理，都要先问一句「失败之前它做过什么」。**

**③ 顺手让 `list_skills` / `read_skill` 也把权限说给模型** —— 模型据此决定「要不要自己先读一遍」
和「先调谁后调谁」（一个能改卡的工具，调用顺序就有意义了）。说成「读不到卡」的后果是
**放弃**：模型会得出「反正它读不到」，然后绕远路。

**验证**：`st-code.js` **594 → 604 条**（E10 加了 touched 传递 / 写完才炸 / list_skills 与
read_skill 三处口径），全绿；`_verify` 11 套共 **1 600 条**全绿（其余 10 套复跑过，都没被波及）；
外部 8 层全绿，`static_check` 的 `ST_`/`st` 名字数仍是 **757**。

## 落地 · D 的第四段：对抗式重审 —— 又揪出两处「行为没错、说法错了」

权限那一套跑绿之后，我拿它跟**文案**对了一遍（system 提示词、面板、导入反馈），
找出两处不一致。两处都**测试抓不到** —— 因为断言只覆盖我**想到**的那条路径。

### ① 只读判据和 system 文案对不上

system 写着「`read_*` 这类只读工具……不算在改卡次数里」，判据却是静态名单
`ST_CODE_READ_TOOLS.indexOf(...)`。一个**没申请 `card.write` 的工具型 skill**
（掷骰子、算个数）不是 `read_*` → **照吃一次改卡步数**。越纯算的 skill 越吃亏。

修法：`stCodeIsReadTool(name)` = 静态名单 **或**「没申请 `card.write` 的工具型 skill」。
⚠ **故意保守**：申请了 `card.write` 的一律按改卡算，哪怕这次只读了一行。
猜错方向的代价不对称 —— 少算一步只是少改一次卡；多算一步会让用户以为「还能改」却发现改不动。

### ② 权限在导入那一刻定死，导入时却不说

`card.write` 的 skill 装进来就能在**没被要求动卡的时候**动卡。这是设计本意，
但**只给一个 `✏️ 能改卡` 徽章不算告知** —— 徽章在另一个面板里，用户点完「装」就走了。

修法：`stCodeSkillsApply` 算出 `writers`，导入反馈里**点名** + 给「移除」这条退路，
顶部闪的那句也带「⚠ 有 N 个能改卡」。⚠ 顺带 `.st-code-skill-msg` 加 `white-space: pre-wrap`
—— 不然提示里的 `\n` 被折成空格挤成一坨，反而更难看见。

## 把「静默少走」变成硬闸门：`_verify/run-all.js`

上面那个坑（4 套被 grep 漏掉）只是**在文档里提醒**，属于「靠人记得」而不是闸门。
既然发现了，就顺手做掉：新写 `_verify/run-all.js`，把三件事变成**硬错误** ——

1. 某个套件**没有产出一行能解析的汇总**（空白 = `NO-SUMMARY` = 退出码非 0）；
2. **目录里多出没分类的 `.js`**（清单跟目录对账；新套件忘了登记当场就报）；
3. 任何 `failed > 0`。

⚠ **故意不写死「期望总数」。** 写死的话每次加断言都要改它，迟早退化成「永远在报的检查」——
那种检查只会被无视（`04-card-editor.md` 里有专条）。它只**打印**总数供跟 README 对照。
要抓的是「**少走了几套**」，不是「数字变了」。

⚠ 两条设计细节：
- `NOT_A_SUITE` 是**显式清单**，不是「不在 `SUITES` 里的都跳过」—— 后者正是新套件被永久无视的写法。
- `run-all.js` **自己也在 `NOT_A_SUITE` 里** —— 写的时候忘了，第一次跑就被自己对账拦下来了
  （「有 1 个 .js 没分类：run-all.js」）。检查在干活。

### 给 runner 自己也做反向测试（`_reverse3.js`）

- 探针 A：丢一个未分类的 `zz-new.js` → 必须退出非 0、**点名文件**、告诉该往哪写、且**在跑套件之前**就拦住。
- 探针 B：让某套不产汇总 → 必须标 `NO-SUMMARY`。

⚠ 探针 B 第一版**红了 3 条**：补丁用 `replace` 把 `'sb-verify.js'` 换成了 `'check.js'`，
于是 `sb-verify.js` 变成未分类，先撞上**对账**那道闸门 —— 退出码确实是 1，
但**没走到 `NO-SUMMARY` 那条路**。改成**前插**（`'check.js', 'sb-verify.js',`）才对。
⚠ 教训：**探针自己也要看「是哪道闸门响的」** —— 只看退出码非 0 就会「因为错的理由通过」，
和「新红的断言先想前提」是同一族。

## 把「约定」变成闸门：转义闸门 + `check.js` 不再读生成物

两个 runner 都做完了，回头收拾 CHANGELOG「还没做」里剩下的那条：

> **skill 返回值进 UI 前的转义**：查了一遍……现状是安全的；但这是一条**约定**而不是一道闸门。

现状确实全对（三条渲染路径都先 `escapeHtml`），可这类「**现状是对的、但没人守**」的东西最难保
—— 因为**没有失败可以复现**。所以先量了一下：写探针把 `stCode*Html` / `stCodeHighlight`
的函数体抠出来，找「没走 `escapeHtml` 的裸插值」，结果是 **11 个构建函数、24 条候选**
（全是数字 / 已转义的局部变量 / `ST_CODE_THINK`、`ST_CODE_TASK_ST` 这类静态常量表的字段）。
**24 条 → 白名单可行**；要是几百条，就说明判据太粗，做了也是「永远在报的检查」，不如不做。

闸门设计（`check.js` 第 5 项 `ESCAPE-GATE`）：把已安全的包装
（`escapeHtml` / `stCodeAttr` / `stCodeJsonText`）**整段抹白**，剩下的 `+ 变量` 是候选，
候选的**多重集**必须跟 `ESCAPE_ALLOW` 白名单**逐字一致**。
- ⚠ 按「函数名 + 标识符名」而**不是**行号 / 出现次序 —— 那两个会漂，这两个不会。
- ⚠ 用**多重集**而不是集合 —— 同一函数里再多一个裸插值，集合看不出来。
- ⚠ 白名单**显式**：新加构建函数、或在老函数里多拼一个变量，都必须来改它。

### ⚠ 顺手抓到一个更实在的：检查在读过时的输入

`check.js` 原来是 `readFileSync('blk0.js')` —— 而 `blk0.js` 是 `extract.js` 的**生成物**。
改了 `saki.html` 忘了重新 extract 就直接 `node check.js`，它检查的是**上一次**的源码，
而输出看起来**完全正常**（`MISSING: (none)` 照样打）。**过时的输入比没有检查更坏**：
它给绿灯，而你没有任何线索知道那是旧的。

修法：`check.js` 自己抽 `saki.html` 的内联 `<script>`，解析改用 `vm.Script`
（等价 `node --check`，但不用先生成文件）→ **快路径从三条命令缩成一条** `node check.js`。

## 把最后一份手写清单也推导掉（`check.js` 第 3 项）

`check.js` 第 3 项原先是 **45 个 `stSb*` 名字**逐个 `declared.has()`。它有两个毛病：
① 加了新函数要记得往里补，**它自己不提醒你**（又一份「约定」）；② 只覆盖清单里那 45 个，
清单外的名字一概看不见。

### 先量再做（`_probe-mine.js`，一次性）

量的是「推导式能不能完整覆盖这份清单的意图」。判据：清单里每个名字都**被引用过**吗？
只要被引用，声明一消失推导式就红 —— 清单是纯冗余。

```
引用总数：口径 A（不涂串）= 639，口径 B（涂串）= 631
手写清单：45 个名字
  声明集合里没有的（本来就该红）：0
  口径 B 里**从没被引用**的（推导式扫不到）：0
  推导式会误报成红的名字（应为 0）：0
加量：`ST_` 前缀单独扫 → 0 条；双前缀一起扫 → 0 条
```

结论：**45 个名字全部被引用** → 推导式完整覆盖，覆盖面从 45 扩到 **758**。
⚠ 我把 45 记成 43 过 —— 手写数组的长度别靠印象数，让脚本数。

⚠ **口径 A / B 差 8 个名字**：不涂串 639、涂串 631。差的 8 个全是字符串 / 注释里的
`stXxx` 字样。**当前它们碰巧都在声明集合里**，所以两种口径都干净 —— 那是**运气**，
不是保证。所以涂串器必须上。

### 改了哪些

- 抽出共享基础设施：`stripNonCode()`（状态机涂字符串 / 注释 / 正则，和外部
  `static_check.js` 同款）+ **两份** `declared` 集合。
- 第 3 项换成推导式：扫 `ST_[A-Z0-9_]{2,}` 与 `st[A-Z]\w*`，排除属性访问
  （看引用点**前 40 字符**是否以 `.` / `?.` 结尾），剩下的报 `UNDECLARED`。

### ⚠ 我自己犯的一个错，当场改回来了

第一版我把**第 1 项**的 `declared` 也换成了完整口径（含形参 / 解构 / for / catch / 对象键）。
那是**错的**：第 1 项查的是内联 handler 引用的名字，handler 在**全局作用域**执行，
合法来源只有顶层 `function` / 顶层 `const|let|var`。把局部变量和对象键也算成「已声明」，
只会**掩盖**真实的缺声明 —— 例如 `const obj = { toggleTab: 1 }` 会让
`onclick="toggleTab()"` 在函数声明丢掉时照样过。

修法：第 1 项保留自己的窄口径，第 3 项用 `declaredAll`。**两个检查语义不同，
就各建各的 `declared`，别图省事合并。**
