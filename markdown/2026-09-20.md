## Code 页加了「第一段」开关

用户原话：
> 请为为agent增加能够选择是否启用【第一段】

### 背景：第一段原来在 Code 页是**硬编码不带**的

上一轮（09-19）用户明确要求过「Code 页不受第一段影响」，所以 `stCodeSysMsgs` 里
**压根没有第一段这条路**。这次要把它变成**可选** —— 关键是**默认必须还是关**，
加开关不能顺手改掉老行为。

### 做法

| 层 | 改了什么 |
|---|---|
| 状态 | `stCode.useFirstSeg = false`（放在 `autoApply` 旁边，注释里写明「默认 false，因为原来就没有」） |
| 存取 | `stCodeSaveUi` 加一个字段；`stCodeLoad` 加一行 `typeof === 'boolean'` 判据（老配置缺字段 → 保持 false） |
| 核心 | `stCodeSysMsgs` 里 `if (stCode.useFirstSeg) { const seg = stAiFirstSegText(); if (seg) out.unshift(...) }` |
| handler | `stCodeUseFirstSeg(on)`：存 + `stCodeFlash` 顶一句（开着但空的时候要说清） |
| UI | 思维强度弹层的「其它」里，和「工具真的改卡」并排 |

**三个设计决定**：

- **文本只有一处**：在【AI 助手】页编辑，Code 页只放开关 + 字数 + 「去那边改」。
  一页存两处迟早分叉，分叉之后谁都不知道该信哪边。
- **复用 `stAiFirstSegText()`**：它已经处理 `{{char}}` 替换和「空着就不发」，重写=维护两处。
- **插在 `stCodeSysMsgs`**：消息的**唯一出口**（`stCodeSend` 只调它一个）。
  插那儿两条协议自动都对：Anthropic 侧 system 会被提到顶层并保持最前。

### 验证

`st-code.js` 的 I 节从「第一段隔离」改写成「**默认不带（老行为）+ 开关打开才带**」，
**622 → 639 条**（+17）：

- 默认关：两种协议的请求体里都没有第一段（老断言**全保留**，并且**开头就显式把开关关掉**，
  不依赖「默认值恰好是 false」——否则测的是「配置文件的当前状态」，换个环境结论就变）；
- 开关开：`messages[0]` 是第一段、`messages[1]` 才是 Code 的 system、role 是 system；
- Anthropic：进顶层 `system` 且排在 Code 那条之前，`messages` 仍以 `user` 开头；
- 空值边界：开着但空 → **不产生空消息**；关着但有内容 → 也不发（**对照组**）；
- 落盘：写进 `stCodeUi`、真走 `stCodeLoad` 能读回来、老配置（缺字段）读回来是 false。

⚠ **测试手法上有一处要记**：验「开关打开后的第一条」时改成直接调
`stCodeRequest(cfg, stCodeSysMsgs(s), {})`，**不再真 `stCodeSend()` 一遍**——
`stCodeSend` 是 `ev(..., true)`（不等 Promise），连发几次会有请求**晚落**在
`window.__aiCalls` 里，占掉后面节的 `__aiCalls[0]`。只在「必须真发」时才发。

⚠ 还有一条**我自己写错的断言**：「老配置读回来是 false」最初写成「先打脏成 true
再 `stCodeLoad`」，可 `stCodeLoad` 缺字段时是**保持现状**而不是**强制重置**，
所以那个测法**必然红**（产品是对的）。改成「干净起点（内存 false + 无该字段）→ 读 → 仍是 false」。

## ⚠ 本轮最大的坑：全局配置没切回来

I 节新加的 Anthropic 验证段用了 `useOwn('anthropic', ...)`，**没切回 openai**。

### ① `check.js` 第 3 项：45 个 `stSb*` 名字 → 推导式

**动机**：手写清单是**约定**不是**闸门** —— 加了新函数要记得往里补（它自己不提醒你），
清单外漏声明的名字一概看不见。

**做法**：先抽共享 `stripNonCode()`（状态机涂字符串 / 注释 / 正则）+ **两份**声明集合，
第 1 项留**窄口径**（顶层 `function` / `const`）、第 3 项用**完整口径**（含形参 / 解构 /
for / catch / 对象键），再扫 `ST_` / `st` 前缀标识符，引用过就必须声明过。

**换之前先量**（一次性探针 `_probe-mine.js`，跑完删）：

| 量什么 | 结果 |
|---|---|
| 手写清单实际几个名字 | 45（我原以为 43） |
| 其中从没被引用过的 | 0 → 推导式**完整覆盖**清单意图 |
| 推导式会误报成红的 | 0 |
| 口径 A（不涂串）/ B（涂串） | 639 / 631，差 8 全是字面量 / 注释字样 |

**两个坑**：
- ⚠ **涂串不是可选项**。`'stCodeSessions'` 这种字面量会被当成引用。
- ⚠ **两种「已声明」口径不能混用**。第 1 项（内联 handler）**只要顶层声明** ——
  handler 在全局作用域执行，把形参 / 解构 / 对象键算成「已声明」只会**掩盖**真缺声明

### ④ skill 自报进度 `host.progress`（用户选「完整」方案）

**缺口**：跑得久的 skill 在界面上完全没反馈（Agent 循环里工具 `await` 串行），
用户看到「正在思考」一直转。

**设计**：单向通道 + 自己的权限 + 自己的两道闸。

| | `host.call` | `host.progress` |
|---|---|---|
| 方向 | 请求-应答 | **单向** |
| 返回值 | Promise | **`undefined`** |
| 占 20 次预算 | 占 | **不占** |
| 消息形状 | `__host` | `__prog` |
| 权限 | `card.read`/`card.write` | `progress` |

⚠ **为什么单开一条**：20 次预算是给读卡 / 改卡的。逐条处理 50 项的 skill 光报进度就烧光，
**真正读卡那一次反被拒**。

三个设计决定：
- ⚠ **返回 `undefined` 不是 Promise** —— 返回 Promise 会诱导 skill 写 `await`，
  等一个永远不来的结果，5 秒后被超时掐掉而作者以为是自己算错了。
- ⚠ **两道闸**：`ST_CODE_PROG_MS = 120`（快了**丢**不排队）+ `ST_CODE_PROG_MAX = 200`。
  不给的话 `for(;;) host.progress()` 能让**父页面**重画几十万次（沙盒自己不卡 =
  独立进程；卡的是父页面）。单条 `ST_CODE_PROG_CHARS = 160`（**截断不拒收**）。
- ⚠ **`progress` 在能力表里映射空数组**：不是工具（走 `__prog`），但**必须在键里**
  （`stCodeManifestOf` 从这张表取「这里有哪些能力」）；反过来
  `stCodePermToolNames` 里**必须不出现**（拼进去会诱导 `host.call('progress')`，死路）。

细节：`finish()` 撤掉那句进度；**只清自己那条**（比 `stCode.prog.id` ——
上个 run 超时被拆时可能有 `__prog` 在路上）；渲染走 `stCodeProgressRefresh()`
（只换 textContent）**不是 `stCodePaint()`**（每条进度重建消息流会把用户往上翻的历史弹回底部）。

**验证**：`st-code.js` 新增 E11 段 **+24 条**（639 → **663**）。
新建 `_reverse7.js`（**4 探针 / 12 条断言**）：

| 探针 | 改什么 | 该红 |
|---|---|---|
| A | `onProg` 去掉权限判断 | 「没申请的那句被丢掉」 |
| B | 去掉节流窗口 | 「同一 tick 连发的第二条被丢」**且次数上限那条仍绿** |
| C | `finish` 里不撤进度 | 「返回之后那句被撤掉」 |
| D | `progress` 不在 `ST_CODE_SANDBOX_PERM` 里 | 「进了能力表」+「两边是一份」 |

⚠ 探针 B 特意多断言一条「**次数上限那条仍然绿**」—— 两道闸互不代替，只断言「红了」
分不清是哪个闸在起作用。
⚠ 探针 D 第一次锚点选错：两个常量里都有 `'progress'`，改错一个红的是**另一条**断言。

### ⑤ 这一轮红了 3 次，**全是断言写错、产品是对的**

| 红的断言 | 真因 | 修法 |
|---|---|---|
| 「能力表就两层」 | 写死了整个数组，加 `progress` 就红 | 改**推导式**（「必须在」，完整性交给对账那条） |
| 「两条进度都到了宿主」 | 探针**同 tick** 连发两条，第二条被节流丢（设计如此） | 探针 `setTimeout` 等过节流窗口 |
| 「还原后逐字一致」（`_reverse6.js`） | 套件每行带耗时，比逐字必然失败 | 比**汇总行** |

**通则**：**写死清单的断言，每次加东西都会来收一次「红」的账**，而那种红最容易被当噪音略过。

| Two channels are two contracts | `host.call` 请求-应答 / `host.progress` **单向**，返回 `undefined` 不是 Promise，**不占** RPC 预算 | 复用 setter 的直觉会让 skill 作者 `await` 一个永不到来的回复 → 挂到沙盒超时；而「报进度吃光改卡次数」的失败读起来像「权限坏了」 |
| Two rate gates | 最小间隔 + 次数上限是**两个**机制 | 反向测试要**说清哪道闸仍绿**，否则「红了」分不清是谁在起作用 |
| Your probe must obey the rule it tests | 探针同 tick 连发触发节流 | **功能完全正确，是测试错了** —— 探针是被测特性的客户端 |
| Pick the anchor that exists once | `PERM` 和 `PERM_TOOLS` 里都有 `'progress'` | 改错一个，红的是**另一条**断言（「两边是一份」），而你的假设那条照样绿 —— **红不是证据，除非确认红的是你那一条** |

⚠ 还有一条顺带记进小节的：**权限名映射到空工具数组是刻意的**（`progress` 不是工具，
走 `__prog` 不走 `host.call`），断言要分三条查 —— 在数组里 / 工具表为空 / 没有任何工具名混进去。

## 第五轮 · **反向测试抓到一个真 bug**（本轮的真正收获）

上一轮我把 `run-all.js` 跑绿（1664/0）就收工了。这次为了给技能补教训，
**重跑了一遍 `_reverse7.js`**，基线直接报 `661 通过 / 2 失败`。

### 现象

两条红的都是**「收尾后进度状态是干净的」这一族**：

```
· 返回之后进度那句话被撤掉了（不留在界面上）
· 而且挡住的是「丢」，不是「失败」（skill 拿到的还是成功）
```

两条查的都是 `String(stCode.prog) === 'null'`，实际是那句进度**留在界面上没被撤掉**。

### 根因：注释写了，代码没写

`saki.html` 的 `stCodeSkillRun` 里，`finish()` 有这么一段：

```js
if (frame && frame.parentNode) frame.parentNode.removeChild(frame);
// ⚠ 收尾要把进度那句话**撤掉** —— 不收的话它会挂在那儿，
//   而下一条消息已经进来了，看着像「还在跑第 7 条」
resolve({ ok: ok, ... });        // ← 注释说的那件事，没有代码
```

**`stCodeProgressClear(id);` 那一行从来没写进去。** 又是这个项目的老朋友：
**批量 Edit 报 success 但有一条没落盘**，而这次漏掉的是一条**语句**——
注释落盘了、`UNDECLARED` 静态检查看不见（函数**声明**存在、也被别处引用）、
`ESCAPE-GATE` 也不管。**只有行为断言抓得住。**

### 为什么上一轮没发现

⚠ **上一轮 `run-all.js` 报的是 `st-code.js 663 通过 / 0 失败`，而这次单跑是 `661 通过 / 2 失败`。**
同一份产品、同一个套件，**两个数不一样**。

两种可能，**这次没查清，下次必须查**：

1. **套件顺序有影响**——`run-all.js` 在前面的套件里跑过某个东西，
   恰好把那两句 `stCode.prog` 弄成了 `null`（比如某处调了 `stCodeProgressClear()`），
   于是断言在**全套里假绿**。若真是这样，这是比原 bug 更坏的一类：
   **一个只在单跑时红的断言，等于没有断言。**
2. 只是 `run-all.js` 那次没跑到（但 `[zh]` 那行数是真的 663，不像没跑）。

⚠ 已按「**每次加断言都要单独跑一遍它所属的套件**」记下来 —— 只跑 `run-all.js` 会漏掉这一类。

### 修法与验证

| 步骤 | 结果 |
|---|---|
| 补上 `stCodeProgressClear(id);`（放在 `resolve` 之前、拆 iframe 之后） | ✅ |
| 单跑 `st-code.js` | **663 通过 / 0 失败** |
| `run-all.js` | 12 套 **1664 通过 / 0 失败** |
| `check.js` | 5/0（`937` / `766` 未变，说明只加了一条语句） |
| `_reverse7.js` | **基线全绿**，4 探针全绿，还原后字节一致 |

**探针 C 的意义变了**：上一轮它是 `NOT FOUND`（锚点找不到），
现在它**真的在守这条修复** —— 删掉 `stCodeProgressClear(id)` → 那条断言红。**第一次看到它生效。**

### 教训（已写进技能）

- ⚠ **绿了不等于验证过了，等于「这次没红」。** 反向测试要**周期性重跑**，
  不能只在写它的那天跑一次 —— 产品后来变了，基线也可能跟着变。
- ⚠ **同一条断言在全套里绿、单跑时红 = 最坏的一类假绿**（套件间状态串味）。
  `run-all.js` 的汇总不能替代单跑。
- ⚠ **注释说什么 ≠ 代码做什么。** 一条只出现在注释里的语句，静态检查（语法、声明、
  转义闸门）**全部看不见**，只有行为断言抓得到。看到「注释承诺了某事」的地方，
  值得专门去 `grep` 一下那句话对应的函数调用**是否真的存在**。
- ⚠ **`_reverse7.js` 里 `NOT FOUND —— 锚点变了` 是响亮的信号，别当噪音。**
  上一轮探针 C 报 `NOT FOUND` 我只当成「锚点写错」，实际是**它要守的那行代码根本不在**。
  ⚠ **锚点找不到 = 待测的东西不在 = 可能就是 bug 本身**，先去产品里看一眼再改锚点。

## 第六轮 · 外部 8 层报的那 1 条红，是**字体时序**不是回归

第五轮修完单跑 `_reverse7.js` 时顺手复跑外部 8 层，报 **1627 通过 / 1 失败**
（早上还是 1628/0）。红的是 `verify_tavern_visual.js`：

```
✗ 移动端顶栏按钮触控高度 >= 32px  →  btnH: 31
```

### 定位过程

| 步 | 做法 | 结果 |
|---|---|---|
| 1 | **先问「我碰过这个吗」** | 本轮产品只加了一行 `stCodeProgressClear(id);`（19252 行），和按钮毫无关系 |
| 2 | 写一次性探针量真实盒子 | `h = 32`（连跑三遍都是 32）→ **单跑三遍视觉层全是 368/368** |
| 3 | 那就不是「红/绿」而是「有时红有时绿」 | 定性成**闪烁断言** |
| 4 | 量**输入**而不是量结果 | 查 `fontSize 12.48px` / `padding 6px` / `border 1px` / `border-box` |
| 5 | 同一页面里 `document.fonts` 状态 + 按钮高度**一起读** | **决定性证据** ↓ |

| 量的时刻 | 文本行盒 | 按钮高 |
|---|---|---|
| 本地像素字体还在 `loading`（兜底字体） | 13px | **31** |
| 7MB 字体加载完之后 | 17px | **32** |

`17 + 6*2 + 1*2 = 32`，兜底字体的 13px 给出 31 —— 而阈值**正好是 `>= 32`**。
所以这条断言的结论取决于「7MB 字体有没有在 `setViewport` 之后那 400ms 里下完」。
**产品完全正确，CSS 一点问题都没有。**

### 修法

套件里量之前显式等字体（`verify_tavern_visual.js` 12b 节，2245 行附近）：

```js
await sleep(500);
// ⚠ 触摸高度这两条断言坐在 1px 边界上：等字体就绪再量
await evaluate(`document.fonts.ready.then(() => true)`);
await sleep(300);
```

复跑：**368/368**；外部全套 **1628 通过 / 0 失败**，恢复。

### 教训（已写进技能）

- ⚠ **量出来的数**正好落在**阈值**上**，先量输入（字号 / 行高 / padding / border），
  最有力的是用 `Range` 量**文本行盒** —— 再在 `fonts.ready` **前后各量一次**。
  数动了 = 字体竞态，修**套件**不修 CSS。
- ⚠ **`getBoundingClientRect().height` 对「带文字的控件」= 行盒 + padding + border**，
  所以它继承**每一次字体切换**。断言余量小于字体行高差的，都是掷硬币。
- ⚠ **「我碰过这个吗」应该是第一个问题。** 这条红出现在一个我完全没动过的层里，
  而且**早上还绿** —— 但对**闪烁**断言来说「早上还绿」什么都不能证明。
  ⚠ 所以判据不能是「我改的」/「以前是绿的」，只能是**重复实验**：单跑三遍。
  一次红 + 三次绿 = 闪烁，不是回归。

一次性探针（`_probe-btn.js` / `_probe-btn2.js` / `_probe-fontbtn.js` / `_probe-fontbtn2.js`）

⚠ 这修正了已有铁律的**表现形式**：「批量 Edit 静默漏」不只表现为「报成功但没落盘」，

#### ⚠⚠ 收尾时发现：⑰ 那个坑，我**在新探针里原样又踩了一遍**（而且是「修它的时候」踩的）

1. **它从来没 `kill()` 过 Chrome。** 同族的 `_probe-stcard-anim.js` / `_probe-tabs-anim.js`
   收尾写的是 `ch.kill(); srv.close(); dropProf();`，我这个只写了 `dropProf()` ——

2. ⚠⚠ **我加的那层「修好它」的 `try/catch` 又把失败吞了** —— 而且吞的不是 EBUSY，是
   **`ReferenceError`**：`ch` / `srv` 是在 async IIFE 里 `const` 出来的，

- `dropProf()` 的 `catch` 改成**出声**（打印路径 + `e.code`）—— 静默失败是这次能被发现的唯一原因，
  是因为我**主动去数了**；把出声做进工具里，下次不用靠自觉。
- 顺序：`kill()` → `close()` → `await sleep(400)` → `dropProf()`（内含 8 次重试）。

> 以及 **`.finally` / 回调 / `setTimeout` 里引用的变量，先确认它在不在作用域里** ——
> 越界引用在 `try/catch` 里长得跟「成功」一模一样。

- ⚠⚠ **「菜单收起后看不见」这条不能只量 `getBoundingClientRect()`。**

#### 一条通则

> ⚠ **用户改主意时，先改「断言」再改「产品」。** 反过来做的话，你会先把产品改对、
