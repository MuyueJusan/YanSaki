## 二、⚠⚠ 本轮最值钱的一条：**「签名验证通过」是一条永真断言**

`verify.sh` 原来那段签名检查长这样：

```
Verifies
Verified using v1 scheme (JAR signing): true
Verified using v2 scheme (APK Signature Scheme v2): true
Verified using v3 scheme (APK Signature Scheme v3): true
```

它只查 `^Verifies` + v1/v2/v3 三行。**问题是：这三行对任何一张证书都为真。**
换密钥、换成别人自签的密钥、甚至换成攻击者的密钥 —— 它照样全绿。
⇒ **判据必须能区分「哪张证书」，而不是「有没有证书」。**

而且这条和「signing identity **就是** app identity」是同一件事的两面：
**签错密钥的包，签名验证全部通过，然后装不上**（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），
**只有在真机上才会发现**。静态检查一个字都测不出来。

### 改成**往返判据**（`verify.sh` §2b）

```
WANT = keytool -list -v  →  密钥库里的证书 SHA-256
GOT  = apksigner verify --print-certs  →  APK 的签名者 SHA-256
断言 WANT == GOT
```

三个配套细节，缺一个就退化成永真：

1. **期望值必须当场从密钥库推**，不能写死。
   写死的指纹 = 过时断言：换密钥后它永远红；更坏的情况是它**永远绿**。
2. **两边都先做形状检查**（`^[0-9a-f]{64}$`）再比。
   否则「两次解析都失败」⇒ `空 == 空` ⇒ **绿**。
   换个工具版本、改个输出格式，这条断言就静默失效 —— 而它看着完全正常。
3. **`keytool` 的输出跟着 locale 变**。中文环境打的是「所有者:」不是 `Owner:`，
   所以必须 `-J-Duser.language=en`，否则 `grep` 静默返回空串（然后被第 2 条兜住）。

### 两个方向都验过（缺一不可）

| 注入 | 期望 | 实测 |
|---|---|---|
| 用 **debug 密钥**签同一个包 | 身份行红 | ✅ 红，退出码 1 |
| 把口令**改错** | 形状行红 | ✅ 红，打印「（空）」，退出码 1 |

两条都不会静默放过。**「对照」≠「必然绿」**：这里第二个注入打的是形状检查，
不是身份比对 —— 它证明的是「读不出指纹时会红」，不是「指纹不同时会红」，两个注入各证一件事。

## 三、⚠⚠ `set -euo pipefail` 下的两个陷阱（都踩过）

- 两个脚本都开着 `-u` ⇒ **引用未设的变量会当场中止脚本**。
  所以新写的每一处引用都得是 `${VAR:-}`。
  否则「没配密钥」（本该走 debug 回落）会被伪装成「脚本崩了」，报错方向全歪。

- ⚠⚠ **`set -e` 会豁免 AND-OR 列表里的「非最后一项」** —— 这条我**差点写反**，所以留实测记录：

  ```
  $ bash -c 'set -euo pipefail; false && echo A; echo B'
  B                                  ← 不中止！rc=0
  $ bash -c 'set -euo pipefail; node --check 坏文件 && echo 通过; echo 后续'
  后续                                ← 不中止！rc=0
  $ bash -c 'set -euo pipefail; node --check 坏文件; echo 后续'
  （报错，没有「后续」）              ← **裸调用**才中止，rc=1
  $ bash -c 'set -euo pipefail; if true; then false && echo A; fi'
                                     ← 块内最后一条 ⇒ rc=1（是「退出码」，不是「中止」）
  ```

  ⇒ 真坑在 `build.sh:119`：`node --check "$ASSETS/ys-ai-shim.js" && echo "   node --check 通过"`
  —— **垫片语法检查失败时，构建照跑**（实测 rc=0，后续步骤全跑完）。
  而垫片语法错的表现是「页面上什么都没发生」（`evaluateJavascript` 的报错只进 logcat）
  —— **正好是最需要拦住的那一类错**。
  ⇒ 所以「这条检查做过」必须由**独立断言**盯着
  （`tools/reverse-ai.py` 里 `check('node --check 通过' in bout, …)` 就是为它存在的），
  **不能指望 `set -e`**。通用形态：**「喊一声」不是「拦一道」**。
  ⇒ 同一个豁免的另一面：`[ cond ] && cmd` 当**脚本 / `if` 块的最后一条语句**时整体返回 1
  ⇒ **退出码变成失败**（假红）。所以「有则执行」写成 `if` 更好 ——
  不是因为它会中止（**中间位置不会**），而是不想让读者去记这条冷知识。

  ⚠ 顺序上我是**先改了 `verify.sh`、并在注释里写下「会当场中止脚本」这个理由**，
  然后才去做实验 —— 结果注释里那句是错的，已回头改成正确理由。
  **一条「看起来天经地义」的规则，恰恰是最该动手跑一遍的那条。**

## 四、⚠⚠ 删 release **不会**删 tag

`release.js` 用 `target_commitish` 在**建 tag 的那一刻**定位 commit。
⇒ 如果 tag 已经存在（比如上次发布留下的），新 release 会**指到旧 commit**，
而 release 页面看着完全正常。

实测：删掉 `apk-v1.2` 的 release 之后，`GET /git/ref/tags/apk-v1.2` 仍然 **HTTP 200**。

⇒ 清空重来必须**两步**：删 release **+** 删 tag ref
（`DELETE /repos/{o}/{r}/git/refs/tags/{t}`）。

本轮：三个旧 release（v1.0 / v1.1 / v1.2）+ 三个 tag **全部删掉**，远端 release 归 **0**、`apk-v*` tag 归 **0**。

## 八、安全检查（commit 前必做）

```
git check-ignore -v android/keystore/YanSaki-13.jks   → .gitignore:36  ✅ 忽略
git check-ignore -v android/keystore/signing.env      → .gitignore:40  ✅ 忽略
git check-ignore -v android/keystore/debug.jks        → （无输出）     ✅ 未被忽略，仍跟踪
```

`.gitignore` 那三行：

```
android/keystore/*.jks
!android/keystore/debug.jks
android/keystore/signing.env
```

⚠ `debug.jks` 放行的理由：口令就是公开的 `android`，和 Android Studio 默认那份同性质，
入库反而有用（保证每次重建签名一致、能原地升级）。**真密钥没有这个性质** —— 本仓库是**公开**的。
⚠ `!` 那行还有个作用：防止「哪天 debug.jks 被删了重新生成，就再也 add 不回来」。

⚠⚠ **本轮真正的教训：`git check-ignore` 只证明「敏感文件」没被跟踪，
证明不了「敏感字符串」没写在别处。** 提交前那一遍全仓 `grep` 就抓到一处 ——
**我把口令明文写进了这份日志**，而日志会被 `cp` 到 `markdown/`（**入库**）。
⇒ 两道检查都要做：

1. `git check-ignore -v <密钥文件>` —— 确认敏感**文件**被挡；
2. `grep -rn '<口令>' --exclude-dir=.git .` —— 确认敏感**字符串**没躺在任何入库文件里。

⚠ 而且连**被忽略的那份日志**也不该记口令 —— 它随时会被同步进仓库，
而「同步」这个动作**不会替你审查内容**（它只是 `cp`）。
