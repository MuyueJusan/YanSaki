## 一、编写器通用（`st*` 命名空间）

- **16 个选项卡**：`home / name / spec / desc / sys / meta / ai / book / greet / regex / th / mvu / sb / code / persona / export`。
  ⚠ `home`（首页）**排在最前**，而且是**默认落点**（`stEditor.tab` 写在三处：初值 / `stLoadDraft` 回落 / `stNewCard`）——
  用户指定。⚠⚠ 加 / 删选项卡要同步改**六处**写死的数字（⚠ 这份清单**已经错过两次**：三处 → 五处 → 六处，
  三次都是整跑才红 ⇒ **别信条数，先 `grep`**），见 `04-card-editor.md` 二。
  ⚠ `persona`（人设生成器）排在 **`code` 后面**，不是 `desc` 后面 —— 用户指定的位置。
- **数据是唯一事实来源**，生成物由结构推出来：
  `card.mvu.nodes` → Zod 脚本 / `[InitVar]` YAML / 更新规则 YAML；
  `card.statusBar` → 「状态栏界面」正则的 `replaceString`。
- ⚠ **`stSet(path, v)` 只写标量叶子**：`cur` 是对象（块对象 / 变量节点 / `statusBar` / `mvu`）一律拒绝。
  以前没这道保护，传错路径会把整块写成 `''`，接着所有「按 id 找块」的遍历全部崩。
- **两种路径别混**：`stSbChain(id).slice(-1)[0].path` 是**块路径**（`card.statusBar.blocks[0]`）；
  字段路径还要 `+ '.color'` 这样。字段构建器（`stInput` / `stArea` / `stSbColorField` …）拿到的
  必须是**字段路径**。
- **DOM id 约定**：`stMvuDomId(id)` / `stSbDomId(id)` = 前缀 + 去非法字符后取末 16 位。
  节点 id 是 uuid（含连字符），**不能**拼成 `'st-mvu-' + id + '-field'` —— 元素不存在，
  断言会静默变 false。同一块在图层和画布里都要出现时，画布那份用 `data-*` 不用 `id`。
- ⚠ **递归遍历块树时，「这一层没有子块」= 空列表，绝不能兜底回根列表**。
  `stSbLocate` / `stSbChain` 早先写成 `list || 根列表`，任何一块的 `children` 是假值
  都会原地转圈到爆栈。现在用「一个参数都不带」识别「从根找起」+ 深度上限 40。
- **编辑时保光标**：`stAfterSet` 默认只存不重画；文字字段一个字一个字敲，重画会把光标顶掉。
  只有「字段显隐会变」（如换 `type`）才 `stRerender()`。需要局部刷新就写 `stXxxRefreshRow(path)`。
  ⚠ **但别把输入框元素本身换掉**：`input[type=color]` 在部分浏览器里边拖边触发 `input`，
  换掉元素取色器会当场断。
- **数值范围可以负**（好感度 -100~100）：`min`/`max` 有专门的 `isRange` 分支，
  **不能**套通用的「夹到 >= 0」。要夹的尺寸类字段按**字段名**查表（`ST_SB_NUM_RANGE`）。
- 复古皮肤 `body.retro-mode` 要跟着覆盖新加的样式；`@media (max-width:760px)` 里多栏要堆成一栏。

### 一之补 · 状态栏「预制块」（第 8 轮新增，`04-card-editor.md` 十三）

四个入口**语义完全不同**，别当成「又一个模板」：

| 入口 | 数量 | 点一下发生什么 |
|---|---|---|
| 版式模板 `ST_SB_TEMPLATES` | 6 | **整张画布换掉**（带 confirm） |
| **预制块 `ST_SB_PREFABS`** | **16** | **加一整组**（多块 + 分组） |
| 块库 `ST_SB_BLOCKS` | 9 | 加**一个**原子块 |
| 我的预制块（`localStorage['stSbPrefabs']`） | 用户攒 | 加用户自己存的那一组 |

- ⚠⚠ **`stSbPrefabApi().blk(type, bind, extra)` 的顺序必须是「先 extra、后 bind」**。
  反过来写时踩过：星级预制块的 `extra` 里带 `max: 5`，把**绑到的变量自己的范围**一起盖掉了 ——
  卡里 0~100 的好感度被压成 0~5，值 50 直接顶满，**五颗星永远全亮**；而套件里
  「绑上了吗」那一类断言**照样全绿**（路径对、标签对，只有范围错了）。
  ⇒ 硬规矩：**变量自己的 `min`/`max` 永远赢过预制块自带的兜底范围**（同 `stSbAutoPick` 的理由）。
- ⚠ **复数（多人好感度）不能循环调 N 次单绑**：`used` 表只挡「**同一条**路径」，
  三个槽会**全绑同一个变量而且不报错**（提示语还会从「2/3 绑上了」变成「都绑上了」——
  **提示语本身也是判据的一部分**）。必须走 `stSbPrefabBindMany`，按变量树序捞 N 个**不同**的。
- ⚠ **`stSbBlockFromRaw` 对垃圾输入是宽容的**（非对象 → 返回一个**空白块**）。
  这在**草稿解析**那儿正合适（半截卡也得能打开），但读**用户存的**预制块时不行 ——
  一份「全是垃圾」的 list 会变成一份装着两个空文字块的**幽灵**，名字看着还正常。
  ⇒ 读用户数据前一律先卡 `if (!b || typeof b !== 'object' || Array.isArray(b)) return;`
  （`stSbUserPrefabs` / `stSbCloneBlocks` **两处都要**）。
- **用户预制块不进草稿**：`localStorage['stSbPrefabs']` = `{ v: 1, list: [...] }`，**跨卡共用**。
  同名 = **覆盖 + confirm**（单入口，少一处「到底改了哪个」的歧义）；
  闸门 = 单条 40 KB / 总计 160 KB / 最多 60 条，**写失败必须说出去**（不静默丢）。
- **绑不上不留「未选变量」的坑**：写**兜底路径**（后续建同名变量即通）+ 用 `warn` 当面说清
  「几个绑上了、几个还是默认路径」。
- ⚠ 新构建函数 `stSbPrefabHtml` 要**点名**进 `check.js` 的 `RE_FN` + `ESCAPE_ALLOW`
  —— 闸门**故意不全收** `*Html`（全收会命中 **27 个**函数，`stSbBlockHtml` 一家 60+ 个裸值）。
  **缺口写在 `RE_FN` 上方，不藏。**
- ⚠ **别按 `.st-sb-palette` 这个类数按钮** —— 预制块那一区**复用了同一个类**，
  旧选择器会数到 9 + 16 = 25。按 handler 前缀 `[onclick^="stSbAddBlock("]` 取。
  **复用 CSS 类是对的（长得一样就该共用），但测试不能按类数数。**

### 一之补二 · 让 AI 生成预制块（第 9 轮新增，`04-card-editor.md` 十三）

第 5 条路：**写一句中文，模型拼好一组**。它**不直接动画布** ——
先落进「我的预制块」，再点一下才进画布。**生成的结果必须先能反悔。**

整条链**复用**已有的 AI 调用（`stAiCfg` → `stAiReady` → `stAiChat` → `stAiJsonOf`），
**没有另起一套配置或请求**。`stream: false` —— 要的是 JSON，边吐边解析没意义。

- ⚠ **只要块，不要 HTML**。模型回 `{ name, icon, blocks: [...] }`，每块过
  `stSbBlockFromRaw` 那份白名单。**不让它回一整段 HTML** —— 那等于把
  「解析别人的手写状态栏」那条最难的路再走一遍，而且整段 HTML 过不了字段白名单。
- ⚠ **把卡里真实的变量路径喂进提示词**（`stSbVarPaths()` 前 80 条：路径 + 类型 + 范围）。
  不喂的话它会编 `stat_data.生命值`，而卡里那个叫 `hp` ⇒ 生成出来**全是死路径**。
  卡里还没建变量时明说一句，让它自己起 `stat_data.xxx`，并告诉用户「建了同名变量就通」。
- ⚠ **不覆盖同名的**（`stSbAiUniqueName`：`战斗面板` → `战斗面板 2`）。
  AI 生成是异步的，弹 confirm 问「要覆盖吗」很别扭；**静默覆盖别人的东西更糟**。
- ⚠ **模型不许碰「保原样」那几组字段**（`stSbAiClean`）：`offX/offY/w/h`、
  `extra/extraInner/extraFill/wrapExtra`、`clsMap/clsOwn` 一律归零，**递归到子块**。
  它们存在的意义是「解析别人的手写状态栏时别动原作者写的东西」，
  而这里生成的是**全新的块** —— 模型瞎猜一个偏移只会把外观锁死。
- ⚠⚠ **两个上限各自独立**：`n > ST_SB_AI_MAX_BLOCKS || deep > ST_SB_AI_MAX_DEEP`。
  踩过一次：只判块数 ⇒ 一棵「5 块、**深 5 层**」的树两个数都没超 24，裁剪根本没跑，
  **深度上限形同虚设**。**任何一个超了都要裁。**
- ⚠⚠ **超深时是「摊平」，不是「砍掉子树」**。砍掉会把内容一起丢 ——
  `row>row>row>row>文字` 砍完只剩三个空 `row` ⇒ 被判「空块」整份拒收，
  用户看到「AI 生成失败」而他明明给了内容。**丢层级可以，丢内容不行。**
  （现场是 `actual=0`，看着像「裁剪写错了」—— 先问「这棵树本来该剩几块」。）
- ⚠ **忙态从状态渲染**（`stEditor.sbPfAiBusy`）：`stRerender()` 会把整个 pane 重建，
  只改 DOM 的话「⏳ 生成中…」一重绘就没了。描述那格同理（`stEditor.sbPfAiDesc`）。
- ⚠ 结果提示要说清**几个路径对得上**（跟预制块插入同一口径）：
  `✅ AI 生成了预制块「X」（N 块，h/m 条路径对得上卡里的变量（剩下的建了同名变量就通））`；
  一组里一个 `path` 都没有时**不提这个数**（不提 `0/0`）。
- ⚠ 新构建函数 `stSbAiRowHtml` 同样要**点名**进 `check.js` 的 `RE_FN` + `ESCAPE_ALLOW`
  （裸值只有 `ST_SB_AI_DESC_MAX` 一个写死的常量，用在 `maxlength` 上，没有外部输入）。
- ⚠ 写「AI 生成」的套件时：**清库必须走 `stSbPfStore([])`**（裸 `localStorage.removeItem`
  清不掉内存里那份 `stSbPfCache`）；**填满 60 条时 `blocks` 不能是空的**
  （`stSbUserPrefabs()` 会把「没有块」的条目**整条跳过**，得到 0 条，看着像 store 坏了）。

### 一之补三 · 人设生成器（第 11 轮新增，`04-card-editor.md` 十六）

- **模板存浏览器本地**（`localStorage` 键 `stPersonaTpl`），**不写进卡** —— 同 AI 配置那条理由。
- ⚠⚠ **「清空 = 回到默认」要两处一起做，只做一处就会自相矛盾。**
  `stPersonaTplSet('')` 要**删键**（不是存空串），**而且** `stPersonaTpl()` 在内存值是空串时
  也要**回落默认**。少做后一半的话，面板上会同时出现三种说法：标签写「（默认）」
  （它问的是 `localStorage`）、框里是空的、点生成又报「模板是空的」。
  ⚠ 这条是**写回归套件时才发现的** —— 断言的方向就是需求，写测试会逼出没想清楚的地方。
- ⚠ **`personaTpl` 初始化必须是 `null` 而不是 `''`**：用 `typeof !== 'string'` 判「还没读过」，
  初始化成空串那个判断就永远成立，自定义模板永远读不出来。
- ⚠ **「现在用的是不是默认」问 `localStorage`，别拿当前值跟常量比** ——
  用户把自定义模板改得跟默认一模一样时，两种说法都不算错，但**显示要跟存储一致**。
- **生成结果不自动进卡**：先进 `stEditor.personaOut` 给你看、可手改，点「写入」才进角色描述。
  **覆盖非空描述前弹 `confirm`**（这一族里唯一不可逆的动作）；追加不用问。
  追加时描述本来是空的就当写入 —— 否则会留一个空行开头。
- **围栏清洗只做一种**（` ``` ` 包着就去掉）。再多的「智能」清洗会顺手吃掉真正的第一行，
  而那种错**看不出来**：输出照样有内容、照样能写进卡。套件里要配「**没包围栏的不许动**」作对照。
- ⚠ **模板里的冒号半角 / 全角混着用**（用户给的那份就是），字段识别必须是 `[:：]`。
  只认半角会**静默少认 9 项**，而面板照样渲染、生成照样成功 —— 只有「项数独立算一遍」抓得住。
- ⚠ **`stPersonaLabels()` 要去重**：`风格` / `标志性穿着` / `配饰习惯` 在三种装束下各出现一次，
  42 行 → **36 项**。数出来的是「字段数」，不是行数。
- 生成完报 **「模板 N 项里对上了 M 项」**，漏项时 `warn` —— 只说「成功」的话，
  模型悄悄改写了标题用户是看不见的。
- 模板 / 生成结果 / 忙态**全部进 `stEditor`**（`stRerender()` 会重建整个 pane）。

## 二、AI 助手（第 6 个选项卡）

- **两套配置二选一**：`stAi.mode = 'follow'`（默认）**现读** `aiConfig`（不是复制）；
  `'own'` 读自己的 `stAi`。`stAiCfg()` 是唯一取配置入口。
- **配置一律不进卡**：`stAi` 存 `localStorage['stAiCfg']`、面板参数 `stAiUi` 存 `stAiUiCfg`
  （不含密钥）。`stCardDraft` 与导出里都没有 Key 的影子。
- **双协议**：13 个预设服务商里**只有 Anthropic 走 `/messages`**，其余全 `/chat/completions`。
  Anthropic 的 messages 必须以 `user` 开头、不能连续同角色（`stAiMergeRoles`），system 提到顶层。
  「发去哪、带什么头」抽在 `stAiEndpoint`（`stAiRequest` 与 `stCodeRequest` 共用）；
  `stAiRequest()` 是**纯函数**，验证套件直接断言 URL / 头 / 体。
- **`stAiJsonOf` 要兜三种脏回复**：三反引号围栏、前后寒暄、尾逗号。
- **生成结果先预览再落卡**：`stAiEntryFromAi` 认不出的字段一律退回默认值，
  越界的 position / depth / order 夹紧，正文和关键词都空的直接丢掉。
- **开场白的注入顺序**（`stAiInjectList`）：停用跳过、Outlet 跳过、空正文跳过，
  按 `↑Char→↓Char→↑AT→↓AT→@D→↑EM→↓EM` 分组，**`@D` 组内按 depth 从大到小**
  （depth 越大离最后一条越远，插得越靠前），同深度再按 `order`。
- **面板参数不能只活在 DOM 里**：`stRerender()` 会重建整个 pane。
  `stAiUiSet`（只写状态）/ `stAiUiSetR`（写+重画）/ `stAiRepaint()` 三种写法分工，
  `<details>` 的 open 也记在状态里靠 `ontoggle` 写回。
- ⚠ **共用的前置检查要能按调用方关掉其中一条**：`stAiReady(cfg, {needModel:false})`
  —— 「拉模型列表」那一步本来就是为了挑模型，要求先有模型就成了死循环。
- **批量新增与单条改写是两套参数**（`ex*` / `en*`）别混用：前者问「生成几条、从哪取素材」，
  后者问「改哪一条、要不要参考别的条目」。
- ⚠ **单条改写用条目 `id` 记状态，不用下标**（`enOpenId` / `enPreview.id` / `enErrId` / `enMsgId`）：
  条目移动 / 删除时下标会漂，状态挂到别人身上。生成期间条目可能被删 →
  回来**按 id 重新找一遍**再写。
- **「参考其他条目」三层过滤**：排除自己、排除空壳、按范围（仅启用 / 全部 / 同分组）。
  `同分组` 在条目没有 `group` 时**静默退回「仅启用」**——别给永远参考不到东西的选项。
- **错误 / 提示要认领到条目上**（`enErrId` / `enMsgId`），否则 A 报的错挂在 B 的面板上。
- **空值不覆盖**：模型给空 keys / 空 comment / 空 content 就保留原来的
  （它偷懒给空数组 ≠ 用户想清空）。
- **「第一段」永远是最前面那一条**（`aiConfig.firstSeg` / `stAi.firstSeg`）：
  `stAiPlanMessages(plan)` 是三个功能面板的唯一出口（第一段 → system → user）。
  角色必须是 `system` —— Anthropic 要求 messages 以 `user` 开头且 system 提到顶层，
  换成 user 塞最前就变成「先说话再给指令」。**空着就整条不发**（同「零值零字节」）。
  它插在 `buildRequestPlan` 两条 `return` **之前** → 开不开酒馆都在最前，
  且**不受「系统提示词」开关影响**。编写器只认 `{{char}}`；AI 对话那边走 `applyUserMacros`（两个宏都换）。
- **提示词结构预览**（`stAiMsgPreview`）四处共用：AI 助手页是**骨架**（真实第一段 + 两条占位），
  扩写 / 单条改写 / 开场白三处是**真实内容**。⚠ **展开状态不进 `stAiUi`** —— 靠 `<details>` 自己管：
  存进状态就意味着每次 toggle 都要 `stRerender()` 重建整个 pane，滚动位置当场丢掉；
  而 plan 纯粹是字符串拼接，算一遍很便宜。预览里必须带**协议说明**，
  否则用户看到 Anthropic 的 messages 只剩一条会以为第一段丢了。

## 三、Code（Agent）页（第 13 个选项卡）

- **模型自己调工具改卡**，不是「生成文本让你贴」。**19 个内置工具 + 工具型 skill**：`read_card` /
  `write_text` / `write_list` / `list_world_entries` / `read_world_entry` / `add_world_entry` /
  `update_world_entry` / `delete_world_entry` / `list_skills` / `read_skill` / **`fetch_url`** /
  **`set_tasks`** / **`remember`** / **`read_doc`** / **`write_doc`** / **`read_regex`** /
  **`write_regex`** / **`read_th`** / **`write_th`**（最后六个见「三之补二」，
  工具型 skill 与读写预算见「三之补三」）。
  ⚠ **工具表的唯一真相源是 `stCodeToolDefs()`**（= `ST_CODE_TOOLS` + 已装好的工具型 skill），
  `stCodeToolsFor(proto)` 只负责把它映射成两套协议的 `tools[]` 形状。
  **别再往 `ST_CODE_TOOLS` 里加动态东西** —— 那样两套协议会分叉。
- ⚠ **`stCodeTool` / `stCodeToolRun` 是 async 的**（`fetch_url` 要真发请求）。Agent 循环里
  必须用 `for...of` + `await`，**不能用 `forEach`** —— forEach 不认 async 回调，
  每个工具结果都会变成 `{}`，而且**不报错**，模型只会看到一堆空结果。
  套件里调 `stCodeTool` 必须 `ev(..., true)`（awaitPromise）。
- ⚠ **`fetch_url` 是唯一会发网络请求的工具，闸门必须留着**（`stCodeUrlGuard`）：
  只放行公网 http/https，拒 localhost / 回环 / 10. / 172.16-31. / 192.168. / 169.254.
  （云元数据）/ 100.64-127. / `.local` / 非 http 协议。理由：**模型能指挥用户的浏览器
  去访问任意地址** —— 用户在自己电脑上开着这个页面，`localhost` 上可能跑着别的东西。
  残余风险：只按字面主机名判断，挡不住 DNS rebinding，浏览器里做不到更严。
  读响应体要**边读边卡上限**（`stCodeReadCapped`），不能先 `resp.text()` 再截断。
- ⚠ **skill 仍然是「用户导入」，模型不能自己装**：没有 `add_skill` 工具。
  四个入口 —— 选目录（`webkitdirectory`）/ 选文件 / 拖拽（`stCodeDragDrop` +
  `stCodeEntryFiles` 递归读目录）/ **从链接导入**（`stCodeImportUrl`，页面去 fetch，
  模型不参与）。四者共用 `stCodeImportFiles` → `stCodeSkillFromText` → `stCodeSkillsMerge`，
  **同名以后导入的为准**。
  文件过滤规则只有一条：`SKILL.md` 一律收，别的 `.md` 只在**一共没几个 .md** 时才收
  （拖一整个仓库进来不会把满仓 README 塞进去）。
- ⚠ **拖拽的 `dataTransfer.items` 只在 drop 事件处理期间有效** —— 必须在**同步**的
  处理函数里先把 `webkitGetAsEntry()` 取出来，再去 await 读文件。反了就是空列表。
  `readEntries` 一次最多给 100 条，**必须循环读到空数组**。
  拖拽高亮**直接改 DOM class、不走状态**（dragover 一秒几十次，走状态就是频闪）。
  另有全局兜底（`stCodeInstallFileDropGuard`）：往页面别处丢文件时拦住浏览器默认的
  「直接打开」，但**只拦 `types` 含 `Files` 的**，否则会废掉状态栏编辑器的拖拽换位。
- ⚠ **导入的反馈挂在 `stCode.skillErr` / `skillMsg`，不借 `stCode.err`** ——
  那个只在会话为空时才渲染得出来，有消息时用户什么都看不到。
- **导入的地址（`stCode.skillUrl`）活在状态里但不持久化**：`stCodeRepaint()` 会重建整个 pane，
  只放 `<input>.value` 里的话一次重画就没了；但地址可能带私有仓库的 token，不该落盘。
- **写路径一律白名单**（`ST_CODE_TEXT_PATHS` / `ST_CODE_LIST_PATHS`）。放模型自由写路径
  等于给它一次「把 `card` 整个写成字符串」的机会 —— `stSet` 只写标量叶子，写坏了整块都没了。
  越权路径**报错而不是静默**（静默的话模型会以为改成功了，接着往下做）。
- **删世界书条目进回收站**（`stCode.trash`），能撤回。删是不可逆操作，不给后悔药的 AI 很危险。
- **`list_world_entries` 只给摘要**（编号 / id / 备注 / 关键词 / 启用 / 正文开头），
  要正文得单独 `read_world_entry` —— 世界书几十条，一次全塞进上下文直接把窗口烧掉。
- ⚠ **文字和工具调用是同一条消息的两半。** 模型一轮里既说了话又要调工具时，必须合成
  **一条** assistant（带 `content` + `tool_calls`）—— 记成两条的话 Anthropic 会因
  「连续两条 assistant」直接 400，OpenAI 会因「带 `tool_calls` 的消息后面没紧跟 `tool`」报错。
  **这一条只有套件的「消息序列」断言抓得到**，光看「工具跑了没」根本看不出来。
- ⚠ **给用户看的一句话提示（`note`）绝不能发给模型**：`stCodeSysMsgs` 里过滤了，
  `stCodeMessagesFor` 里没有 —— **两处都要堵**。Anthropic 那边还会把它当 user 消息，
  直接触发「连续两条 user」。
- **不受「第一段」影响**（用户明确要求）：`stCodeMessagesFor` **自己拼** `[system] + 会话消息`，
  完全不经过 `stAiPlanMessages`。有一条断言专门盯：给 `stAi.firstSeg` 填哨兵串，
  Code 的请求体里不能出现它。
- **版式**：`@media (max-width: 900px), (orientation: portrait) and (max-width: 1100px)`
  下单栏 + `【code】/【Agent】`切换。
  ⚠ **不能用 `display:none` 藏另一栏** —— 那样切回来时滚动位置和输入框内容都还在 DOM 里
  但看不到，用户会以为丢了。做法是两栏都渲染、只切 `view` 类，切换状态存 `stCodeUi.view`。
  `#st-panes` 在 Code 页要加 `st-code-mode`（`overflow:hidden; padding:0`）——
  否则外层那个滚动容器会把两栏各自的高度撑坏，右栏的消息列表滚不动。
- **思维强度**（`ST_CODE_THINK`：关 4 / 低 8 / 中 12 / 高 20 步）只改 system 里「怎么做」的
  措辞和步数上限，不动协议。
- 会话存 `localStorage['stCodeSessions']`，最多 40 个。会话是**跨卡**的 —— 换一张卡会话还在
  （消息里本来就带着「当时改的是什么」）。标题取第一句用户输入。

### 三之补 · skill 自动注入 / 任务清单 / 项目记忆

这三样都是「让这个领域 agent 更像一个真 agent」的补丁。共同点：**全都不进角色卡**。

**① skill 自动注入（`stCodeSkillAuto`）**

「只列名字、模型自己伸手读」是**概率性**的 —— 它可能该读没读、读了没照做。
所以再加一条**确定性**的路：用户这句话命中触发词，就把正文**直接拼进 system**。

- 触发词来源：frontmatter 的 `triggers` / `trigger` / `keywords`（三种写法都认），
  分隔符 `,` `，` `、` `;` `；` `/` `|` 换行都算（`stCodeTrigList`）——
  触发词是人随手写的，全凭手感。
- **没写触发词就退回用 `name` 兜底**（`stCodeSkillTriggers`），零配置也能用起来。
- `@skill 名字` 是强制加载，触发词写得不合适时用户的兜底手段。
- 面板上每个 skill 一个输入框（`stCodeSkillTrigSet`），⚠ **`oninput` 只存不重画**。

⚠ **单字触发词一律丢掉**（`length >= 2`）。一个「的」字等于每条消息都命中 ——
那不是触发，是把整个 skill 常驻进上下文，白烧 token。

⚠ **命中结果累积在会话上**（`s.autoSkills`），不是只算当前这一句：用户说
「改一下状态栏」（命中），接着说「再换个颜色」（不命中）—— 只算当前句的话第二轮
正文就掉了，模型会突然忘掉刚才那份说明。代价是上下文只增不减，所以配总量上限
`ST_CODE_AUTO_CHARS`（24000 字）：**装不下就退回「只列名字」而不是硬塞**
（单个 skill 正文可以到 40000 字，一次塞好几个等于把上下文一次烧光）。

⚠ **结果要排序**（`localeCompare`）。让 system 只跟「命中集合」有关、不跟「用户按什么
顺序提到」有关 —— 否则同一组 skill 会生成两种 system。

⚠ **已经删掉的 skill 要从名单里清出去**，否则它会一直占着 system 的位置。

`read_skill` 这条路**保留**。system 里分两节写：「可用的 skill」（名字 + 描述）和
「已自动加载的 skill」（正文，注明**不用再 read_skill**）。

**② 任务清单（`set_tasks`，第 12 个工具）**

让过程**可见** —— 「像在推进」的感觉很大一部分来自「你能看见它在推进」。

- **整表替换，不是增量**：增量语义表达不了「某一条被删了」，而模型更新清单时本来就容易漏删除。
- 状态只有三个（`ST_CODE_TASK_ST`）：`pending` ○ / `doing` ◐ / `done` ●。
- 上限 `ST_CODE_TASKS_MAX = 24` 条、单条 `ST_CODE_TASK_CHARS = 240` 字。
  **上限是防「把每一步都拆成一条」**，不是怕它写不下。
- 存在**会话**上（`s.tasks`），跟着 `stCodeSessions` 一起持久化 —— 刷新后还在，切会话跟着切。

⚠ **脏数据要兜住**：空 `text` 的条目直接丢（模型偶尔塞一条占位的）、未知 `status` 归
`pending`、裸字符串也当 `{text}` 收。**整表为空才报错**。

⚠ **清单默认展开**，判据写成 `stCode.open.tasks !== false`（不是真值判断）——
`open` 里还没这个键时要当**展开**，它是「正在进行中」的东西，藏起来就没意义。

⚠ **刷新清单只能换那一块**（`stCodeTasksRefresh` 只改 `#st-code-tasks` 的 innerHTML），
**绝不能 `stCodeRepaint()`** —— 模型跑工具的时候用户可能正在输入框里打字，一重建字就没了。

**③ 项目记忆（`remember`，第 13 个工具 —— `fetch_url` / `set_tasks` / `remember` 这一组的第 3 个）**

把用户反复强调的偏好存下来，每次注入 system，省得每轮重复。
存 `localStorage['stCodeMemo']`，**纯文本、一行一条**（不是数组），上限 4000 字。

⚠ **行数是现数出来的**（`stCodeMemoCount`），没有第二个「条数」字段 ——
多一个字段就多一处能对不上的地方。

⚠ **注入位置紧跟「## 怎么做」之后**，标题里明写「**优先于上面的通用做法**」——
不这么写它就会被当成又一条泛泛的建议，模型照样按默认习惯来。

⚠ **满了要拒绝，不能静默截断**。截断会让「我以为记住了」变成「其实只记了一半」，比没记更坏。
同一句重复提交时**当成功**（模型很容易说两遍），不报错。

⚠ **输入时只存不重画**（`stCodeMemoSet`）：`oninput` 直接写状态与 localStorage 并更新计数，
**不 `stRerender()`** —— 重画会把 textarea 换掉，光标当场丢。同理 `stCodeMemoRefresh`
在元素**正被聚焦**时不写 `value`（模型追加记忆时用户可能正写着）。

### 三之补二 · 让 agent 能读改「正则 / 酒馆助手 / MVU / 状态栏」

用户问：**「可以让 agent 能够读取改写正则，酒馆助手和 mvu 状态栏吗？」**

**先说结论：这不是四样平行的东西，只有两个真容器。**

| 用户说的 | 实际住在哪 |
|---|---|
| 状态栏 | 「状态栏界面」那条**正则**的 `replaceString` |
| MVU 变量结构 | 写着 `registerMvuSchema` 的那条**酒馆助手脚本**的 `content` |
| 正则 | `card.regex[]` |
| 酒馆助手 | `card.thScripts[]`（文件夹里的也算） |

⚠ **`card.statusBar` / `card.mvu` 只是编辑器的工作副本**，靠 `stSbSync` / `stMvuSync`
写回去。所以对**别人的卡**来说，读这两个字段读到的是个**假象** —— 这个认识决定了后面
所有设计。

**为什么分两套形状**

- **状态栏 / MVU 是「一份」** → 整份文本替换（`read_doc` / `write_doc`）。而且它们各有一条
  **现成的往返通道**，进去出来都是模型最擅长的文本：
  状态栏是 HTML（`stSbDocHtml` ↔ `stSbParseDoc`），MVU 是 Zod 源码
  （`stMvuZodCode` ↔ `stMvuParseZod`）。
  **不给它那棵树** —— 让模型拼 JSON 树既啰嗦又容易把结构写坏。
- **正则 / 脚本是「一列」** → 按条目改（`read_regex` / `write_regex` / `read_th` / `write_th`），
  抄世界书那套（清单 → 读一条 → 增 / 改 / 删）。**整列替换会静默丢东西**：
  模型看不到的那几条会被它一起写没，而且没有报错。

⚠ **这一块的核心风险（`stCodeEntryGuard`）**：**状态栏就住在那条正则里，MVU 的 Zod 就住在
那个脚本里。** 模型把它们当普通条目删掉 / 改掉，等于把状态栏、MVU 整个抹了 ——
而且**它自己不会知道**（没有任何报错，卡看起来还是好的）。

```
stCodeEntryGuard(kind, item)
  regex: stMvuRegexKind(item) 命中 →
           sbShow               → 拒绝（「这条就是状态栏本身」，指路 write_doc）
           hide/wait/done/sbHide → 拒绝（「MVU 装的」，指路 MVU 页）
  th   : content 含 MagVarUpdate     → 拒绝（「MVU 的核心」）
         content 含 registerMvuSchema → 拒绝（「MVU 的变量结构」，指路 write_doc）
```

⚠ **唯一的例外是「只改开关」**（`stCodeOnlyToggle`）：关掉一条 MVU 正则是正当需求
（不想让 AI 看到变量更新），而且它不会跟生成器打架 —— 生成器压根不管 `disabled` / `enabled`。

⚠ **`stCodeOnlyToggle` 必须先要求 `mode === 'update'`。** 只看「参数里有没有多余字段」
是不够的：`{mode:'delete', id:'状态栏界面'}` 的参数集合**恰好也在白名单里** ——
于是「删掉状态栏」会被放行。这不是理论问题，套件 E6 当场抓到过。

⚠ **`write_doc` 的 MVU 分支强制要求文本里有 `registerMvuSchema`。** 作者常写
`const Base = z.object({…})` 再 `Base.extend({…})`，不指名的话很可能改到基底上去 ——
那是**静默销毁原作者的变量定义**。

⚠ **`stMvuParseZod` 的标识符要同时认 ASCII 和 CJK**（`ST_MVU_IDENT`）。中文社区的卡里
`const 角色 = z.object({…})` / `registerMvuSchema(角色)` 这种写法很常见；只写
`[A-Za-z_$]` 的话这类卡会**整个读不回来**，表现是「编辑器说认不出这张卡的 Zod」，
而用户完全不知道为什么，只会觉得「我这张卡明明是好的」。
⚠ 把 `id` 插进 `RegExp` 之前要转义（`$` 在外面是行尾锚）。

⚠ **`read_card` 对那四样要指路，不能说「卡里没有这个字段」。** 它们是卡里**真实存在**的
字段，`stCodeGetPath` 查得到 —— 所以指路必须放在**解析之前**，否则那个分支根本走不到，
模型拿到的是一坨内部表示的 JSON。**报错信息说错话比不报错更坏：它会让人放弃**
（模型会得出「这张卡没有正则」的结论，然后压根不去动，而卡里明明有一堆）。
指路表是 `ST_CODE_PATH_HINT`。

⚠ **大值给「形状摘要」而不是硬截断**（`stCodeBrief`，`ST_CODE_BRIEF_CHARS = 3000`）。
硬截断最坏的地方不是「少看到东西」，是模型看到的是一段**看起来完整**的 JSON ——
它会当成全部，然后基于半截数据做决定。摘要至少让它知道自己没看到全部，也知道该去读哪一块。

⚠ **回收站里装的是 `{kind, item}` 包装而不是裸条目**（`kind` ∈ `book` / `regex` / `th`）。
正则和脚本的删除也走这里，`stCodeUndoDelete` 必须按 `kind` 分流才知道放回哪个数组
（否则撤回一条正则会把它塞进世界书）。早期只存裸条目的草稿兼容（认成 `book`）。

⚠ **`stCodeFillRegex` / `stCodeFillTh` 同样「空值不覆盖」，但有两个例外**：
`replaceString` 和脚本 `content` **允许是空串** —— 「匹配到就删掉」是正当写法
（MVU 的「对AI隐藏变量更新」那条就是空替换）。

**system 里要补的东西**（`stCodeSystem`）

- 「这张卡现在长什么样」里**必须报个数**：正则几条、脚本几个、状态栏有没有、MVU 装没装。
  不报的话模型不知道卡里有没有，要么干脆不碰，要么凭空去 `write_doc` 一个 ——
  **把已有的覆盖掉**。
- 单开一节「卡里那几样「不是普通字段」的东西住在哪」：落点 + 该用哪个工具 + 哪些会被拒。
- 「限制」里明说**这四样不在字段白名单里**，否则模型会用 `write_text` 硬写 `statusBar`
  之类的路径，撞上白名单被拒之后还得再猜一轮。

### 三之补三 · 读写预算、工具型 skill、沙盒与权限

**① 读和写**绝不能**共用预算**

⚠ 这是整个工具集里唯一一条**会静默毁卡**的路径，2026-09-19 才堵上。

- **起因**：`read_doc` 读到的是截断版（尾巴上贴一句「…（结果太长，已截断）」），
  模型照着它 `write_doc` 回去 —— `stSbParseDoc` 用 `DOMParser`，对**残缺 HTML 极其宽容**，
  照样解析成功 → **尾部块全没了，全程零报错**。而且截断是**永久**的（进 `sess.msgs` 的就是截断后的文本）。
- **两档预算**：`stCodeToolCap(name)` —— 读整份文档的工具（`ST_CODE_READ_TOOLS`）给
  `ST_CODE_READ_CHARS = 32000`，其余给 `ST_CODE_TOOL_CHARS = 12000`。
- **截断标记是一道闸门**：标记抽成常量 `ST_CODE_CUT_MARK`，`stCodeCutGuard(text)` 在
  `write_text` / `write_doc` 里**先于** `stCode.autoApply` 判断执行 ——
  **「真的改卡」开关关着的时候也必须拦**，否则模型会收到一条「只演示」的成功回执，
  以为自己写成了。
- **`read_doc` 带 `from`**：从指定偏移接着读，读到尾会说明。提示语留在代码围栏**外面**，
  免得被一起复制进正文。`ST_CODE_DOC_CHUNK = ST_CODE_READ_CHARS - 600` 给提示留位置。
- ⚠ **只读工具不占改卡次数**：`ST_CODE_READ_TOOLS` 里的不涨 `used`，
  另配 `ST_CODE_READ_STEPS_MAX = 40` 兜住「一直读转圈」；轮次上限 `th.steps + ST_CODE_READ_STEPS_MAX`。
- ⚠ **清单拼错名字不报错，只是静默退回老行为**（那条工具又开始吃步数）。
  所以套件里用的是**推导式**断言，不是写死名单：凡名字匹配 `/^(read_|list_)/` 的工具
  必须在只读清单里（以后加读工具忘登记会被抓到）；只读清单里不许出现
  `write_` / `add_` / `update_` / `delete_`。

**② 两种 skill 并存，不是替换**

- `kind:'knowledge'`（正文注入 system，照旧）/ `kind:'tool'`（注册成模型手里的工具）。
  **知识型（字段映射表 / 格式规范 / 坑列表）没法变成函数**，强行工具化是降级。
  导入时自动判：`.js` 或带 manifest → 工具；`.md` → 知识。
- 工具型 = `/*!MANIFEST {JSON Schema}!*/` 头注释 + `run(args)`。
  **manifest 直接变成模型看到的 `tools[]`** —— 一份文件既是可执行体又是自己的说明书。
- ⚠ **工具名必须 `^[A-Za-z0-9_-]{1,64}$`**（两套协议都要求），**撞内置名也要拒**。
  一个叫「我的技能 v2.0」的 skill 会让**整个请求**挂掉，报错还跟 skill 毫无关系。
- ⚠ **`stCodeSkillFromText` 是三态，不是两态**：skill 对象 / `{err}`（看得出是 skill 但装不了）/
  `null`（不是 skill）。**凡是「解析失败」和「这不是那种东西」后果不同的地方，
  都不能共用一个 null** —— 两态会把「manifest 写错了」静默吞掉，用户只能回去猜。
  `stCodeImportFiles` 收 `errs` 一路带到面板上。
- **每个界面都要区分两种**：system 里分开列、`list_skills` 标 `[工具]` / `[知识]`、
  `read_skill` 遇到工具型**指回工具名**、自动注入池**排除工具型**、面板上挂 🧰 徽章且不给触发词输入框。
  不分的话模型会把「读手册」和「调工具」搞混。

**③ 沙盒 = 不透明源 iframe + 文档内 CSP，不是 Worker**

- `sandbox="allow-scripts"`（**没有 `allow-same-origin`** → 不透明源）的 iframe，
  `srcdoc` 里再塞 `<meta http-equiv="Content-Security-Policy"
  content="default-src 'none'; script-src 'unsafe-inline'">`。
- ⚠ **Worker 是「并发」边界不是「安全」边界**：它有 `fetch` / `XMLHttpRequest` /
  `importScripts` / `IndexedDB` / `WebSocket`，`blob:` worker 还**继承页面源**。
  原型用 `new Worker(blobUrl)` 当沙盒是错的。
  **真正的边界是 RPC 暴露了哪些方法** —— skill 改卡本来就得 postMessage 回父页面。
- **实测四条（Chrome，2026-09，别再重新推一遍）**：
  1. 沙盒文档里 `fetch` → 被 CSP 挡（TypeError）✓
  2. `new Worker(blob:)` → **也被挡**（`worker-src` 回退到 `default-src 'none'`）
  3. 加 `worker-src blob:` → worker 起得来，但**它自己的 `fetch` 还是被挡**（继承 CSP）
  4. 沙盒里 `while(true)` → **不冻父页面**：不透明源 = 跨源 → Chrome 把它放**另一个进程**，
     父页面 `setInterval` 照跳（实测 59→161），沙盒里 5e8 次循环跑了 548 ms
- ⚠ **第 4 条是 `ST_CODE_SANDBOX_MS = 5000` 能真正生效的原因** —— 靠的是**进程隔离**，
  不是事件循环。所以它是**硬闸门**，不是「尽力而为」。`stCodeSkillRun` **一定** resolve、
  **一定**在 `finish()` 里摘掉 iframe（超时 / 出错 / 正常三条路都走它）。
- ⚠ **写 `srcdoc` 前转义 `</script`**：`.replace(/<\/script/gi, '<\\/script')`。
- ⚠ **探针本身也是代码，也会错**：第一版探针给出**假的「父页面冻住」**读数 ——
  探针页自己在 `target="_blank"` 的锚点里引用了一个**已被删掉的变量**，整段脚本压根没跑。
  用 `<script type="text/plain">` 重写才拿到真数据。**做测量前先确认测量工具是活的。**

**④ skill 落盘在 IndexedDB**

- 为什么必须搬：工具型 skill 带 **JS 源码**，一份连正文上百 KB；localStorage 是**同步**的，
  写 800 KB 会卡住主线程；而且 5 MB 上限十个就顶到。
  `ST_CODE_IDB_NAME = 'saki-code'` / `ST_CODE_IDB_STORE = 'kv'` / `ST_CODE_IDB_MS = 3000`（开库超时）。
- **铁律一：只写一处。** 后端记在 `stCodeSkillBackend`，写 IDB 成功就**清掉** localStorage 老键
  （`stCodeSkillClearLs`）。两边都写迟早分叉，而分叉之后**没人知道该信哪边**。
- **铁律二：降级要打脏标记**（`ST_CODE_SKILL_LS_DIRTY = 'stCodeSkillsLsDirty'`）。
  不打的话后果是：IDB 临时抽风 → 这次写进 localStorage → 下次打开 IDB 又好了 →
  读到的是**旧的那份**，新的悄无声息地没了。
- **铁律三：迁移顺序不能反。** 先写成功**再**删老键。反过来，写失败就等于把用户的 skill 全删了。
- ⚠ **「启动读」和「导入写」要排成一条串行链**（`stCodeSkillChain`），
  而且写之前**先拍 payload 快照** —— 不排的话，读回来的旧列表会盖掉刚导入的，
  **两边都不报错**。链上任何一环失败都不能让后面的卡住。
- ⚠ **`stCodeLoad()` 不再读 skill**：内存里的 `stCode.skills` 是**同步真相**，存储层是异步的，
  读进 `stCodeLoad` 会跟后面的写抢。改由 `openStEditor()` 和 `stCodeSend()` 各自 `await
  stCodeSkillsLoad()`（它是**记忆化的一次性**加载，重复调不重复读盘）。
- **写失败给的是人话**（`stCodeSkillFailText()`），不是异常 —— 撞配额上限时用户得知道
  「是存不下了」，而不是「点了一下没反应」。

**⑤ 权限：两层能力 + 三个「不给」**

沙盒把 skill 关得太死 —— 它连自己刚被调起来要干什么都读不到。所以给一条**反向通道**：
skill 里 `await host.call('read_card', {})`，父页面执行完回信。但「能给」≠「该给」。

| 能力 | 能调的工具 | 危险 |
|---|---|---|
| `card.read` | `read_card` / `read_doc` / `read_regex` / `read_th` / `list_world_entries` / `read_world_entry` | 低 —— 读到的东西**出不去**（CSP 断网），只能回给模型 |
| `card.write` | `write_text` / `write_list` / 世界书增删改 / `write_doc` / `write_regex` / `write_th` | **高 —— 真的会改用户的卡** |

- ⚠ **`fetch_url` 永远不给**（任何层都没有）。它是唯一出网通道，给了就等于把 CSP 断网的
  意义抹掉一半 —— skill 能把刚读到的卡（私密设定）**拼进 URL 发到公网**。
  地址闸门挡的是「访问内网」，挡不住「把内容发出去」。**整套设计里最硬的一条。**
- ⚠ **`set_tasks` / `remember` 不给** —— 会话级状态，skill 用不上，给了只会污染。
- ⚠ **`read_skill` / `list_skills` 不给** —— 它们读的是用户的 **skill 库**不是卡，
  所以不属于 `card.read`。**这是设计判断，不是漏登记。**
- **闸门在三层**：导入时（`stCodeManifestOf`，声明了不认识的能力 → 拒收）；
  运行时（`onHost` 按声明的 `perm` 放行）；**底下走同一个 `stCodeToolRun`** ——
  另写一条写路径 = 把写白名单 / 回收站 / 「真的改卡」开关**全绕过去**。
- ⚠ **不在沙盒里做权限判断** —— 沙盒里的判断等于没判断（skill 能改自己的代码）。
- ⚠ **权限在导入那一刻定死**，运行时不会临时给（否则「申请」就成了摆设）。
  用户点「装」那一下就是明确同意，所以面板上要**一直**标 `✏️ 能改卡`（警示色）。
- ⚠ **一次 run 最多 20 次宿主调用**（`ST_CODE_SANDBOX_RPC_MAX`）。不给上限的话
  `while (1) { await host.call(...) }` 能在这 5 秒里把卡读上千遍 ——
  **沙盒超时掐得掉沙盒，掐不掉父页面正在跑的那一串。**
- ⚠ 单次另有 `ST_CODE_SANDBOX_RPC_MS = 4000`（比总超时短），让 skill 有机会 catch 到
  「这次调用失败了」然后自己决定怎么办，而不是整段一起被掐。
- ⚠ **`host` 的 `onmessage` 必须先认 `__hostRet` 再认 `__call`** —— 反了的话回信被当成
  一次新调用然后什么都不发生，**不报错，只是每个 `host.call` 都超时**。
- ⚠ 父页面收 RPC **也要验 `e.source === frame.contentWindow`** —— 页面上还有状态栏预览
  那个 iframe，不验的话它能冒充 skill 来调工具。
- **`stCodeSkillPermsOf` 求交集**（manifest 声明的 ∩ 宿主真有的），不直接信 manifest ——
  老草稿里可能存着早就下线的能力名，直接信就等于「skill 自己给自己发权限」。
- ⚠ **推导式断言里的「例外」必须显式写出来**（套件里是 `NOT_CARD` 常量 + 单独一条
  「确实不在表里」）。不写的话，下次真漏登记时你会以为是「又一个例外」而顺手加进排除名单。

**⑥ 少给参数不许当空值写**

- ⚠ **`write_text` 的 `value` 是 `undefined` / `null` 时拒收**。原来写成
  `String(a.value == null ? '' : a.value)` —— 少写一个参数名、或者把 `text` 当成参数名
  （`write_doc` 用的就是 `text`），**那个字段当场变成空串**，而返回的是
  「已写入 description（现在 0 字）」这种**成功回执**。
- ⚠ **空串 `""` 仍然是合法值** —— 那是「故意清空」，和「忘了给」必须分开。
- 同一族（空值不覆盖）在 `write_list` 的 `items` 和 `update` 的「没传的字段不动」上都防住了，
  只有 `write_text` 漏了。**加写工具时照这一条抄。**

**⑦ 渲染 skill 返回值：现在安全，但是靠约定**

`stCodeMsgHtml` / `stCodeSkillPopHtml` / `stCodeHighlight` **三条路径全都先 `escapeHtml`**。
⚠ 但这是一条**约定不是闸门** —— 以后新加渲染路径要自己记得，别直接 `innerHTML` 塞远程内容。

**⑧ skill 改过卡要一路带 `touched` 回来**

- Agent 循环只看 `r.touched` 才 `stCodePaintJson()`（重画右侧那份卡 JSON）。
  skill 走「沙盒 → RPC → `stCodeToolRun`」**两层** —— 不逐层带上来，外层拿到的是 `''`，
  结果就是「skill 说改好了、卡里**真的**改了、用户右边看到的是**没更新的卡**」，
  而**所有断言都是绿的**。
- 修法：`stCodeSkillRun` 在 `onHost` 里记 `touchedAny`，`finish()` 一起 resolve 出来，
  `stCodeToolRun` 的 dyn 分支原样返回。
- ⚠ 通则：**中间隔了两层的返回值，每一层都要显式往上带**。少带一个字段不报错，
  只是下游少做一件事 —— 这类 bug 的共性是「功能是对的，只是某个副作用没触发」。

**⑨ 失败信息不许无条件说「卡没有动」**

- skill 完全可能**先写成功、再自己抛异常**（`host.call('write_text', …).then(() => { throw … })`）
  —— 这时候卡里**留着它的改动**。说成「卡没有动」是**最坏的那种假话**：
  用户以为没动就不会去检查，改动就那么留在卡里。
- 修法：按 `touched` 分流 —— 改过说「⚠ 它**已经改过卡了**，卡里留着它的改动」，
  没改才说「卡没有动」。
- ⚠ 通则：**凡是「失败 ⇒ 什么都没发生」的推理，都要先问一句「失败之前它做过什么」。**

**⑩ 能不能碰卡，三处口径要一致**

`stCodeSystem` / `list_skills` / `read_skill` 都要说清这个工具型 skill 能碰卡到什么程度
（「它自己也能读改卡：card.read」/「纯算它自己的东西，碰不到卡」）。
⚠ 模型据此决定「要不要自己先读一遍」和「先调谁后调谁」（一个能改卡的工具，调用顺序就有意义了）。
说成「读不到卡」的后果是**放弃** —— 模型会得出「反正它读不到」，然后绕远路。
⚠ 加新的展示面时，别只抄一半口径。

**⑪ 「算不算只读」要用 `stCodeIsReadTool()`，不能只看静态名单**

`ST_CODE_READ_TOOLS` 里**只有内置工具**，而 system 承诺的是「`read_*` 这类只读工具不算改卡次数」。
一个**没申请 `card.write` 的工具型 skill**（掷骰子、算个数）不是 `read_*`，
用静态名单就会**照吃一次改卡步数** —— 越纯算的 skill 越吃亏，而用户看到的是那句承诺。

`stCodeIsReadTool(name)` = 静态名单 **或**「没申请 `card.write` 的工具型 skill」。
⚠ **故意保守**：申请了 `card.write` 的 skill 一律按改卡算，哪怕这次调用只读了一行。
猜错方向的代价不对称 —— 少算一步只是少改一次卡；多算一步会让用户以为「还能改」却发现改不动。

⚠ 通则：**凡是提示词里承诺过的行为，判据都要跟那句话对得上。** 这类不一致**断言抓不到**，
因为断言只覆盖「我想到的那条路径」，而「system 里写的那句话」从来没被当成被测对象。

**⑫ 权限在导入那一刻定死 → 导入时就必须点名告知**

`card.write` 的 skill 装进来之后，能在**没被要求动卡的时候**动这张卡。这是设计本意
（用户自己选的），但**只给一个 `✏️ 能改卡` 徽章不算告知** —— 徽章在另一个面板里，
得专门去看，而用户点完「装」就走了。

`stCodeSkillsApply` 里算出 `writers`，在导入反馈里**列出是哪几个** + 给「移除」这条退路
（移除立即生效），顶部闪的那句也带上「⚠ 有 N 个能改卡」。
⚠ 顺带：`.st-code-skill-msg` 必须 `white-space: pre-wrap` —— 否则提示里的 `\n`
被折成空格、挤成一坨，反而更难看见。

⚠ 通则：**「用户同意了」和「用户被告知了」是两件事。** 授权发生在哪一刻，
告知就必须发生在哪一刻 —— 事后的徽章、别处的开关都不算。

**⑬ 进度上报：两道闸在父页面，`host.progress` 单向**

沙盒 skill 报进度走 `host.progress` —— 它**单向**（返回 `undefined`），而且**不吃**那 20 次
`ST_CODE_SANDBOX_RPC_MAX` 预算（吃预算的是 `host.call`）。

三道闸**全设在父页面**（沙盒不可信，不能指望它自己节流）：
- `ST_CODE_PROG_MS = 120` —— 最小间隔，同 tick 连发会被节流丢掉；
- `ST_CODE_PROG_MAX = 200` —— 单次 run 最多留 200 条；
- 单条 `ST_CODE_PROG_CHARS = 160` —— 超长那条自己会被裁。

⚠ **闸只丢不清**：撤掉进度只能靠 `finish()` 里那一次 `stCodeProgressClear(id)`，而且**只清自己那条**
（清全部会误伤别的 run）。

⚠ 权限表 `ST_CODE_PERM_TOOLS` 里，`progress` **映射到空数组但必须留在键里** —— 删掉这个键，
`progress` 就变成「未声明的权限」，判断会走另一条分支。
⚠ 能力表键与 `PERM` **必须是同一份**（两处各写一份一定会漂）；⚠ **判断只在父页面做**；
⚠ **权限在导入那一刻定死**（见 ⑫）。

## 四、运行时判定（所有「原样」的准绳）

- **酒馆助手把消息楼层里的代码渲染成界面的条件只有两条**：
  ① 代码在四反引号/三反引号围栏里；② 代码里**同时有 `<body>` 和 `</body>`**。
  满足之后它被当作**一个独立网页塞进 iframe** —— **`<style>` / `<script>` / 外链资源全都可用**。
  `vw` / `vh` 以 iframe 为准（只有 `min-height:*vh` 被官方特判为以视口为准）。
  ⚠ 项目里原先写着「沙盒 iframe 会剥掉 head 样式，所以只能内联」——**这条是错的，已推翻**。
- **「原样解析」= 运行时怎么解析，编辑器就怎么解析**（`stSbFences` / `stSbRuntimeInfo`）。
  不合格的原稿（有围栏没 `<body>` / 连围栏都没有）**照样解析**，报告里 🚫 说明
  「玩家那边看不到，只会看到源码」，写回时补成合格包装。围栏**外**的原文存
  `statusBar.pre` / `post`，逐字节拼回去。
- **base64 结构注释放在 `<body>` 里面**（`stSbMarkOf`）：注释不是元素，不影响那两条判定、
  也不多出块。放外面会多出一个「合格块」。
- **class 必须保原样**（`clsMap` 按 7 层 + 外壳 `shellCls`）：既然是真 iframe，
  「`<style>.hp-k{…}</style>` + `<span class="hp-k">`」就是正当写法，class 一丢
  那段 CSS 整个落空且**不报错**。
- ⚠ **内联永远赢过 class**。生成器照主题写一串内联，作者的 CSS 就白写了。所以按
  **属性**粒度抑制（`clsOwn[层]` = 原稿那层内联里真正写过哪些属性名；
  `stSbLook` 只放行这份名单里的声明）。**按「层」粒度是错的** —— 手写稿常是
  「字号自己写、颜色靠 class」，整层放过就等于颜色被主题色盖掉。
  结构性声明（flex / `position` / `overflow` / `calc()` 宽度）不走这个筛子。
- **`white-space:pre-wrap` 要收敛**（`stSbPreWrap`）：带 class 的层只在**文字里确实有换行**
  时才写；原稿没换行、CSS 也没提，它的默认是 `normal`，凭空插一句就是改样子。
  不带 class 的层照旧无条件写（生成物一直是这么写的，改了会动到字节）。
- ⚠ **`white-space` 不许进文字/标题块的 `extra`**：`<br>` 被换成了 `\n`，靠的就是生成器
  那句 `pre-wrap`；让原稿的 `normal` 盖上去，换行当场就没了。
- **`shellExtra` / `shellOff`**：外壳上 6 套主题表达不了的声明（阴影 / 渐变 / 毛玻璃）。
  `shellExtra` 只在**解析别人的状态栏**时才有值，追加在主题样式**之后**（同属性后者胜 →
  它盖住主题，主题仍然管块内部的默认色）。生成器**无条件**写 11 条外壳属性
  （`ST_SB_SHELL_PROPS`），原稿没写哪条就关掉哪条。装满 11 条 = 外壳退化成裸 `div`。
- **解析别人的状态栏**（`stSbParseDoc`）的铁律：**拆不动就原样留成「高级 HTML」块**，
  绝不静默丢内容。三条「故意不拆」：句子里带宏（留文字块）、带 `style` 的行内标签
  （留高级块）、`<table>`（「光壳」规则会把它拆散，所以只认 `div`/`span`
  且白名单不含 `width`/`height`）。
- **「尽可能按原样」= 拿生成器产物当基准做差集**（`stSbOwnMaps` → `stSbExtraOf` →
  `stSbKeepStyle`）：`原稿 style − 生成器给同一个块写出来的 style = 必须保住的声明`。
  **这样解析器和生成器永远共用一套判据**，改生成器不用同步维护白名单。
  按元素分层存：`extra`（最外层）/ `extraInner`（「底」）/ `extraFill`（「亮」）/
  `wrapExtra`（分组里的列容器）；bar 的轨道底色单独走 `track` 字段。
  **生成器已经写过**的声明不记 —— 记了就是同属性写两遍，用户之后改字号/颜色就改不动了。
- **颜色不是一个**：手写状态栏里「显示名」「没点亮那排圆点」「右边那个数值」是三处
  独立颜色 → `labelColor` / `emptyColor` / `valueColor`。`var` 不要 `valueColor`
  （它的 `color` 本来就是数值色）。
- ⚠ **回写闸门**：`mvuOwn` / `sbOwn` 只是第一层。`stSbSync()` 还要求
  `stSbDetect().state === 'mine'`（产物里带 `<!--MVU_STATUS_BAR:…-->`），
  要强写只有 `stSbSync(true)`。**绝不静默覆盖别人手写的内容**。
- **解析后立刻覆盖卡里那条正则**。不覆盖的话 `sbOwn` 是 true 而 `state` 还是 `foreign`，
  之后每次编辑都会静默不写回 —— 比覆盖更糟。原稿放内存（`stSbParseBackup`，
  **不进草稿**），会话内可还原。
- **画布 ≠ 玩家看到的**。画布用的是编辑器的 CSS。画布下面另挂一个真机预览 iframe：
  同一套包装、`sandbox` **故意不给 `allow-same-origin`**、宏换示例值、240ms 防抖，
  外加一条「运行时体检」说明玩家那边会不会显示。

## 五、自由摆放（`offX` / `offY`）与尺寸（`w` / `h`）

- **自由摆放写进产物时必须是相对定位**：`position:relative;left:Xpx;top:Ypx`。
  **绝对定位会脱流** —— 运行时那边后面的块整个塌上来，那不是「把这块挪一点」而是把整张排版砸了。
- ⚠ **两个偏移都是 0 时一条声明都不写**（`stSbOffCss` 返回空串），单条为 0 时那条也不写。
  这是 `sb-keep-compare.js` 逐像素对照能成立的前提 —— 破了它，对照立刻变红。
- **解析时 `left` / `top` 只认 `position` 恰好是 `relative` 且单位是 `px` 的**：
  `static` 上的 `left` 是无效的，读成偏移等于凭空补一句 `position:relative` 把无效变有效；
  `absolute` / `fixed` 是脱流写法，是人家自己的排版手法。两种都原样进 `extra`。
  读回来的偏移要排在 `stSbOwnMaps` 差集**之前**，否则同一句会既进 `offX` 又进 `extra`。
- ⚠ **「纯定位壳」要拆**（`stSbOffOnlyWrapper`）：`<div style="position:relative;left:8px">`
  裹着别的东西时，不拆就会被兜底成高级块，下一轮生成时块自己又写一次 → 壳 + 块两层 →
  **再解析偏移翻倍**（8 → 16），越存越歪。⚠ 它必须排在 `stSbParseEl` 的**兜底之前、
  所有结构识别之后** —— 放最前面会压过结构识别（裹着轨道的定位壳本该认成进度条）。
- **显式尺寸（`w` / `h`）**：0 = 自适应、**一条声明都不写**（`stSbSizeCss`），单条为 0 时
  只写另一条。⚠ **`space` 块的高不走 `h`，走它本来就有的 `height` 字段** —— 差异收在
  `stSbSizeKeys(b)` 一处，别在别处再判一遍 `type === 'space'`。
- **尺寸只认 `px`**：`%` / `calc()` / `em` 原样进 `extra` 带走 —— 换算成 px 写回去等于
  把人家的响应式写法改成死的。
- **尺寸在画布上写「块自己」，偏移写「命中框」**。偏移挂 `.st-sb-hit` 是因为命中框就是
  拖动时跟手挪的那个元素；尺寸**不能照抄** —— 命中框是自动宽度，`width` 写它身上块不会变。
  所以尺寸两边都写块自己，命中框另补 `width:fit-content` 贴轮廓。`stSbBlockHtml` 的
  `noOff` 参数**管不到尺寸**。
- ⚠ **读回尺寸前先跟「生成器基线」比一遍**（`stSbSizeBaseline`：把 `w`/`h` 清 0 生成一遍，
  看生成器本来会写什么）。不比的后果：分割线自己写着 `height:1px`（**生成器写的**），
  会被读成「用户设的」→ 下一轮多写一条 + 差集把原来那条抄进 `extra` → 一条变两条，
  逐字节对照当场红。`stSbSizeNum` 下限是 **1 不是 8**（手写稿真有 `height:1px`），
  8 只当**拖动**地板。
- **拖把手按「内容盒」算**（`stSbMeasureEl` = 边框盒 − padding − border），因为写出去的
  `width` 就是内容盒宽度；用 `getBoundingClientRect()` 当起点，块有 padding 时第一次拖会跳。
  **西 / 北边拖动位置跟着走**，且要**先夹紧 w/h 再反推位置** —— 反过来拖到下限以下时
  块会一边缩一边继续跑。落库只写**这次真正动过的轴**。
- **八向把手只在选中的块上渲染**（每块八个 × 6 块 = 48 个小方块，指针不知道抓哪个）。
  有把手时徽章要往右让一格（`.st-sb-hit.st-sb-hh`）。`Alt+方向键` 改尺寸（1px / Shift 10px），
  与 `方向键` 挪位置分工；没设过尺寸时先量当前大小当起点，不然 `0 → 1` 会缩成 1px 宽。
- **自由摆放与结构排序互斥**（`stEditor.sbFree`，默认开，跟着草稿存）：
  开着走指针事件挪位置（`draggable=false`），关掉才是 HTML5 DnD 换顺序。
  `stSbDragStart` 在自由摆放开着时主动 `preventDefault()` 并返回。
  **DnD 做不了挪位置** —— `drag` 只给屏幕坐标、`drop` 之后失联，拿不到连续位移。

### 六之一 · 为什么「绿」不算验证

### 六之二 · 一条只活在注释里的语句

那两条红都是「收尾后进度状态是干净的」那一族。根因在 `stCodeSkillRun` 的 `finish()`：

```js
if (frame && frame.parentNode) frame.parentNode.removeChild(frame);
// ⚠ 收尾要把进度那句话**撤掉** —— 不收的话它会挂在那儿，
//   而下一条消息已经进来了，看着像「还在跑第 7 条」
resolve({ ok: ok, ... });        // ← 注释说的那件事，这里没有代码
```

**三个静态检查从三个方向同时看不见它**：

| 检查 | 为什么看不见 |
|---|---|
| `SYNTAX` | 语法完全合法 |
| `UNDECLARED` | `stCodeProgressClear` **声明在**、**别处也在引用** → 符号是健康的 |
| `ESCAPE-GATE` | 不相关 |

**只有行为断言抓得到。** ⚠ 通则：**注释说了什么 ≠ 代码做了什么。**
看到「注释承诺了某件事」的地方，值得专门 `grep` 那句话对应的调用**在不在**。

### 六之三 · 那条语句是「写进去又丢了」，不是「从来没写」

上一轮把这件事记成了「那一行**从来**没写进去」。**这个结论是错的**，第七轮查清了：

`st-code.js` 的 E11 里有一条断言 ——

```js
check('返回之后进度那句话被撤掉了（不留在界面上）', await ev(`String(stCode.prog)`), 'null');
```

它前面刚跑完 `prog_yes` 这个 skill，而 `prog_yes` **一定会报 2 条进度** ⇒
`stCode.prog` 一定被设成对象 ⇒ **没有 `finish()` 里那行 `stCodeProgressClear(id)`，
这条断言不可能通过**。而上一轮那次 `run-all.js` 报的正是 **663 / 0**（一条都没红）
⇒ **那行代码当时在文件里。**

真实经过：**写进去 → 落盘 → 跑绿 → 之后被静默弄丢 → 下一轮发现它不在。**

⚠ 这修正了「批量 Edit 静默漏」的**表现形式**：

| 形态 | 表现 | 事后 `grep` |
|---|---|---|
| (a) | 报成功，**没到磁盘** | 找不到 |
| (b) | 到了磁盘，**又被后续批量改动覆盖掉** | 找不到 |

**两者一模一样**，而且**都会把注释留在原地**（所以文件照样解析、静态检查全绿）。
⇒ 对策不同：形态 (b) 意味着**每过一轮批量改动都要重新 grep 一遍**，不只是写完那一次。

⚠ 更一般的教训：**「某件事从来没发生过」是关于过去的断言，要拿当时的文件快照支撑，不能靠回忆。**
本次没有快照（`/tmp/saki.bak` 是 09-19 19:18 的，早于这个功能），
所以上面这条是**从「断言能不能通过」反推**出来的，不是直接观测 —— 记录时必须标明这一点。

### 六之四 · 两个 runner 结论不一致：先查「是不是同一份文件」

同一份产品、同一套 `st-code.js`：

最直觉的解释是「套件间状态串味 → 断言在全套里假绿」（**比原 bug 更坏**的一类）。
但那是**假设**，要拿实验换。

**实验**：`_probe-falsegreen.js` 把 bug 注回产品，两边各跑一遍：

|---|---|---|---|---|

**`run-all.js` 如实报红，不盖。** 危险假设**证伪**；那个 `663/0` 只能是文件状态（见六之三）。

⚠ 有意思的是探针头部那句推理（「每个套件都是各自 spawn 一个 node 进程，所以串味不成立」）
**本来就写对了** —— 但**推理对不等于事实**，是这次注入实验把它变成事实的。
**「run-all 会不会盖红」这类问题只能量，不能推。**

### 六之五 · 量出来的数正好落在阈值上 → 先量输入，别改 CSS

外部 8 层报一条红：

```
✗ 移动端顶栏按钮触控高度 >= 32px  →  btnH: 31
```

产品这一轮**只加了一行**（`stCodeProgressClear(id);`，19252 行），和按钮毫无关系；
而且早上还是绿的。**单跑三遍视觉层全是 368/368。**

定位靠**量输入**而不是量结果：

| 量的时刻 | 文本行盒 | 按钮高 |
|---|---|---|
| 本地像素字体还在 `loading`（兜底字体） | 13px | **31** |
| 7MB 字体加载完之后 | 17px | **32** |

`17 + 6*2 + 1*2 = 32`，兜底字体的 13px 给出 31 —— 而阈值**正好是 `>= 32`**。
所以这条断言的结论取决于「7MB 字体有没有在 `setViewport` 之后那 400ms 里下完」。
**产品完全正确，CSS 一点问题都没有。**

修法（套件里量之前显式等字体）：

```js
await sleep(500);
// ⚠ 触摸高度这两条断言坐在 1px 边界上：等字体就绪再量
await evaluate(`document.fonts.ready.then(() => true)`);
await sleep(300);
```

⚠ **`getBoundingClientRect().height` 对「带文字的控件」= 行盒 + padding + border**，
所以它继承**每一次字体切换**。断言余量小于字体行高差的，都是掷硬币。

⚠ 判据不能是「我改的」/「以前是绿的」（对**闪烁**断言来说，「早上还绿」什么都不能证明），
只能是**重复实验**：一次红 + 三次绿 = 闪烁，不是回归。

### 六之六 · 一条标签骗人的断言（第七轮顺带修的）

```js
check('而且挡住的是「丢」，不是「失败」（skill 拿到的还是成功）',
  await ev(`String(stCode.prog)`), 'null');
```

**标签承诺的是 `r.ok`，判据测的却是 `stCode.prog`。**

它**不是**假绿 —— 两道节流闸（`ST_CODE_PROG_MS` / `ST_CODE_PROG_MAX`）**只 `return` 不清**
（会清 `prog` 的只有 `stCodeProgressShow` 里「空串 = 主动清」那一支，20349 行），
所以它确实在测 `finish()`；而且它测的是**狂刷 300 条把 prog 刷满之后**这个场景，
和上面那条（普通 2 条进度）**不是重复**，覆盖是有效的。

但它**在骗人**：读标签的人会以为「丢 vs 失败」有对照组，实际那件事由上一行的 `r.ok` 覆盖了。
→ 已改标签为「狂刷被节流之后，进度那句话同样被 finish 撤掉（闸只丢不清）」。

⚠ 通则：**断言的标签是给下一个人看的契约。** 判据改了标签没跟着改 = 下一个人靠它下错结论。

### 六之七 · 反向测试的「名单」，本身就是一条会静默失效的断言（第九轮）

`_reverse11.js` 给 `sb-verify9.js` 做反向测试时加了一道闸门：
**探针点名的断言名，必须在基线里真的存在**。第一次跑就抓到 4 处，两类：

**① `green`（对照组）里放一个不存在的名字 —— 安静得要命。**

「对照组一条都没红」对**不存在的名字**天然成立 ⇒ **对照组被悄悄削弱，探针照样全绿**。
（`red` 里放不存在的名字会红得很吵，所以只查 `red` 是不够的，**两边都要查**。）

**② 抽 ✅ 名字时把名字自己的前导空格吃掉了。**

`check()` 打的是 `  ✅ ` + 名字，而**名字自己可能带前导空格**：

```js
check('  是摊平不是砍掉 —— 5 块一块没少', r.n, 5);
// 打出：  ✅   是摊平不是砍掉 —— 5 块一块没少
// 抽名：/^\s*✅\s+(.*)$/  →  `\s+` 把名字自己的两个空格一起吃了
// 名单里手抄的是带空格的原文 ⇒ indexOf 永远 -1
```

⇒ **两边都 `trim` 才是同一个名字。** 顺手把比对收成一个 `hit(list, x)`，
别在每个调用点手写 `indexOf(x)`。

**③ 名单对不上就「直接退出」，别浪费后面 4 次整跑**（每次约 40 s）。

⚠ 通则：**反向测试的 `red` / `green` 名单是手抄的，手抄的东西会漂。**
漂了之后它**不会报错，只会少验** —— 所以必须自己查一遍「这些名字还在不在」。
这跟「写死清单的断言每次加东西都来收账」是一体两面：
写死的清单**会红**（烦人但看得见），**手抄的名单不红**（安静但更坏）。

### 六之八 · 失败项的列表符，两套件不一样（第九轮）

| 套件 | 格式 |
|---|---|
| `sb-verify8.js` | `失败项：\n  - 名字\n  - 名字` |
| `sb-verify9.js` | `失败项：\n  · 名字\n  · 名字` |

照抄上一套的 `failsOf`（只剥 `-`）会**一条都匹配不上** —— 而且表现为
「对照组一条都没红 ✅ / 没有预期之外的红 ✅」，**看着像过了**。
⇒ 两个都剥：`.replace(/^\s*[-\u00b7]\s*/, '')`。

⚠ 这跟「汇总行有两种格式」（`N passed, N failed` vs `N 通过 / N 失败`）是**同一类病**：
**格式差异不报错，只安静地少看一半。**
⇒ 跨套件抄解析代码之前，先去**看一眼两边的打印语句**，别假设它们一样。

### 六之九 · 「套件超时」先问「机器当时在忙什么」（第九轮）

`run-all.js` 的单套上限是 **240 s**（`TIMEOUT_MS = 4 * 60 * 1000`）。第九轮整跑时
`sb-verify2.js` 报了 `TIMEOUT`，`— [无]`（连汇总行都没产出）。

**单跑同一套：21 s / 62 通过 / 0 失败。** 干净重跑整跑：**17.9 s**。

同一个窗口里，连**没超时**的 `sb-verify.js` 都从 **21.4 s** 涨到了 **87.9 s**（4 倍）。
⇒ **就是并发争用**：我当时一边整跑一边跑 `_audit-anchors.js` / `_audit-counts.js` /
几个 `node -e`，每个都会起进程（其中几个还会起 Chrome）。

⚠ 所以「套件超时」的第一问是 **「机器当时在忙什么」**，不是「产品是不是坏了」。
⚠ 纪律有两半，别只记一半：
1. **两套 harness 一律串行**（并行会让外部 Chrome 层只跑 1/371 却照样打 ✅）；
2. **整跑期间别并发任何别的进程** —— 否则时间预算被吃掉，慢的那套先撞 240 s 的墙。

⚠ 一个 21 s 的套件撞到 240 s 的墙，说明**不是「跑得接近上限」**（那是另一种 flake，
见技能里那条）。**同一个症状，两种病因** —— 先看数字分布，再下结论。

### 六之十 · 判据依赖「正则切在哪儿」的检查，等于没有检查（第九轮）

外部 `static_check.js` 报 `style 块 #2 大括号配平 → depth:-1`。**那一轮我没碰 CSS** ——
所以第一件事不是去改 CSS，而是**数输入**：

| | 次数 |
|---|---|
| 文件里 `<style` | **23** |
| 文件里 `</style>` | **4** |

多出来的 19 个全在 **JS 字符串**里（状态栏生成器要拼 `<style>` 出去）。
`/<style\b[^>]*>([\s\S]*?)<\/style>/gi` 会把每个 `<style` 配到**下一个** `</style>`
⇒ 所谓的「块 #2 / #3 / #4」是**被切了一半的 JS 片段**（块 #2：8281~9352 行，
两头都在函数中间）。**JS 片段没有理由括号配平。**

⇒ **这个检查的红与绿，取决于那两刀切在哪儿** —— 加几十行无关代码就能让它翻转。
它一直在「通过」，但那不是「没问题」，是**运气**。

修：**先摘掉 `<script>` 再找 `<style>`**，并补一道「提取本身对不对」的闸门
（script 之外 `<style` / `</style>` 数量要相等且等于块数）。
修完 `4 个 style 块` → **`1 个`**，全绿。

⚠ 通则：**「检查红了」和「产品坏了」之间，隔着一次「先数输入」。**
⚠ 更强的通则：**一个判据如果依赖提取器切在哪儿，它的绿和红都不携带信息。**
给任何「从大文件里切块再检查」的脚本，都配一条**「提取出来的东西对不对」**的自检
—— 否则你验的是提取器的手气，不是产品。

### 六之十一 · 改了套件的断言名，要重跑「以它为靶子」的反向测试（第九轮）

反向测试的 `red` / `green` 名单是**手抄靶子套件的断言名**。第九轮我为了修「旧套件前提失效」
改了 `sb-verify8.js` 里两条断言名 —— 而 `_reverse10.js` 正是以它为靶子。

⚠ **这种腐烂不会报错。** `red` 里放不存在的名字会「永远红」（吵），
`green` 里放不存在的名字则「天然成立」（**静**）—— 名单烂了，探针照样打 ✅。

⇒ 改了断言名，**去重跑对着它的反向测试**（这条是「移除一个功能会让反向测试的锚点腐烂」
的弱化版 —— **连改名也会**）。第九轮重跑 `_reverse10.js`：全部达标，
顺手把存在性闸门补进去，**47 条点名断言全在基线里** ⇒ 上一轮的反向测试是**真的健康**。

### 六之十二 · 超时的套件会漏掉自己的临时 profile

`run-all.js` 的 `spawnSync` 超时（240 s）会**杀掉**套件进程 ⇒ 套件 `finally` 里的
`rmSync(profile)` **根本没跑**。实测：那次超时的 `sb-verify2` 留下了一个 12 MB 的
`cdp-sb2-*`；而**干净重跑那次没留**（清理本身是好的）。

⇒ 套件自带的清理**有效**，但**「被外面杀掉」这条路它兜不住** ——
这是 240 s 超时的**附带代价**，不是清理写错了。
⇒ 清残留走 `_verify/_purge-tmp.js --go`，**要用户点头**（默认只数不删，故意的）。

### 六之十三 · 审计工具报 ✅ **不等于**对（第十轮）

`_audit-anchors.js` 的 §3 判据是「表里那个行号**必须是一条注释横幅的开头**」，
另外配一道**软提示**：「是横幅、但正文跟区块名几乎不共享字 ⇒ 可能漂到别的横幅上了」。

第十轮往 CSS 里插了一段新横幅（`复古线框战机：**整页游戏**…`），**正好落在表里
`1890 复古模式覆盖` 那个位置上**。于是：

- 硬判据：1890 那一行确实是 `/*` 开头 ⇒ **✅**；
- 软提示：区块名「复古模式覆盖」跟新横幅正文共享 `复古` **两个字** ⇒ 达到门槛 ⇒ **不响**。

**真相是整段 §3 尾部集体 +27。** 结果是审计工具**报了「两张表全部对得上」**，
而表里 17 行全是错的 —— 比不报还坏（不报至少会让人去看一眼）。

⇒ 教训：**「那一行是个横幅」只是必要条件，不是充分条件。** 往 CSS 里加**内容相似的**
横幅（尤其带「复古」「游戏」「AI」这种高频词）时，软提示基本失效。
⇒ 改完 CSS **别只看审计的 ✅** —— 顺手 `grep` 两三个锚点原文核一下；
⇒ 新横幅的命名**尽量避开**表里已有区块名用过的字（这次要是叫「iframe 小游戏容器」就不会撞）。

### 六之十四 · 断言的名字**不能取决于运行时分支**（第十轮）

`game-verify.js` 里那条「摘掉之后 rAF 停了」原本写成两个分支两个名字：
`…（window 已被回收 ⇒ 停）` / `…（tick 两次读数相同）`。看着更精确，其实是给反向测试挖坑：

- 基线里**永远只出现其中一个**名字（浏览器把 detached window 回收了，走的是前者）；
- 注入之后走的**正好是另一个**分支 ⇒ 探针的 `red` 点了一个**基线里查无此人**的名字。

`_reverse12.js` 的存在性闸门**当场拦下**了（「R1 点名的断言在基线里都在吗 → 找不到」）。

⚠ 真跑起来更糟：`red` 匹配不上时，「预期该红的都红了」会因为**一条都没有**而照样打 ✅ ——
反向测试**静默失效**。

⇒ 判据合成**一个布尔、一个固定名字**；**走的是哪个分支要 `console.log` 打出来**，
不许静默选。（`  ℹ window 已被回收（__GONE__）…` 那一行就是干这个的。）

### 六之十五 · 判据「天然成立」的第三种形态（第十轮）

`game-verify.js` 里「切到别的游戏之后，重新打开是不是**全新的一局**」，
第一版判据是 `score === 0`。反向测试（R1：卸载失效）注入之后**这条照样绿** ——
因为上一局只跑了 1.5 秒，**分数本来就是 0**。判据等于没写。

⇒ 换成长度（`gameDurationSeconds < 0.5`）：老那一局已经跑了好几秒，新的一局必然从 0 开始。
⇒ 同族：**「某个值等于它的初值」不是「它被重置过」的证据** —— 初值本来就可能是那个值。
要证「重置」，得先证明「它曾经离开过初值」（配一条 `> 0.3` 的对照）。

### 六之十六 · 内联进来的字符串会往静态检查的「已声明 / 被引用」两边灌水（第十轮）

`check.js` 第 1 项（`MISSING`：内联 handler 引用的函数都声明过）用的是**原文** `code`，
不是涂过的 `clean` —— 这是**故意的**：主页自己的 `onclick="…"` 就是写在 JS 字符串里
构建出来的，用 `clean` 会一起涂掉、那一项就变成空转。

代价是：第十轮内联进来的那份游戏源码（108 KB）**同时**往两边灌水 ——
实测它给 `declared` 添了 **32** 个名字（27 个来自 `function name(`、5 个来自
`const x = function|(`），给 `used` 添了 **4** 个；其中 `selectShip` / `togglePause` /
`restartGame` / `showShipSelect` 四个**正是它自己那些 handler 引用的**。
自洽，所以不误报，但它让「主页里同名函数被删掉」**可能被掩盖**。

⇒ 把那段（`BEGIN ST_SHOOTER_SRC` ~ `END`）从第 1 / 2 / 4 项用的文本里**切掉**；
⇒ ⚠ **并且把切了多少字节打出来** —— 静默地少看 108 KB 比不切更坏。
   现在闸门自己就把三个数打出来（`check.js` 第 1 行输出）：

   ```
   内联游戏源码: 切掉 108651 字节；顶层 `function name(` 887 → 860；declared 1020 → 988；used 150 → 146
   ```

   ⚠ **引用这几个数时直接抄这一行，别抄旧的输出** —— 它们是「当时的读数」，
   重构一次就作废（实测被写错过一次：记成 886 / 859 / 1019 / 987，
   那是**抽出 `stShooterFocus` 之前**量的，而那个函数**在 blob 之外** ⇒ 两边各 +1）。
⇒ ⚠ **口径必须同源**：报告和判据**都调** `declaredNamesOf()` / `usedNamesOf()`。
   原先两处各写一遍正则（还是不同写法）⇒ 改一处就静默漂，报告里的数跟判据用的集合对不上。
⇒ ⚠ **27 ≠ 32**：27 只是 `function name(` 那一条正则的差，
   拿它当「`declared` 灌了多少」会**少算 5 个**（另 5 个来自 `const x = function|(`）。

### 六之十七 · 顺序型断言有三种静默形态（第十二轮）

第 12 轮只做了一件事：把 `persona` 从 `desc` 后面挪到 `code` 后面（**数量不变，只动顺序**）。
「跟数量绑定」的断言一条都不用改；**跟顺序绑定**的会来收账，而它们分三种长相：

| 长相 | 例子 | 会不会红 |
|---|---|---|
| ① **遍历清单是字面量数组** | `verify_tavern_visual.js` 的 `[[id, marker], …]` | ❌ **根本不会红** —— 新项不在里面，只是静默少走一页（**最阴**） |
| ② **子串正则** | `st-code.js` 的 `/sb,code,export/` | ❌ **照样匹配** —— `ST_TABS.map(t=>t.id).join(',')` 变成 `…,sb,code,persona,export,…`，而 `/sb,code,export/` 的子串**还在**，正则跑到 `export` 就不再看后面 ⇒ 等于把 `persona` 从覆盖里静默漏掉 |
| ③ **相邻距离写死** | `persona-verify.js` 的 `pi - di === 1` | ✅ 会红（`persona` 一挪，`pi - di` 从 1 变 11），但要**同时补一条反向对照** |

⇒ ①② 是**静默失效**：改完顺序跑一遍，套件照样全绿，而覆盖已经少了一块。
   **只有「把整段列全 / 改成相邻距离 / 改成从源码枚举」才修得掉。**
⇒ ③ 会红，但**光改数字不够**：正断言只要求「挨着 `code`」，**不要求「离开 `desc`」** ——
   位置其实没挪动也能让它绿。所以配一条对照：`pi - di !== 1`。
⇒ ⚠ 本轮实测：那条对照**第一版自己写错了** —— `check(name, actual, pred, expect)` **只收 4 个参数**，
   我按正断言的形状写成 5 个（`pi - di, 1, v => v !== 1, '≠1'`）⇒ `pred` 成了字面量 `1`，
   判 `11 === 1`，**当场红**。⚠ **函数谓词只占一个位置，后面只剩一个「给人看的期望值」。**
⇒ 顺带：`st-code.js` 那条的断言名从「code 排在 sb 和 export 之间」改成
   「code 排在 sb 和 export 之间、**persona 紧跟其后**」—— 名字里写明现在盯的是什么，
   下次再挪时**光看名字就知道该改哪条**。
⇒ ⚠ **第四种：序数。** 文档里写「AI 助手是**第 7 个**选项卡」，`persona` 一挪 `ai` 就变**第 6 个** ——
   **静态检查一个字都看不见**，载体还散在三处（`RULES.md` 节标题 / `04-card-editor.md` 正文 / `MEMORY.md`）。
   挪项之后 `grep -rn "第 [0-9]* 个选项卡"`，每个都**从产品实测**：
   `awk '/const ST_TABS = \[/,/^        \];/' saki.html | grep -o "id: '[a-z]*'" | cat -n`。**别手算。**
⇒ ⚠ **还有一处「看不见的位移」**：这次改的那段**用户可见文案多了一行** ⇒ 它**后面**的锚点整体 +1
   （`5541→5542`、`5566→5567`、`5571→5572`、`5576→5577`）。`_verify/_audit-anchors.js` 会报「几行对不上」，
   但**它只扫表内的** —— 表外那三个（`#gameCard` / `#gameShooterWrap` / `#gameShooterFrameHost`）得自己 `grep`。
   ⚠ **「加了 3 行」不等于「锚点都 +3」**：改的是哪一段，只有那一段**之后**的才动。

### 六之十八 · 「新建」那条分支**永远没被执行过**，看起来也是全绿（第十二轮）

`setup-dev.sh`（新设备上把仓库里的技能 / 记忆装回 `.workbuddy-ai/`）写完后，第一版验证是：
在本机跑 `bash setup-dev.sh --go` —— 输出 **9 行「一致，不动」**，一片绿。

⚠ **但那 9 行里没有一行走过「新建」分支** —— 本机这些文件**本来就在**。
`install()` 有四条路（镜像不在 / 一致 / 已存在且不同 / 新建），而**「新建」才是唯一的主路径**
（换设备就是这个场景），它**一次都没执行**。

⇒ 修法：**把目标目录换掉再跑**。`DEST_SKILLS` 挂在 `$HOME` 下，所以
`HOME=/tmp/xxx bash setup-dev.sh --go` 就能真的走「新建」，再 `cmp` 逐字节核对落地内容：

```bash
T=/tmp/setupdev-test; rm -rf "$T"; mkdir -p "$T"
HOME="$T" bash setup-dev.sh --go
cmp "$T/.workbuddy-ai/skills/<name>/SKILL.md" markdown/<mirror>.md   # 必须逐字节一致
rm -rf "$T"                                                          # 探针自己造的东西无条件删
```

⚠ **只测「已存在」那几条分支，等于没测这个脚本** —— 它在**本机**上永远只走那几条。
⚠ 同理，**错误分支**（未知参数、目标不可写）也要各来一发，别只测 happy path。
⇒ 判据是「**这条分支被执行过**」，不是「输出全是绿的」。**绿只等于「这次没红」。**

### 六之十九 · 折叠面板：「收起了」**不能**拿 `getBoundingClientRect()` 判（第十二轮）

第十二轮给人设生成器的「模板」加了折叠（默认收起），写断言时**又**踩了同一个坑 ——
而这条规矩**上一轮还在 `MEMORY.md` 里**，被我压缩索引时误删了，且 `RULES.md` 里本来就没有
⇒ **两处都没有了**。所以这次落到这儿：

⚠⚠ **`grid-template-rows: 0fr` + `overflow: hidden` 是「裁切」，而裁切不影响 `rect`。**
里面那个 `textarea` 的 `getBoundingClientRect()` **照样是满高**，收起 / 展开量出来一模一样：

```js
ta.getBoundingClientRect().height   // 280 —— 收起时也是 280
```

⇒ 判「收起了」要**量那个真正塌下去的东西**（外层网格容器自己）+ 做**命中测试**：

```js
getComputedStyle(body).gridTemplateRows   // "0px" vs 真 px
body.getBoundingClientRect().height       // ~0 vs ~300
// 折叠头下方 60px 处打一针：收起时打在折叠块**外面**，展开时打在里面
```

⚠ **命中测试那个点必须先断言「落在视口里」**，否则点在屏幕外时 `elementFromPoint` 返回
`null` ⇒ `.closest` 为假 ⇒ 「收起」**天然成立**，一条什么都没看的绿。
⚠ 套件里**故意留一条**「里面 textarea 的 rect 照样是满高」当断言 —— 看着像废话，它的作用是
**下一个人想改回量 rect 时当场变红**，而且红在名字上就写着为什么。

⇒ **教训不只是「用命中测试」，还有一条流程上的**：压缩 `MEMORY.md` 时我逐条 `grep` 核了
「`RULES.md` / 技能里有没有」，但**只核了当时手上那几条** —— 这一条没在手边，就被当成重复项删了。
**「删前确认」要对着「准备删的那一条」核，不是对着「我记得重复的那一批」核。**

### 六之二十 · 推送绿了、远端 blob 一致，**也不代表上线了**（第十三轮）

第十二轮改完推送（`4002051`，远端 11/11 blob 一致）之后，**线上还是旧版**。这是本项目第一次
真正卡在「部署」而不是「代码」上，值得单开一条。

⚠⚠ **`git push` 退出码 0 + 远端 blob 一致，只证明「仓库对了」，不证明「站点对了」。**
要判「上线了没」，唯一的判据是**拿线上那个文件的字节算 sha1，跟本地比**：

```js
const r = await fetch('https://<域名>/index.html?cb=' + Date.now());
const buf = Buffer.from(await r.arrayBuffer());
sha1(buf) === sha1(fs.readFileSync('index.html'))   // 这才叫「上线了」
```

⚠ **HEAD 请求的 `content-length` 是压缩后的**，别拿它比字节数 —— 要 GET。

#### 判据：`cancelled` 要先**数 job**

```
GET /actions/runs/<id>/jobs  →  { total_count: 0, jobs: [] }
```

- **`failure`** = job 跑过、某步挂了 ⇒ 去读 step。
- **`cancelled` 且 `total_count: 0`** = **job 从没被调度**，run 在**排队阶段**就被掐了。

再加 `updated_at - created_at ≈ 1 秒`，基本可以直接指向**并发组**，不用再猜构建。

⚠ 更硬的一条：`GET /repos/<o>/<r>/deployments` —— **排队阶段被取消的 run 根本不会创建
deployment**，所以 `/deployments` 里最新那条会**停在更早的那个 sha 上**。这比看 run 列表权威。

#### 根因形态：多条 workflow 共用一个 `concurrency` group

本项目实测：`hugo.yml` / `jekyll-gh-pages.yml` / `static.yml` **三条**全部
`on: push: branches: ["main"]`，**全部** `concurrency: { group: "pages", cancel-in-progress: false }`。

GitHub 语义：**新进入同一组的 run 会取消「已在排队（pending）」的那个** ——
`cancel-in-progress: false` 只保证**不打断正在跑的**。三条同时被一次 push 触发 ⇒ **互相取消**，
谁恰好在 pending 谁死。

⚠ **每条单独看都是「最安全的写法」**（`cancel-in-progress: false` 看起来最保守），
合起来却在互相残杀 ⇒ **看并发配置要连着 `on:` 一起看**，单看一条看不出来。
⚠ 旁证：同一 commit 的 `GET /commits/<sha>/check-runs` 里会多出**别条 workflow 的**
`build : completed/failure`（本项目那两条是 GitHub 自动塞的模板，这里根本没有 Hugo/Jekyll 站点，
所以每次必败）。

#### 修法：先用**非破坏性**的解锁，再谈删

`workflow_dispatch` **只触发被点的那一条**，不会带上 push 触发的兄弟 ⇒ 它独占并发组：

```js
POST /repos/<o>/<r>/actions/workflows/static.yml/dispatches  { "ref": "main" }   // → 204
```

本项目实测 21 秒跑完、7 个 step 全绿、线上立刻变成新版。
**真正的修法**是让那两条不用的 workflow 不再跑（否则以后每次 push 都有概率被静默吞掉，
而且它们会在**每个 commit** 上持续刷假的 `build : failure`）—— 但那是改用户的仓库，**要先问**。

⚠⚠ **「停用」比「删掉」好，能选可逆方案时就选可逆方案。** 实测：

```js
PUT /repos/<o>/<r>/actions/workflows/<文件名>/disable   // → 204，状态变 disabled_manually
PUT /repos/<o>/<r>/actions/workflows/<文件名>/enable    // → 204，随时能回来
```

停用**完全可逆**、且保住了「这两条曾经存在、且每次都败」的证据；删除会把证据一起抹掉。
（同一条原则：`_purge-tmp.js` 默认只数不删、`setup-dev.sh` 默认 dry-run。）
本项目 2026-09-23 已把 `hugo.yml` / `jekyll-gh-pages.yml` 停用，`static.yml` 保持 active。

⚠ **`/actions/workflows` 的 `workflow_id` 可以直接传文件名**（`hugo.yml`），不必先查数字 id。

**固化成了工具**：`_verify/deploy-check.js`（只读，`--runs` 顺带查 Actions / deployment / workflow 条数）。
⚠ 它不是套件（依赖网络），必须登记进 `run-all.js` 的 `NOT_A_SUITE`，否则 runner 会当「未分类 `.js`」报硬错误。
⚠ 比字节数**不能用 HEAD** —— HEAD 的 `content-length` 是压缩后的。

#### ⚠ 一条流程教训：文档里「纯噪声，不影响部署」那句是**上一轮自己写的**

README 里那句错话，是**接入 GitHub 那一轮**写的 —— 当时**观察到了「互相取消」这个现象**，
却把它判成了「不影响部署」。下一轮它就以「推送成功、线上没变」的形式回来收账了。
⇒ **观察到了现象 ≠ 判对了后果。** 「它俩会互相取消」和「这不影响部署」是两句不同的话，
中间那步「**取消的到底是谁**」当时没查。
⇒ **现象写进文档时要写「我查到了什么」，不要写「所以没事」** —— 后者是结论，结论要证据；
而一句错的结论会在文档里躺很久，还会被下一次的自己当成前提读。

#### ⚠ 取令牌：别用 `sed`，也别把变量放错位置

1. ⚠ **`sed` 的分隔符跟字符类撞了**：`s@…\([^@]*\)@…@` —— `@` 既是分隔符又在 `[^@]` 里，
   报 `unknown option to 's'`；换 `#` 那版又报别的。**不跟它耗**。
2. ⚠⚠ **`node -e '…' TOK="$TOK"` 把变量传成了「脚本参数」，不是环境变量** ⇒ 脚本里
   `process.env.TOK` 是 `undefined` ⇒ 请求 401。正确写法是**前置**：`TOK="$TOK" node -e '…'`。

**推荐做法：在 Node 里读凭据、在 Node 里发请求** —— 没有 shell 引号问题、没有 `sed` 方言问题、
也**不可能把令牌打进终端**：

```js
const line = fs.readFileSync(credPath, 'utf8').split(/\r?\n/).find(l => l.trim());
const TOKEN = line.match(/^https:\/\/[^:]+:([^@]+)@/)[1];   // 永远不打印 TOKEN
```

#### ⚠⚠ 先怀疑「自己造的假线索」

`GET /pages` **不带令牌返回 404 —— 公开仓库的健康 Pages 也是 404**。我一度拿它当
「Pages 配置丢了」的证据，白绕一圈。带令牌同一个仓库读出来完全正常
（`build_type=workflow` / `cname=yansaki.top` / `https_enforced=true`）。
**同一个查询，认证状态不同会给出方向相反的结论** —— 判「配置坏了」之前先确认「我是不是没带认证」。

#### 收尾：临时脚本无条件删

诊断用的三个脚本（`_verify/_pages-diag.js` / `_pages-diag2.js` / `_pages-dispatch.js`）
用完**立刻删** —— `_verify/` 里下划线开头是「临时脚本」的约定（`run-all.js` 会跳过它们），
但**跳过 ≠ 可以留着**。

#### ⚠ `git push` 被代理挡死时：用 **Git Data API 兜底推送**（第十三轮实测）

本机 git **必须**走本地代理（直连 `github.com:443` 不通），而代理会周期性对 `github.com`
返回 `CONNECT tunnel failed, response 502`（实测连续 11 次 / 跨 4 分钟全败）。
**同时 `api.github.com` 直连是通的** —— 因为 **Node 的 `fetch` 不走 `http_proxy`**。
**同一个网络、两条路、一条死一条活。**

```bash
env -u https_proxy -u HTTPS_PROXY -u http_proxy -u HTTP_PROXY git push origin main
#   "Could not connect to github.com:443"  ⇒ 代理是**必须**的，绕不开 ⇒ 走 API
```

**核心手法：复刻一模一样的 commit 元数据**（tree / parent / author / committer / message 全从
本地 `git cat-file commit` 原样取出）⇒ **远端算出来的 sha 等于本地 sha** ⇒ **零分叉**
（不会出现「本地领先一个哈希不同的提交」那种需要 rebase 的烂摊子）。

```
blob   POST /git/blobs    {content: base64, encoding:"base64"}   → 比 `git rev-parse <sha>:<path>`
tree   POST /git/trees    {base_tree, tree:[{path,mode,type,sha}]} → 比 `git rev-parse <sha>^{tree}`
commit POST /git/commits  {message,tree,parents,author,committer}  → 比本地 sha
ref    PATCH /git/refs/heads/<b>  {sha, force:false}               ← **只有上面全中才走这一步**
```

⚠⚠ **每一步都拿本地 sha 当闸门，任何一步对不上就立刻退出** —— 此时远端 ref **一个字节都没动**
（`create blob/tree/commit` 都**不会**移动 ref），只会留几个 dangling 对象。
**这就是它敢试的原因**；`force: false` 再让 GitHub 自己拒掉非快进。
⚠ **message 要逐字节一致、含结尾换行** ⇒ 读原始 commit 对象按**第一个**空行切（别用 `-p` + `trim`）。
⚠ **日期**：Git 存 `<epoch> <+HHMM>`，API 要 ISO 8601 ⇒ 从 epoch + 存下来的 offset 反推，
否则 offset 不往返、sha 就不等（`1790158678 +0800` → `2026-09-23T18:17:58+08:00`）。
⚠ 改动路径用 `git diff-tree -r --no-renames --name-status -z <parent> <sha>`（`--no-renames` 把
`R100 old new` 拆成 `A`/`D` 一对）；删除项在 tree 里传 `sha: null`。
⚠ **会写远端的脚本，默认动作必须是只读** —— 工具 `_verify/api-push.js` 默认 dry-run，`--go` 才真推。
⚠ 写它时自己踩了个**会卡死**的 bug：留了一行 `git hash-object --stdin`（**等 stdin**，跑起来无限挂起）。

展开版见当日日志「二十八」，可复用版见技能 `git-push-existing-github-repo` §6。

### 六之二十一 · 「判据范围定错」是**独立**的失败形态，而且它长得像「工具很严格」（第十三轮）

把「文档节号撞号」检查固化成 `_verify/_audit-sections.js` 时，第一版按
**「同一文件、同一层」**去比 ⇒ 一次报出 **24 处假撞号**：

```
2026-09-20.md   ❌ 撞号 [H3 / cir / ①] 共 7 处（第 142 / 706 / 855 / 967 / 1027 / 1290 / 1398 行）
CHANGELOG.md    ❌ 撞号 [H3 / cir / ①] 共 27 处 …
```

全是假的：日报 / CHANGELOG 里每个 `## 第 N 段` **各自有 `### ①…⑧`**，那是**每段内部的局部编号**，
跨段重复完全正常。**正确的范围是「同一个父节内」**（按标题栈找最近的上级标题，`##` 的父节是文件根）。

⚠⚠ **假红比不检查更坏 —— 它会让人开始无视这个工具**（跟「永远在报的检查」同一个下场）。
⚠ **「判据范围定错」和「判据太松」是两个相反的病，但症状都是「红/绿得不对劲」**：
- 太松 ⇒ **静默少走**（漏报，看着一片绿）；
- 范围错 ⇒ **假红成灾**（看着很严格）。
两者都**不会自己暴露**，只能靠「拿真实数据跑一遍看红的是不是真问题」来发现。
⇒ **写范围型判据时先问一句：「这个范围里，重复到底该不该算错？」**
⇒ **如果一次报出两位数的问题，先怀疑判据，别先怀疑数据。**

**配套要求：范围型判据必须有反向测试，而且正反两面都要证。** 本项目 `_selftest-sections.js`（14 项）：

| 项 | 期望 | 为什么 |
|---|---|---|
| 基线（不注入） | 绿 | 否则工具本身坏了 |
| 注入**真撞号** | **必须红** | 否则它是个摆设（「从来没抓到过东西」也是绿） |
| 注入**跨父节重复** | **不能红** | **给范围 bug 立碑** —— 保证它不会被重新判成错 |
| 注入**跳号** | 只打 ⚠、**退出码仍 0** | 钉住「软提示不计入失败」这条行为断言 —— **没被测过的断言跟没写一样** |
| 还原 | 逐字节 sha1 | 注入器污染了被测对象，后面全是假的 |

⚠ 写这种测试时的一个小坑：**`execFileSync` 在退出码非 0 时抛异常**，而「非 0」正是要观察的东西
⇒ 必须用 **`spawnSync`** 拿 `status`。
⚠ 收尾那句「N 项全部符合预期」**必须数出来，别写死** —— 实测补了第四项之后它还在说「三项」。

### 六之二十二 · 改了**调用点**，锚在它身上的反向测试会静默失效（第十三轮）

给 `stExportMsg(text, kind)` 加第三个参数 `scope` 时，全站 **14 处** persona 调用点被改成
`stExportMsg(..., 'persona')`。改动本身是对的，但 `_reverse13.js` 的 **R2** 探针锚定的是
**跨 4 行**的一段代码，里面正好含这一行：

```js
stExportMsg('已取消 —— 角色描述没动。', 'warn');      // 本轮变成 ..., 'warn', 'persona');
```

⇒ 注入点在产品里**命中 0 次**，R2 那一组全部失效。

⚠ **救回来的是闸门，不是运气**：`_reverse13.js` 在跑整跑**之前**先数一次
`ORIG.split(p.from).length - 1`，**必须恰好是 1**，否则当场 ❌ 并 `continue`
（**不跑那 9 次**）。所以症状是「一行 ❌ + 2 分 22 秒没白花」，而不是
「R2 那几条悄悄变成永远为真」。

⚠⚠ **把失效形态想全**：

| 形态 | 症状 | 自己会暴露吗 |
|---|---|---|
| 命中 **0** 次（锚点整段变了） | 注入等于没注入，「注入后」跑的是**基线** ⇒ 基线是绿的 ⇒ `预期该红的都红了` **立刻红** | ✅ 会 |
| 命中 **> 1** 次（锚点太短） | 一次注入改多处，红的是**别的**几条 | ✅ 会（「恰好这几条」那条闸门） |
| 命中 **1** 次，但**命中的是残缺片段** | 注入生效、红的也**恰好是预期那几条** —— 但它验的已经不是原来那件事了 | ❌ **不会** |

⇒ **改任何调用点（加参数、改文案、挪位置）之后，把所有反向测试重跑一遍。**
⇒ **别只 grep 探针名** —— 探针的 `from` 是**代码片段**，改的是片段里的字面量，
   跟「探针叫什么」毫无关系。**判据是「注入点还能不能命中，且命中数 == 1」。**

### 六之二十三 · 「挪走」和「再抄一份」在画面上**长得一样** ⇒ 要上下游各打一针（第十三轮）

用户要的是「把工作状态**挪**到按钮上方」。可「挪」和「两边都写一份」对用户来说，
差别只是**同一句话出现一次还是两次** —— 而断言如果只写了「页内格里有这句话」，
**两种实现都会绿**。

所以 `_reverse13.js` 加了两针，打在**同一件事的上游和下游**：

| 探针 | 打哪 | 注入 | 预期红 |
|---|---|---|---|
| **R7** | 下游：`stPaintMsg()` 里常驻条的**让位判定** | `show = !!m.text`（常驻条永不让位） | **恰好 2 条** —— 那两条「常驻条是空的」 |
| **R8** | 上游：`stExportMsg()` 里 `scope` **存不存** | `scope: ''`（scope 永远丢） | **恰好 5 条** —— 页内格那 3 条 + 常驻条那 2 条 |

⚠ **两针的 red 名单不一样，而且 R8 的 red 里包含了 R7 的那两条** —— 这是对的：
上游一断，消息**确实**跑到常驻条去了，那两条本来就该红。
⚠ 但也正因为如此，**它们不能互为对照**：拿 R7 当 R8 的对照组会「对照组自己也红」。
⇒ **对照组要挑「这一针打不到的那部分」**（这里挑的是 DOM 顺序、默认隐藏、收尾清理那几条）。

**推广**：一个需求如果同时包含「**加**了什么」和「**去掉了**什么」（挪位置 / 换通道 / 改归属），
**两边都要有断言** —— 只写「新的地方有了」，漏掉的正是「旧的地方还在」。

### 六之二十四 · 断言「崩不掉」是反向测试能跑的前提（第十四轮）

写新断言时，**必须预判「注入之后它会怎么红」**。

`persona-verify.js` 的 I2 段第一版写的是：

```js
check('新条目的正文就是生成结果',
  await ev(`stEditor.card.bookEntries[${b0}].content`), OK_REPLY);
```

产品没改之前跑一遍 —— 按钮还不存在，`.click()` 那行就抛了；更麻烦的是**等产品改好、
反向测试把 `a.push(e)` 拆掉之后**：条目压根没建出来，`bookEntries[1]` 是 `undefined`，
读 `.content` **抛 `TypeError`**，`ev()` 把它抛出来 ⇒ 套件**当场炸掉**。

⚠⚠ **炸掉的后果不是「多红一条」，而是「拿不到汇总行」**：

| | 正常失败 | 崩掉 |
|---|---|---|
| 汇总行 | 有（`N 通过 / M 失败`） | **没有** |
| `failsOf()` | 拿到 M 条名字 | **空** |
| 反向测试的判据 | 「预期该红的都红了」能核 | **全部无从谈起** —— 那一针等于白跑 |

而且**症状长得很像「探针设计得不对」**，很容易去改探针，其实是断言自己的问题。

**做法**：读数组 / 对象元素一律写成**取不到就当空**的形式 ——

```js
String((stEditor.card.bookEntries[i] || {}).content || '')
JSON.stringify((stEditor.card.bookEntries[i] || {}).keys || [])
```

⚠ 但 `|| []` 会**掩盖**「元素不存在」这件事（缺元素时 `keys` 读成 `[]`，正好等于
「关键词为空」的期望值）。所以**别指望这一条去抓「条目没建出来」** ——
旁边必须另有一条**显式数长度**的断言（`bookEntries.length === b1 + 1`）来盯它。
**「不崩」和「抓得到」是两个要求，一条断言只干一件事。**

### 六之二十五 · 提示文案**天然为真**：它报的是一个「不会变」的数（第十四轮）

「追加到世界书」成功时会打一句：

```js
stExportMsg('✅ 已追加到世界书（第 ' + a.length + ' 条 · 关键词：' + nm + '）。', …);
```

`a` 就是 `stEditor.card.bookEntries`，**`a.length` 是 push 之后的长度** ——
可 `push` 被拆掉时，`a.length` **根本不会变**，于是那句提示**照样说「已追加到世界书（第 1 条）」**。

`_reverse13.js` 的 **R9** 把 `a.push(e)` 拆掉之后，实测：

- **红的 8 条**全是「条目本身」的（数量 / 正文 / 启用 / 备注 / 关键词 / 渲染 / 那两条连带的）；
- **`提示说已追加到世界书` 和 `提示是 ok` 是绿的** —— 而且这是**故意留绿**的：
  它绿着正是这一针要展示的东西 —— **光看提示，功能像是成功了**。

**判据**：一条提示如果报的是**「这次操作自己算出来的数」**（`a.length`、`out.length`、
`labels.length`），那它**对「操作有没有真的发生」是免疫的**。
⇒ 断言别只盯着提示文案，**要盯着状态**（长度 / 字段 / DOM）。

⚠ 这条和「绿 ≠ 验证过了」是**同一个病的两种长相**：
一种是「断言永远为真」，这一种是**「被断言的东西永远为真」**。
写提示的时候顺手问一句：**这句话有没有可能在我搞砸的时候还说得出口？**

### 六之二十六 · 「对照组」必须**不同**，不能只是**存在**（第十五轮）

需求改成「世界书的名称和关键词都取生成结果里 `姓名:` 后面的字符」，于是 I2 段加了取值断言。
原来的对照组用的是：

```js
const OK_REPLY = '姓名: 夜乃\n年龄: 19\n性别: 女';   // 而卡名也设成了「夜乃」
```

于是：

| 断言 | 「从 `姓名:` 取」实现 | 「从卡名取」实现 |
|---|---|---|
| 备注 === `夜乃` | ✅ | ✅ |
| 关键词 === `["夜乃"]` | ✅ | ✅ |

**两条取值路径读出来是同一个字符串** ⇒ 这两条断言**分不出产品是从哪儿取的名**。
把取值函数整个删掉、让它一路回落卡名，它们**照样全绿** —— 一条**恒真**断言，
只不过伪装成了「有对照组」。

**做法**：另起一份结果，**让期望值故意不等于卡名**：

```js
const BOOK_REPLY = '姓名: 艾莉丝\n年龄: 19\n性别: 女';   // 卡名仍是「夜乃」
```

⚠ **写「从 A 取」这类断言之前，先问一句：A 和 B 会不会碰巧一样？**
「有对照组」≠「对照组能区分」 —— 恒真的断言和根本没写断言，**在报告上长得一模一样**。

⚠ 与 `六之十五` 同族但形态不同：那几种是**判据本身**天然成立，这一种是**对照组**天然成立。

⚠ 连带：改了靶子套件的断言名，`六之十一` 那条就得再走一遍。本轮 R9 的名单
（`red` 8 → **11**、`green` 11 → **22**）是**存在性闸门**在整跑之前拦下的 ——
「名单是手抄的」这笔账，每加一条断言都会来收一次。

### 六之二十七 · 「回落」是**把失败伪装成成功**（第十五轮）

`mode === 'book'` 的取名链是三层回落：

```js
const inName = stPersonaNameFromOut(out);          // 生成结果里「姓名:」后面
const nm = inName || stStr(stEditor.card.name);    // 回落卡名
e.comment = nm || '人设';                          // 再回落一个字面量
if (nm) e.keys = [nm];                             // 两处都没有 ⇒ 关键词留空
```

落回卡名那一层**特别像成功**：条目建出来了、正文一字不差、渲染正常、提示还是绿的 ——
**只有名字悄悄不是你想要的**。

⚠ 所以**回落必须在提示里说出来**：

```js
(inName ? '' : (nm ? ' —— 生成结果里没有「姓名:」，用的是卡名' : ' —— …'))
```

**判据**：任何「取不到就换一个」的分支，都要在用户看得见的地方说明它换了。
静默回落 = 用户拿到一个「看起来对」的结果，错误被推迟到他真正要用的时候才爆。

⚠ 配合 `六之二十五`：回落支的提示**不能只报成功** —— 否则「回落了」和「取到了」
在提示上分不出来，而这一支恰恰是最需要被看出来的那一支。

### 六之二十八 · CRLF 会从**运行时数据**里进来（第十五轮）

老坑是「`saki.html` 是 CRLF ⇒ JS 里 `/\/\/.*$/` 整条匹配失败」。这一轮是它的**新形态**：
**带 `\r` 的字符串不是文件里的，是运行时喂进来的。**

取值函数第一版：

```js
const m = String(text).match(/^[ \t\-*]*姓名[ \t]*[:：][ \t]*(.*)$/m);
```

`text` 是**模型返回的文本**（走网络、再经 `textContent` 拼装），行尾是 `\r\n`。而 JS 的：

- 多行模式下 `$` 匹配的是 `\n` **之前**的位置，`\r` 会**留在** `(.*)` 的捕获组里
  ⇒ 值尾巴上挂着一个 `\r`；
- 表现是断言 `=== '艾莉丝'` **红**，而打印出来**肉眼一模一样**（`\r` 不可见）。

**做法**：进函数第一步先归一 ——

```js
const t = String(text == null ? '' : text).replace(/\r\n?/g, '\n');
```

⚠ **判据**：凡是用 `$` 锚行尾、或按行切分的正则，**先问「喂进来这个字符串是谁造的」** ——
`saki.html` 自己（CRLF）、`localStorage` 里的旧数据、`fetch` 回来的响应、模型输出，
**都可能带 `\r`**。别默认它跟调用点同一个行尾。

### 六之二十九 · 注入之后的**连带红**，也要一条不落地写进 `red`（第十六轮）

反向测试的判据是三条：**预期该红的都红了** / **对照组一条都没红** / **没有预期之外的红**。
第三条最容易被当成「探针坏了」，其实它经常在说一件**真事**：
**打坏一个函数，红的不止你想的那几条。**

第十六轮 R9 打的是「追加到世界书」（把 `push` 拆掉）。预期 **11** 条红，实测 **38** 条。
多出来的全是**连带**：

```js
const idx = a.length - 1;          // 注入：不 push
// ⇒ 条目压根没建出来，而下面这些读的是 bookEntries[b - 1]
//    —— 那个下标落到了**原有条目**上，于是读到的是它的关键词 / 备注
```

于是「没有「姓名:」⇒ 回落卡名」「两边都没有 ⇒ 关键词是空的」这些**看着跟这一针无关**的
断言跟着红了。**它们红得对** —— 功能确实坏了，只是坏得比预期更广。

⚠ **做法**：连带红**一条不落地写进 `red`**。别为了让闸门闭嘴去改产品、也别去放宽判据。
⚠ **反向也要防**：如果连带红**没有**发生，说明那一针根本没走到那条路上 —— 那才是探针坏了。

⚠⚠ **「对照」不等于「必然绿」。** 同轮 R13（`stPersonaBookWrite` 忽略 `prev` ⇒ 覆盖退化成追加）
里有两条 `（对照）覆盖没有把启用开关改回去` / `…正则开关…` 也红了。原因：覆盖退化成追加之后，
被查的是**原来那条**（它的开关还是默认值，而这两条本来是在查「被改过的那条」）。
⇒ **对照断言绿的前提是「被测的那条路真的被走到了」**，它跟 `red` 一样要跟着实测修。

### 六之三十 · 在样式块里写 `</style` 会把样式块**当场截断**（第十六轮）

`<style>` 是 HTML 的 **raw-text 元素**：解析器在它里面**只找 `</style`** ——
**CSS 注释挡不住它**。所以往样式块里（哪怕写在 `/* … */` 里）放一个**结束标签的字面量**，
样式块在那一行就结束了，**后面的 CSS 全部变成正文**。

第十六轮就是这么坏的：改注释时顺手写了 `` `</style>` **之后**的锚点照样整体后移 ``，
`.st-ask { position: fixed; … }` 连同复古覆盖**整条规则失效**。

**症状**：元素**掉回文档流**（computed `position: static`）。
⚠ **rect 看不出来** —— 它的 rect 是 `{t:1070, w:1240, h:92}`（视口才 900 高），
只是「位置离谱」，看着不像「样式没生效」；
**命中测试一枪就中**（「屏幕正中必须点到它自己」→ 报 `OTHER:DIV.st-actions`）。

⚠⚠ **更该记的是我顺手把闸门改错了。** 外部 `static_check.js` 那道「style 块提取没错位」
**先**红过一次（注释里提到**开**标签 ⇒ `2 开 / 1 闭`）—— 那**确实是误报**，提取是对的。
我把它改成「**先摘掉注释再数**」；**这一改正好把上面那个真错藏起来了**，
因为注释里的 `</style>` 也一起被摘掉了。

**正确判据：按解析器的规则数 —— `</style` 是唯一终止符，不做任何注释剥离。**

| 注入 | 期望 | 实测 |
|---|---|---|
| 真实文件 | ✅ 绿 | `close=1 blocks=1` |
| 样式块里多一个**结束**标签字面量 | ❌ 红 | `close=2` |
| 样式块里多一个**开**标签字面量 | ✅ 绿 | `close=1` |
| 真的多一个 style 块 | ❌ 红 | `close=2 blocks=2` |

⚠⚠ **「误报」和「真错」长得一模一样，区别只在「你数的是哪一个标签」。**
把闸门放松到「不再误报」很容易顺手把**真错**也放过去 ⇒
**修闸门之前先问一句：它数的那件事，跟解析器数的是不是同一件事。**

⚠ **同族坑（换载体、同一条规矩）**：`<script>` 里不能出现 `</script`；
CSS 注释里不能出现 `</style`；JS 字符串里嵌 HTML 要打断 `</script`（七）。
⇒ **凡是要把「标记语言的结束标签」当普通文字写进它自己的块里，先问一句「谁在扫这个字面量」。**

### 六之三十一 · 反向测试的**另一半**职责：告诉你哪条路没人看着（第十七轮）

这一轮是「API 全局配置」（把全站 AI 配置收成一份真相源 `apiGlobal`，【ai对话】可跟随 / 独立，

**a. 一条断言在两种实现下都绿 ⇒ 它天然分不出来源。**
「切回跟随：编写器读到的还是全局那份」—— 因为**「点回跟随」这个动作本身**就会把 `aiConfig`
刷成全局值，于是「读全局」和「读 `aiConfig`」又指向同一串了。反向测试 **R1** 原本把它算作

⇒ **断言的位置不对，它就永远绿** —— 而它长得跟旁边那几条一模一样。

**b. 一条注入在套件里没有任何可观测效果 ⇒ 说明套件缺一条断言**（反过来找洞）。
**R8** 拆掉 `aiSyncOwnFromEffective` 的守卫，第一轮跑下来**一条都没红**。
想清楚之后真场景是：**跟随模式下 `persistSystemPrompt()` 照样会跑**（改预设 / 改提示词都会调它），
无条件同步就把用户那份独立配置换成了全局值。补上「跟随：改系统提示词不会冲掉独立那份」才咬得动。
⇒ **反向测试不只是「证明断言会红」，它还会告诉你哪条路没人看着。**

**c. 又一次「新断言必须崩不掉」。** **R6** 把 `followGlobal` / `own` 抹掉之后，
套件里 `await ev('aiConfig.own.apiKey')` 直接抛 `TypeError` ⇒ **套件当场炸掉、连汇总行都没有**，
反向测试拿不到「红了几条」，那一针**等于白跑**。修法：读嵌套属性一律 `(aiConfig.own || {}).apiKey`，
读 `localStorage` 一律 `JSON.parse(localStorage.getItem(k) || 'null') || {}` —— 给个空壳让断言**红**，
而不是把整个套件带走。

**d. ⚠ 改「跟随源」这类东西，先 grep 套件里有没有人直接写那个字段。**
`persona-verify.js`（19 条红）与 `sb-verify9.js`（**连汇总行都没有**）都红了，形状一样：
它们在 `configAi()` 里**直接写 `aiConfig.*`** 来「配好 AI」，而这两条路都走 `stAiCfg()`
⇒ 现在读的是 `apiGlobal` ⇒ **请求压根没发出去**。改成配 `apiGlobal` 后两套立刻回到 **277/0**、**123/0**。
⚠ 症状很能骗人：「确实发了 1 次请求」失败**看着像功能坏了**。

### 六之三十二 · 两个流程坑（同一轮）

### 六之三十三 · 「猜」和「决议」是**两步**，断言要打在**决议**上（第十八轮）

第十八轮加第三种协议时，把「服务商 → 协议」写成两层：

| 层 | 函数 | 干什么 |
|---|---|---|
| 猜 | `stAiGuessProto(baseUrl, provider)` | 看关键词（`anthropic` / `aiplatform` / `generativelanguage`…） |
| **决议** | `stAiProtoOf(provider, baseUrl)` | **先查预设表**，查到就用；只有没写的（`custom`）才去猜 |

第一版**只给「猜」写了断言**，它猜得全对、全绿。而真正决定请求形状的是**决议** ——
预设表里给 `custom` 写了 `proto: 'openai'` ⇒ 决议**整条跳过 URL 那一步** ⇒
用户「自定义」粘 Anthropic 的域名时**按 OpenAI 形状发出去**（400），
**界面显示是对的，只有真发一次请求才看得出来。**

⇒ **一条断言看着绿，可能只是因为它量的是旁边那一步。**
   **「量得没错，但量错了对象」= 没量。**
⇒ 修法不只是改产品：**断言要打在真正决定行为的那一步上**，并且
   **给那一步单独造一个只有它能答的场景**（这里是「空 Base URL」——
   猜不出来（只能给 openai），只有表能答）。
   ⚠ 而「只有它能答」这个说法本身**也要核**：实测「vertex / anthropic 空 URL」
   光靠 provider 名字也猜得对 ⇒ 只有 `gemini-native` 那一条是真的「只有表能答」。
   断言名里写着「只有表能答」而其实不是，比不写更坏。

### 六之三十四 · 反向测试**跑着的时候别改产品**（第十八轮）

`_reverse*.js` 的做法是：启动时把产品读进内存当基线，每个探针注入 → 跑套件 → **从那份内存写回磁盘**。
⇒ 你中途改了 `saki.html`，**下一次还原就把它盖掉**，而且**没有任何提示**
（那两行改动的上下文还在，文件照样解析 —— 只有回读那一处才发现是旧的）。
第十八轮就这么丢过一次「Code 页的协议闸门」，过了几步 `grep` 才发现。

⇒ 规矩：**要么等它跑完再改，要么改完立刻回读那一处**。
⇒ 中途 `kill` 会留下两样东西：`_verify/_reverse*.bak`（**里面是干净基线**）
   和**一份被注入过的产品**。下次启动时套件会**拒绝跑**（那是对的，别把它当 bug），
   人工先 `cp` 回来、核对没有注入痕迹（`grep "注入："`），再删 `.bak`。

### 六之三十七 · 模板字符串里出现**反引号**会把字符串提前结束（第十八轮）

套件里 `ev()` 的参数几乎都是模板字符串。在**注释**里写一个 `` `custom` `` 就会把它闭合，
后面的代码变成语法错 —— 而报错位置指向**模板字符串开头那一行**（这里就是函数开头），
离现场几十行，看着像「函数写坏了」。

⇒ 一轮之内**踩了三次**，所以做成闸门：`_verify/_lint-suites.js`

### 六之三十八 · 命令行里的正则**反斜杠会被吃掉**（第十八轮）

在 Bash 工具的命令串里写 `\s`，到 `node` 手上会变成 `s` —— `/value:\s*'/` 变成 `/value:s*'/`。
`/s*/` 是「零个或多个字母 s」，**语法合法、语义全错**；这次运气好它撞上 `'` 报了语法错，
否则就是一条**静默不同**的正则（跟「写死清单每次加东西都来收账」同一族）。

⇒ 命令行里的正则**一律不写 `\s` / `\d` / `\w`**：用 ` *`、`[0-9]`、`[^']` 这种字符类代替，
   或者 `node - <<'EOF'` 从 stdin 灌脚本（heredoc 也救不了 —— 变换发生在 shell 之前）。
⇒ ⚠ 由此推一条：**「我写的命令」和「真正跑的命令」可能不是同一串** ——
   凡是靠命令行拼出来的判据，输出不对时**先把命令本身打出来看一眼**，别先怀疑被测对象。

### 六之三十九 · 防崩的写法会把断言变成**天生为真**（第十九轮）

为了「注入删掉整个字段时别让套件抛异常」，取值一律写 `(x || [])`。但**空数组的
`every` / `some` 有定义好的返回值**：`[].every(...) === true`、`[].some(...) === false`。
⇒ 于是这条断言

```js
check('阈值全是 OFF', (body.safety || []).every(x => x.threshold === 'OFF'), true);
```

在 `safetySettings` **被整个删掉**时**照样绿** —— 而它名字里写的正是这件事。
第十九轮反向测试 R3 实测：注入删掉那一行，这条**没红**，是闸门「没有预期之外的红」
把它顶出来的（红的是旁边两条）。

⇒⚠⚠ **「崩不掉」和「不会永远为真」是互相打架的两个要求，必须同时满足。**
   形状一律改成**「数出来跟期望比」**：

```js
check('阈值全是 OFF', (body.safety || []).filter(x => x && x.threshold === 'OFF').length, 5);
```

   字段没了 ⇒ `0 ≠ 5` ⇒ 红；阈值写错 ⇒ 少于 5 条 ⇒ 红；**而且不会抛**。
⇒ 凡是 `|| []` 后面跟着 `every` / `some` / `find` 的断言，都要按这条重新看一遍。

### 六之四十 · 「函数写好了」和「函数被调用」是两件事（第十九轮）

上一轮加了「空响应要说得出原因」，函数 `stAiWhyEmpty` 写得很完整 —— 但**零调用点**：
三条请求路径上一个都没接。⚠ **静态检查全都看不见它**（函数声明在、语法通、
`UNDECLARED` 也不报，因为没人引用它），**行为断言也看不见**（测的是函数返回值，
它照样对）。⇒ 用户看到的还是「AI 没说话」。

⇒ 加一个函数之后，**覆盖要盯调用点，不是盯定义**。具体做法：拿「空响应」这个场景
**走真实请求路径**（桩返回空响应 → 调 `nonStreamChat` / `stAiChat`），断言它**抛出来的错**
里带着原因 —— 而不是直接调那个函数比返回值。
⇒ ⚠ **一份逻辑有两份实现时，两份都要走一遍**：`nonStreamChat`（【ai对话】）与
   `stAiChat`（编写器）是两处独立代码，只改一处、只测一处，另一处照样静默。

### 六之四十一 · 反向测试的注入要**只打它声称要打的那件事**（第十九轮）

R1 声称「`stAiVertexProject` 不派生」，注入却是把**整个函数体**换掉 —— 连
「用户手填优先」那一支也一起打掉了。结果**对照组里一条跟着红**（那条断言的前提是
「SA JSON 能提供项目」，跟手填无关），闸门当场拦下。

⇒ 注入的 `from` / `to` 要**窄到只覆盖被声称打掉的那几行**，别图省事整块替换。
   ⚠ 反过来也成立：**真该红的连带红，一条不落地写进 `red`**（第十九轮 R1 实测
   红 3 条、名单只列了 2 条 —— 多出来那条的前提**正是这一针打断的东西**，所以它该红）。
   「不是我直接打的」不是放过它的理由。

### 六之四十二 · 一份逻辑两份实现时，探针要**逐针点名跑哪一套**（第十九轮）

产品里「就绪判定」有两份：`apigReadyCheck`（全局面板）与 `stAiReady`（编写器 /【ai对话】）。
一份反向测试脚本如果写死「跑 `vertex-verify.js`」，那 `stAiReady` 那条路**永远不会被注入**——
而这一轮最硬的 bug 恰好在它里面（完整模式被「没填 Key」拦下）。
⇒ 探针结构里给每针加一个 `suite:` 字段，**逐针指定跑哪一套**（`_reverse16.js` 就是
  8 针里 5 针打 `vertex`、3 针打 `apig`）。⚠ 一条产品逻辑有 N 份实现，就该有 N 份覆盖 ——
  这是「对照组必须不同」在**结构**层面的版本。

### 六之四十三 · 「照着形状拼 URL」不等于「那个方法存在」（第二十轮）

Google 的资源路径长得很有规律，于是很容易照着别的方法的形状拼一个：
`/v1/projects/{p}/locations/{l}/publishers/google/models` —— 看着完全合理，
但**那条资源下根本没有 `list` 方法**（官方 REST 目录里只有 computeTokens / countTokens /
embedContent / generateContent / predict / rawPredict / stream*）⇒ 注定 404。
真正有 `list` 的是 **v1beta1** 的 `publishers.models`。

⇒ **拼 URL 之前先翻一眼官方 REST 目录里那条资源的方法清单**（导航页本身就够了，
   不用点进方法详情）。⚠ 「形状对」和「方法在」是两件事 —— 404 只会说「找不到」，
   不会说「这个方法不存在」。
⇒ 同族：**别指望从「同类产品」抄到我们想要的接口**。这一轮去翻酒馆的
   `src/endpoints/google.js`，发现它**根本没有列模型的路由**（只有 caption / voice /
   tts / image / video）—— 它不列模型。**从别处抄不到，说明这条路是我们自己加的**，
   那就更没有「照着抄就不会错」的保险。

### 六之四十四 · 「逐条补兜底」就是会漏（第二十轮）

`hidden` 属性自带的 `display: none` 会被任何**同权重**的 `display: flex` / `grid` 盖掉。
这个坑第一轮踩在 `.apig-vertex-box` 上，当时的修法是**给那一处补一条**
`[hidden] { display: none }` —— 后来又给 `.apig-sa-masked` / `.apig-verify-out` 各补一条。
第二轮照样漏：`.ai-field`（`display: flex`）没补，于是 `keyF.hidden = true` **完全无效**，
属性设对了、**画面上照样看得见、不报任何错**，是用户看出来的。

⇒ **兜底要写成全局的一条**：`[hidden] { display: none !important; }`。
   ⚠ 「哪几处需要」这个判断本身就会漏 —— 所以**别逐条判断**。
⇒ 判据也要跟着改：**读 computed `display`，不读 `hidden` 属性**。读属性的话，
   这个 bug 在套件里**照样全绿**（属性确实是 `true`）。

### 六之四十五 · 同一件事两份实现时，**可选参数只传了一份**（第二十轮）

「就绪判定」有两份：`stAiReady(cfg, opts)`（编写器 /【ai对话】）与 `apigReadyCheck(cfg)`（全局面板）。
两边都要能问「**只检查到模型那一层为止**」（拉模型时不能要求先有模型），
但只有 `stAiReady` 那边传了 `{ needModel: false }` —— `apigReadyCheck` 漏了。
后果：Vertex 下必须先手打一个模型名才能点「获取模型列表」，
而这一步**本来就是为了挑模型** ⇒ 功能整个废掉，界面上却只是「按钮点了没反应」。

⇒ 一份逻辑 N 份实现时，要逐份核的不只是**函数体**，还有**调用点传的参数**。
   ⚠ 这跟六之四十二是一对：那条讲「探针要逐份打」，这条讲「改的时候要逐份改」。

### 六之四十六 · **「跑不了」和「坏了」长得一模一样**（第二十轮）

`run-all.js` 里 18 次 `spawnSync` **全部立刻失败**，打出来是：

```
18 套，共 **0 通过 / 0 失败**
❌ check.js   —   [无] 0.0s  ← 没有可解析的汇总行
（18 套全部这一行）
```

⚠⚠ **这个输出长得像「18 套套件全坏了」** —— 而真正坏的只是 runner 起不了子进程。
`0.0s` 是唯一能看出真相的线索（**真跑过的套件不可能 0.0s**），
但它混在 18 行一模一样的红里，太容易当成「套件集体崩了」去查产品。
⚠ 手跑单套 `node check.js` 却是好的 ⇒「单跑绿、整跑全红」这个组合
   会把人往「串味 / 竞态」上带，**这次是环境，不是产品**。

**真因（排查绕了三轮，前两轮的结论都是错的）**：
这个环境里 **`spawnSync` 一律返回 `EBUSY`，而异步 `spawn` 完全正常**。
实测（`_diag-spawn2.js`）：`spawnSync` → `err=EBUSY`；`spawn` → `code=0`。
⚠ 而 `spawnSync('where.exe')` / `spawnSync('git')` **也一样 EBUSY** ⇒
   第一轮据此误判成「沙箱只放行一层进程创建」，绕道写了个 bash 驱动版。
   那一版**能用**，但**根因判断是错的** —— 改回异步 `spawn` 之后 `node run-all.js` 当场恢复。
⚠ 套件自己（`persona-verify.js` 等起 Chrome）一直用的是**异步 `spawn`**，
   所以它们从来没受过影响 —— 这正是「单跑绿、整跑红」的由来。

⇒ 判据：**同一件事「做不到」和「做出来是坏的」，报出来的东西必须能分开**。
   `run-all.js` 现在把 `r.error` 单独报成 `SPAWN-FAIL ← 起不了子进程：<code>`，
   不再和 `NO-SUMMARY` 混成一个样子。

⇒⚠⚠ 更值钱的那条：**「环境不允许」这个结论，要拿同一件事的另一种写法证伪过再下。**
   这里 `spawnSync` 与异步 `spawn` 就是同一件事的两种写法，**只试了一种就下了结论**；
   代价是白写一个驱动 + 一条写错的记忆（本条已改回）。
   （同族：六之三十三「量得没错但量错了对象 = 没量」。）

⇒ 顺带：整跑现在有**两个驱动**（`run-all.js` **首选** / `run-all.sh` **备用**），
   套件清单与汇总正则抽到 `suites.js` **单一真相源**，两个驱动 `require` 同一份。
   ⚠ 抄一份必然分叉 —— 「两种汇总格式」那个坑本身就是抄出来的（见 `run-all.js` 文件头）。
   ⚠⚠ **第二十一轮补**：**外部那份驱动（`…\2026-09-17-00-10-39\_verify\run-all.js`）
   当时漏改了，一样是 `spawnSync`** ⇒ 外部 8 层整跑打出来是
   「8 层全部 `0.0s` + 没有可解析的收尾行 / 合计 0 通过 0 失败」。
   ⇒ **同一个坑会在「你没改的那份实现」里再来一次**；修完要问一句「这件事有几份实现」。
   两份驱动现在都补了「没通过的层 / 套件打印尾部输出」（见六之五十一）。

### 六之四十七 · **「注入没效果」有两个完全不同的原因，长得一模一样**（第二十一轮）

第二十一轮新加了一整页（编写器「首页」选项卡），`home-verify.js` 一次就 **60/0 全绿**。
反向测试 5 针跑完 —— **8 条不达标，而产品一条 bug 都没有**，8 条全是探针／套件自己的毛病。
分三类：

**① 注入点根本没命中 ⇒ 改探针。**
R1 的 `from` 写成 `"            { id: 'home', … },\n"`，而 `saki.html` 是 **CRLF**
⇒ 命中 **0 次** ⇒ `String.replace` 什么都没做 ⇒ 注入是**空操作**。
表现是 `注入后套件跑完了 {"pass":60,"fail":0}` —— 和基线**一模一样**。

⚠⚠ 这就是「**注入没效果**」，但它和「**断言太弱**」的报错形态**完全一样**
（都是「预期该红的三条一条没红」）。分开它们的唯一手段是**唯一性闸门**
（`ORIG.split(p.from).length - 1 === 1`）—— 它当时**确实**打了 `出现 0 次`，
但那几行被 `tail -70` 截掉了，是事后才回头看到的
⇒ **别用 `tail` 收窄反向测试的输出**，那些闸门行就是它的诊断价值所在。

⇒ 判据：**带 `\n` 的注入片段，在产品是 CRLF 时一律换成「行内片段」（不带尾换行）。**
这次把 R1 改成 `from: "        const ST_TABS = ["` 就好了。

**② 断言本身是永真的 ⇒ 改套件。**
R5 注入 `added = picked`（不 clone），套件却报 60/0 —— 同样是「注入没效果」，
但这一次**注入真的命中了**。真因在套件：

```js
await ev(`… stEditor.card.bookEntries[1].content = '被改了' …`);
await feedFile(CARD_JSON, …);   // ← 重新 feed：parseWorldBook 又 parse 出**全新对象**
check('卡里改条目不污染来源', await ev(`stEditor.extractSrc.entries[0].content`), '内容甲');
```

比的是**两个不同的对象**：`extractSrc.entries[0]` 是刚 parse 出来的，跟卡里那条
**从来就不是同一个** ⇒ **删掉 clone 也照样绿**。
⚠ 而且 `stExtractImport()` 末尾本来就会 `extractSrc = null`，逼得人只能「再 feed 一次」——
这个坑**几乎是必然踩上的**。

⇒ 判据：**要验「两处是不是同一个对象」，必须在「建立关系之前」抓住引用，再比。**

```js
await ev(`window.__srcRef = stEditor.extractSrc.entries[0]; true`);   // 先抓引用
await ev(`stExtractImport()`);                                        // 再建立关系
await ev(`(function(){ stEditor.card.bookEntries[0].content = '被改了'; return true; })()`);
check('卡里改条目不污染来源', await ev(`window.__srcRef.content`), '内容甲');
```

⚠⚠ 「重新解析一遍 / 重新读一次文件 / 重新构造一份」拿到的**永远是新对象** ——
拿它去问「是不是同一个」，问的是**恒假**的问题；反过来当成「来源有没有被改」就**恒真**。
（同族：六之三十三「量得没错但量错了对象 = 没量」。）

**③ 探针「删掉一个东西」经常连带把整套崩掉。**
R1 第一版是「把 `home` 从 `ST_TABS` 里删掉」。结果套件里那句
`document.getElementById('st-tab-home').click()` 拿到 `null`，
而 `ev()` 遇到页面异常是**直接 `throw`** ⇒ **整套崩掉、连汇总行都没有** ⇒
反向测试拿不到「红了几条」，那三条「预期该红」全部判失败。

⇒ **探针优先选「插入 / 改值」，别选「删除」。**
删除会让所有依赖它存在的代码一起塌，而塌法往往是**异常**而不是**断言失败** ——
前者连汇总行都不给你。这次的替代写法是「在最前面插一个探针选项卡」：
一次把「总数 16」「排在最前」打红，而「在清单里」仍然绿 ⇒
那条**反而成了活着的对照组**，比原来那版还强。

⚠⚠ 最后记一句：这 8 条不达标**一条产品 bug 都没抓到**，但那一轮**绝不是白跑** ——
R5 抓到了一条**永真断言**，那正好回答了「新写的 60 条断言里有没有天生为真的」。
反向测试的价值不在「它绿了」，而在于**它是唯一能把「注入没效果」和「断言太弱」分开的东西**。

**④ ⚠⚠ 「要改哪几处」这条提醒，本身是一个没人检查的载体。**

本轮加一个选项卡，按项目里那条老提醒改了**三处**写死的数字
（`persona-verify.js` / `smoke.js` / `st-code.js`），本地整跑全绿。
到跑**外部 8 层**之前顺手 `grep` 了一下 `ST_TABS`，才发现**外部 harness 里还有 7 处**：

```
verify_steditor.js      B6 条数 / C1 条数 / C12 条数 / C2 标签清单 / C3 id 清单 / C4 默认选中 / P69 id 清单
verify_tavern_visual.js 左侧有 N 个选项卡 / 选项卡文案齐全 / 默认选中 /
                        展开后 N 个标签 / 折叠后 N 个标签 / 移动端折叠后 N 个图标 / tabWalk 两处清单
```

⇒⚠⚠ **那条提醒写的是「共三处」—— 它自己就是错的**，而它错了**没有任何东西会去核**。
更坏的是它的**语气**：它读起来像「照这个清单改完就没事了」，于是**它把一次排查变成了确信**。

⇒ 判据：**枚举类提醒（「要改这几处」「共 N 个地方」）必须写清「这是怎么数出来的」，
   否则它就是一个没有观察者的写死清单。**
   本轮的修法：把清单扩到**六处**，并且**在提醒里点明「『共三处』这句话本身就是不完整的」** ——
   让下一个人知道**这个数字也该被怀疑**。
   ⚠⚠ **但「五处」也没数对** —— 收尾整跑时 `st-ai.js` 报 341 通过 / 2 失败，
   其中一条正是它自己第 797 行的 `选项卡数量变成 15`（**第六处**）。
   这份清单**改过三次：三处 → 五处 → 六处**，每一次都是「照上一版清单改完、整跑又红」。
   ⇒ 结论不是「这次终于数对了」，而是：**手写枚举一定会漏**。
     真正可靠的只有**整跑**（`run-all.js` 把每一套的断言数打出来，跟 README §7 表对不上
     就是少走或有红）。**别再用「改完清单」当收尾判据。**

⚠ 同族：六之三十六（文档里的数字要有观察者）· 六之三十九（写死清单每次加东西都来收账）。
   这三条合起来是一件事：**「写死的东西」不只是代码里的常量，也包括「提醒你改哪里」的那句话。**

### 六之四十八 · **「过时断言」和「永真断言」是同一枚硬币的两面**（第二十一轮）

`st-ai.js` 里有一条断言写的是 `/没返回任何模型/` —— 而产品在第十四段把
`stAiFetchModels` 拆出 `stAiFetchModelsOnce` 时，顺手把这句报错改成了
「返回里没有模型（字段名对不上？）」。**产品改了「人话」，断言没跟着改。**

⚠⚠ 它和「断言永真」（六之三十九）是**镜像的两面**，两个都不会自己好：
- **永真断言** ⇒ 套件**一直绿**，其实什么都没验；
- **过时断言** ⇒ 产品**一点问题没有**，套件**一直红**。

而「一直红」更阴：**红久了就没人看**。这一条漂了整整一轮，直到整跑把
「`st-ai.js` 341 通过 / 2 失败」打出来才被翻出来。

⇒⚠⚠ **`grep` 产品会骗人。** 这次 `grep -c "没返回任何模型" saki.html` 返回 **1** ——
看着像「这个串还在产品里」，其实是**产品注释里还留着**那一处（讲历史的）。
⇒ 唯一可靠的发现方式是**跑一遍看它红**；静态 `grep` 只能当**线索**，不能当判据。

⇒ 判据：**断言引用产品的「人话」时，只守语义、不守整句。**
这次拆成两条：① **拒绝**（不静默返回空数组）；② 报的错说的是「**没有模型**」这件事。
⚠ 但也**不能宽到「只要抛错就算过」** —— 那会放过「抛了一个无关的解析错 / 网络错」。
**「宽」和「松」是两件事**：宽是「不锁死措辞」，松是「不检查语义」。

### 六之四十九 · **「注入点唯一」这道闸门，挡不住「没人跑」**（第二十一轮）

`_reverse14.js` 的 R4 把产品的**报错文案**一起写进了 `from`
（`throw new Error('这个接口没返回任何模型');`）。文案一改 ⇒ 注入点**命中 0 次**
⇒ 那一针**静默变成空操作**，漂了整整一轮。

⚠ 闸门本身是**好的** —— 它会把「命中 0 次」报出来，不会伪装成「没注入也全绿」。
⚠⚠ **但闸门只在有人跑它的时候才起作用**，而这一套用的是 `spawnSync`
（本机必 `EBUSY`，见六之四十六）⇒ **它根本跑不起来**。
⇒ 于是「有闸门」这件事变成了**心理上的保险**：以为有人守着，其实没有人跑。

⇒ 判据：**探针的 `from` 尽量选结构性的东西**（函数名 / 调用点 / 常量名 / 一段代码骨架），
   **别选人话**（报错文案 / 提示语 / 注释）。产品改一句文案，人话就没了，
   而**产品那边看不出任何异常** —— 只有探针悄悄死掉。
⇒ 推论：**任何「只在被运行时才成立」的保证，都要问一句「那它多久被跑一次」。**

### 六之五十 · **harness 自己的结构缺陷，会伪装成「产品坏了」**（第二十一轮）

`vertex-verify.js` 是**全 `_verify/` 里唯一一套两样都占的**：

1. **CDP 端口写死**（`const cdpPort = 9711;`）—— 其余 16 套都走「先真绑一下、绑得上才算数」。
   连跑整套时上一轮 Chrome 还没退干净就占着这个号，症状是「连不上 CDP」。
2. **盲等 `await sleep(2500)`** 而不是等 `Page.loadEventFired` —— 整套连跑时
   （前面已经起了十几轮 Chrome、主页还要 `@import` 拉 Google Fonts）2500 ms **不够**，
   页面还没跑完内联脚本。

⚠⚠ **症状极具误导性：`1 通过 / 1 失败`** —— 而那唯一一条**通过**的恰恰是
`加载后没有未捕获异常`，因为**什么都还没跑**，自然零异常。汇总行**完全看不出**是「加载没完成」。

⇒ 判据：**「通过数 = 1」而那条恰好是「零异常 / 零报错」时，先怀疑「加载没完成」，别怀疑产品。**
   同族：六之四十六（`0.0s` 是「驱动没起来」的唯一线索）—— 都是**「跑不了」伪装成「坏了」**。

⇒ 修法：端口一律「先真绑一下」（`listen` 成功才算数）；加载一律等**真实事件**
   （`Page.loadEventFired` + `document.fonts.ready`），**别赌时间**。
⚠ **故意不留超时回落** —— 回落会把「加载卡住」伪装成「跑过去了」，那种失败更难查。
⚠ 单跑一次是 **147 / 0** ⇒ 确认不是产品回归。
   **「假红」必须靠「同一套单跑是绿的」来证伪，不能靠「我觉得是环境」。**

### 六之五十一 · **驱动坏掉时，报出来的东西必须能自己指认自己**（第二十一轮）

外部那份 `run-all.js` 也是 `spawnSync` ⇒ 打出来是：

```
✅ 全部 8 层：0.0s + ← 没有可解析的收尾行
合计 0 通过 / 0 失败
```

⚠ **唯一的线索是那个 `0.0s`**（真跑过的层不可能 0.0s），但它混在 8 行一模一样的红里。
⚠⚠ 六之四十六 那条**当时只改了本地那份驱动**，外部那份漏了
⇒ **同一个坑会在「你没改的那份」里再来一次。修的时候要问一句：这件事有几份实现？**

⇒ 两份驱动现在都补了**「没通过的层 / 套件打印尾部输出（最后 25 行）」**：
   ⚠ **只打印、不落盘** —— `_verify/` 里的生成物用完就得删，留两份就一定有一份是错的；
   而真正需要的只是「为什么红」那一小段。

### 六之五十二 · **表里的数字有两种：写死的会红，推导的永远不会红**（第二十一轮）

README §7 那张「逐套断言数」表里，`smoke.js` 本轮从 **90 变成了 91** ——
而**没有任何一行代码需要改**。原因是它有一个
`for (const t of tabs) check('选项卡 ' + t + ' 渲染', …)`：**每条选项卡一次断言**，
所以加了「首页」之后它自己就变 91。

⚠ 对照：`st-ai.js` 里那句写死的 `选项卡数量 16` 就会**自己红**。
⚠⚠ **推导出来的数字永远不会红** —— 只能靠「**拿实测跟表对**」发现
（`run-all.js` 打出来的那个数）。光看代码看不出来，光跑套件也看不出来
（它绿着，只是**条数变了**）。
⇒ 这正是 README §7 那张表除了「给人看」之外的**第二个用途**，也是六之四十七
   「整跑是唯一可靠判据」的另一个侧面。

### 六之五十三 · **「命令没输出」不等于「结果为空」**（第二十一轮）

排查 Chrome 层超时时，我用 PowerShell 数进程 —— 屏幕上**一片空白**，
于是我写下「**没有任何 node / chrome 在跑，环境是干净的**」。**这个结论是错的。**

同一条命令换 `tasklist` 再问一次：**18 个 chrome、7 个 node**。
真相是**那个 PowerShell 工具在本环境根本不返回 stdout** ——
连 `Write-Output "probe-ok"` 都一个字不回。

⚠ 形状：**「工具静默失败」和「结果为空」在屏幕上一模一样**（都是空白），
   而**两者指向完全相反的结论**。我把「工具没给我答案」读成了「答案是空」。
⚠ 判据：**先拿一条「已知必定有输出」的探针试工具**（`Write-Output "probe-ok"`）。
   连它都被吞 ⇒ 是**工具坏了**，不是结果为空 ⇒ 换工具（这里换成 `tasklist`）重问。
⚠⚠ 同族：六之二十七（「取不到就换一个」= 把失败伪装成成功）、
   六之二十五（「跑完了」≠「每条都跑到了」）。
⇒ **凡是从「没看到」推出来的结论，都要先确认「看」这个动作本身生效了没有。**

### 六之五十四 · **跑着的时候改 harness ⇒ 在跑的进程用的是旧代码**（第二十一轮）

Chrome 层报 `TIMEOUT`，第一反应是「产品回归了」。**先别怀疑产品，先核「它跑的到底是哪份代码」：**

| | 日志说 | 源码说 |
|---|---|---|
| 超时上限 | `超过 360s` | `const TIMEOUT_MS = 15 * 60 * 1000`（= **900 s**） |

⇒ **两个数对不上 ⇒ 那个进程加载的不是现在这份源码。** Node 只在首次求值时读一次文件，
   之后**盘上怎么改它都看不见**；而这次的改动恰好落在它跑的过程中
   （`stat` 的 mtime **晚于**进程启动时间，是铁证：`17:37` vs `17:27`）。

⚠ 还有一条更细的判据：**日志里有没有新加的那行打印**。这一轮给收尾加了 `⏱ 收尾 …` 逐行计时，
   而日志里**一行都没有** ⇒ 再次证明跑的是旧版本。
⚠⚠ 所以 `TIMEOUT` / `0 通过` / `0.0s` 这类**看着像产品结论**的东西，
   **有可能只是「跑的不是这份代码」** —— 它跟真回归长得一样。
⇒ 机械判据：**跑前跑后各拍一次 `sha1sum *.js`，跑完 `diff` 一下**；有差异 ⇒ 这轮结果作废、重跑。
⇒ 同族：六之三十四（**别在反向测试跑着的时候改产品**）—— 那次被改的是**产品**，
   这次被改的是 **harness**，**两个方向同一个坑**：
   **「改动的时机」和「跑动的时机」重叠了。**

### 六之五十五 · **删一个文件要 200 ms ⇒ 递归删目录会卡死整层**（第二十一轮）

外部视觉层 `verify_tavern_visual.js` 的 `finally` 里：

```js
try { chrome.kill(); } catch (e) {}
try { fs.rmSync(profile, { recursive: true, force: true, maxRetries: 8, retryDelay: 150 }); } catch (e) {}
```

这一句**从不返回**。⚠ 症状：**所有检查在 108 s 就打完了**，然后**卡到驱动把它掐掉**，
报 `TIMEOUT` —— **看起来像「这一层跑不完」**。

⚠⚠ **我连着猜错两次，最后是量出来的**：

| 步骤 | 结论 |
|---|---|
| 给收尾**每一步打时间戳** | `ws.close` / `chrome.kill` / `srv.close` / 等退出**全是 +0.0s**（主进程**早就退了**），然后 `rmSync` 永不返回 |
| 猜 ①「`kill()` 是异步的，等 Chrome 退出再删」 | ❌ **错** —— 改完照样卡（它本来就已经退了） |
| 猜 ②「`maxRetries × retryDelay` 重试风暴」 | ❌ **错** —— 改成 `maxRetries: 0` 照样卡 |
| **量：单文件写 / 删** | **写 6 ms，删 216 ms** ← **真因** |

⇒ 真因：**这个 tmpdir 里「删一个文件」要 ~200 ms**（写只要 6 ms）。
一个 Chrome profile 有**几百个文件** ⇒ 光删就是 **100 s 起**，加上目录遍历与重试就是「永不返回」。
**跟 Chrome 无关、跟重试次数无关、跟产品更无关。**

⇒ 修法（**两版才对，第一版还不够**）：

```js
// 第一版：异步删 + 硬性 3 秒上限 —— 能跑完，但**进程打完汇总后不退出**
await Promise.race([
    fs.promises.rm(profile, { recursive: true, force: true, maxRetries: 0 }).catch(() => {}),
    sleep(3000)
]);
```

⚠ 第一版的坑：`process.exit()` **拦不住 libuv 线程池里正在跑的删除任务** ——
汇总行 `371/371 通过` 打完了，进程**还活着 30 s+**（后台任务因此判为「没结束」）。

```js
// 最终版：**派一个 detached 子进程去删** —— 主进程立刻退出，垃圾留给它慢慢清
const cleaner = spawn(process.execPath, ['-e',
    'require("fs").rmSync(process.argv[1],{recursive:true,force:true,maxRetries:0})',
    profile], { detached: true, stdio: 'ignore' });
cleaner.unref();
```

实测收尾 **0.3 s**（`派后台删 profile +0.2s`）且进程**立刻退出**（`EXIT=0`）。
删不完也没关系，剩下的交给 `_verify/_purge-tmp.js`（白名单里有 `cdp-`）。
⚠ **「等它删完」和「别卡住」只能选一个 —— 选不卡住。**

⇒ 判据（**这条比 bug 本身值钱**）：
   1. **「卡住了」不要猜哪一步慢 —— 给每一步打时间戳。** 五行就够。
   2. **「听起来合理的故事」可以连着错两次。** 两次改完都照样卡，而两次的理由都说得通。
      唯一把它们否掉的是**数字**。
   3. **怀疑「这一步慢」时，把这一步单独拎出来量** —— 这次最后一步是
      「写一个文件 vs 删一个文件」各计一次时，一眼就分出来了。
   4. **修完要看「进程退出了没有」** —— 汇总行打完了 ≠ 跑完了（六之二十五的又一形态）。
   同族：六之四十六 / 六之五十（都是「症状指向 A，真因在 B」）——
   这一族问题的通用解法只有一个：**把中间过程变成可观测的数字。**

⚠ **顺带（同一件事的另一面）—— 这里我一开始判断错了。**
本地套件也各删一次自己的 profile（`rmSync` + `maxRetries: 8`，**29 个文件**都是）。
我**先**写下「它们**没卡**（每套 ~285 s 能跑完），本轮没动（风险大于收益）」——
⚠⚠ **然后当场被咬**：`_reverse18.js --only R6` 的基线卡了 **10 分钟**不退，
真凶正是 `home-verify.js`（第二十轮新写的套件）的**同一句** `rmSync`。
它**所有断言全绿、页面 5.9 s 就加载完**，然后卡在删 profile ⇒
**连汇总行都打不出来**（汇总行在 `finally` **之后**）⇒ 反向测试拿不到「红了几条」。
⇒ 改成 `spawn(detached)` 后：**60 通过 / 0 失败、`EXIT=0`、用时 10 s**。

⚠⚠ 教训：**「别的套件能跑完」不等于「这个套件不会卡」。**
「它们都没事」这个结论**本身就是没量过的判断** —— 同族六之三十三（「猜」和「决议」要分开量）。

⚠⚠⚠ **「剩下 28 个不动」这条结论当场也被证伪了**（同日实测，三套、三条独立证据）：

| 套件 | 实测 | 汇总行 |
|---|---|---|

⇒ 两件事：
   ① **它们确实会卡**（不是「能跑完」）—— 上一版结论是**没量过就下的**，同一个坑第二次。
   ② ⚠⚠ **汇总行打不打得出来，取决于它写在 `finally` 的哪一边** ——
      写在**之后**的（`persona-verify` / `st-code`）一旦卡住就**永远拿不到条数**，

      ⇒ 这正是「**被截断的层跟『通过了』长得一模一样**」的又一种形态。

     磁盘争用会让 ~200 ms/文件 再翻几倍 —— 但**修法一样，一行**：

   ⇒ 结论：**这不是「28 个不用动」，是「28 个都该动」**，只是优先级低于产品。
   ⇒ **已改**（2026-09-24，两批）：本地 **29 个文件**铺上 `spawn(detached)` ——

### 六之五十七 · **`w:0` + computed 有值 = 「已解析但还没布局」；轮询必须等实质条件**（第二十二轮）

整跑时 `sb-verify7.js` 报两条红，而**同一套单跑三次全绿**：

```
❌ 真机预览里那块也变宽了  actual={"w":0,"cs":"210px"}  expect="210"
❌ 真机预览里也是 260px    actual={"w":0}               expect="260"
```

#### 判据：`cs` 读得到、`rect` 是 0 ⇒ **没布局**，不是「产品坏了」

`getBoundingClientRect().width` 是 **0**，而 `getComputedStyle(el).width` 是 **`"210px"`** ——
**元素在 DOM 里、inline 样式也在，就是它所在的文档还没被布局**。
（`display:none` 的元素，computed width 同样返回**指定值**而不是 `auto` ⇒ 这个组合正是「没布局」的签名。）
⇒ 断言里**同时记 `cs`** 是值得的：只有 `w` 的话，`0` 既可能是「没渲染」也可能是「产品真的算成 0」，
**分不开**。

#### 根因：`frameEval` 的语义 + 调用点等错了东西

`frameEval` 的契约是「**把第一个不抛异常的答案当正经答案返回**」—— **`null` 也算正经答案**。
于是调用点的轮询写成 `if (i2) break;` 就**等到「有值」就停**，而不是等到「实质条件成立」：
srcdoc 刚换上时元素已经解析出来、还没布局 ⇒ 立刻 break ⇒ 读到 `w:0`。

改成 `if (i2 && i2.w > 0) break;`（260 那条同理）。
⚠ **这不是放宽断言** —— 断言仍然要求 `w === 210`；只是**不在「还没渲染」的瞬间取样**。
真要是产品坏了（永远不是 210），循环跑满后照样红，而且报出来的是**真实读数**而不是布局伪影
（比「红在 `w:0` 上」有用得多）。

⚠⚠ **同族的坑要在同一套里扫一遍，别只改踩过的那一处。**
`sb-verify6.js` 早就踩过**一模一样**的坑，还留了注释：
「frameEval 只在**抛异常**时才重试，返回 null 它认为是正经答案 —— 于是就成了随机翻车」，
并在调用点等实质条件（`if (h2 && h2.pos === 'relative') break;`）。
`sb-verify7.js` 这两处**漏了** ⇒ **只修踩过的那一处 = 把坑留给隔壁**。
判据：`grep` 全部 `^\s*if \(.+\) break;`，**逐个问「我等的这个条件是实质的吗」** ——
`if (wsUrl) break;`（CDP 连接轮询）等的就是实质条件，不用动；
「等到 `document.body.querySelector(...)` 有值」不是。

#### ⚠ 「复现不了」≠「没问题」

探针实测：空闲机器上采样序列是 `null → 210|210px` —— **抓不到 `w:0`**，
那个窗口**比一次采样还短**。加 4 个 IO + CPU 压力进程后，`260` 的序列变成**连续 20 次 `null`**
⇒ **负载只会把窗口往后推，不会把它消掉。**
⇒ 定性靠**两条合起来**：① 单跑重复全绿；② 机制在代码里**可指认**（上面那两步）。
⚠ **别指望「再跑一遍看看」** —— 窗口比采样短的时候，跑十遍也可能一遍都不红。

#### ⚠ 顺手发现的另一个缺陷：**不是本次红的根因，别搞混**

`oopif` 数组**只 push 不删**（`Target.attachedToTarget` 里 push，**全仓没有一个
`Target.detachedFromTarget` 处理**；4 份实现：`sb-verify5/6/7/8`）⇒
一轮下来 **5 个里 4 个是 session 已死的僵尸**。

⚠ 它**把诊断带偏过**：我第一眼就误判成「`frameEval` 从尾部往前扫 ⇒ 选中了隐藏的僵尸帧」。
**否掉的判据**：从尾部往前扫时，**最新那个活帧排在最后**，僵尸帧只会**抛异常被跳过**、
**不会答话** —— 而 `w:0` 是**答了话**的 ⇒ 值来自**活帧**，僵尸是清白的。
已补上 `detachedFromTarget` 修剪（列表只增不减属于「每加一次东西就来收账」那一类）。

⚠ 同轮实测：**并发跑套件会 `EADDRINUSE`** —— `pickPort()` 是 **TOCTOU**（先 `listen` 再 `close`，
中间不占坑），三个进程同时探到同一个空端口就一起抢，两个直接 `FATAL`，
**打出来的是「0 通过 / 1 失败」，和「产品坏了」长得一模一样**。
⇒ 套件**一律串行**这条规矩，这次是被实测再次确认的，不是形式主义。

## 七、内联一整份外部网页（小游戏「复古线框战机」，第十轮）

需求：把 `G:\retro_vector_space_shooter (1).html`（105 508 字节 / 2 353 行的**完整独立网页**）
搬进主页的小游戏弹窗。它自带 Tailwind CDN + Google Fonts + 自己的选机页 / HUD / 暂停页 /
结算页 / 3 种 Boss —— 改写成在 480×260 那块 canvas 上跑等于重写一遍。

### 7.1 路线：iframe + **内联**

`iframe` 是**独立文档**，它的 id / class / 全局变量一个都不会漏到主页上来 —— 这正是要的。
但内容必须**内联**（`srcdoc`），不能放成 `games/shooter.html`：实测 `saki.html` 对外
**零个**本地相对引用（只有 Google Fonts 和 Discord 两个远程 URL），
加一个外部文件就等于把它从「双击就能跑的单文件」变成「要一起拷贝的目录」。

常量 `ST_SHOOTER_SRC` 放在 `<script>` 的**最末尾**（`26384 ~ 28737`）——
**这样它上面所有行号锚点都不动**（见 §六之十三，行号锚点是这个项目的老伤口）。

### 7.2 五条转义规则（同时满足两个解析器）

HTML 那个解析器最阴 —— 它**不认识 JS 字符串**，只会一路找 `</script` 把外层掐断。

| 规则 | 不转义会怎样 |
|---|---|
| `\` → `\\` | `/\d+/` **静默**变成 `/d+/` —— 游戏能开、正则全废。**最要命的一条** |
| `` ` `` → `` \` `` | 模板字面量被提前闭合 |
| `${` → `\${` | 当成插值 |
| `</script` → `<\/script` | 外层 `<script>` 被**提前掐断**，页面从这儿往后全废 |
| `<!--` → `<\!--` | HTML 词法器在 script data 态见到 `<!--` 进 **script data escaped** 态，此后遇到 `<script` 再进 **double escaped** 态 —— 在那一态里 `</script` **不再算结束标签**。原文件恰好凑齐这个序列（`<script src=tailwind>` 第 7 行、`<!--` 第 129 行、主 `<script>` 第 329 行） |

⚠ 前四条里 `\/` `\!` 都是 JS 的 NonEscapeCharacter（求值回 `/` `!`）⇒ **运行时拿到的
字符串跟原文一字不差**。这正是「往返逐字节比对」要证的事。

⚠ **单趟逐字符替换，别用一连串 `.replace()`** —— `\` 先变 `\\` 之后，后面几条规则会去动
那些新产生的反斜杠，顺序稍微一乱就是双重转义。

⚠ 文件里存 **CRLF**（跟 `saki.html` 统一），但 JS 规范要求模板字面量把 `<CR><LF>`
**规范化成 `<LF>`** ⇒ **运行时那份是纯 LF**。两边都对，别把「运行时没有 `\r`」当 bug。

### 7.3 判据：往返逐字节，不是「能跑起来」

`_mk-shooter-embed.js` 三档：干跑（转换 + 往返自检 + 报告，**不写文件**）/ `--go` / `--verify`。
**它当场抓到两个真 bug，都在工具自己身上**：

- `out += '<\\/'` 顺手把 `/` 也吐了出去，循环接着又输出一次原来的 `/` ⇒ `</script` 变成
  `<//script`（`<!--` 同病 → `<\!!--`）。**这种错不报错**，只会让游戏里某个标签悄悄失效。
- 提取器用「从头找第一个 `` `; ``」收尾，被正文里一句 `` radioText.innerText = `📡 ${msg}`; ``
  提前截断 ⇒ 求值报 `Unexpected end of input`，**看着像「文件写坏了」，其实是读的人切错了刀**。

⇒ 写盘前的守卫也有过一版**永远误报**的：数 `<script` 的个数 —— 可字面量里那两条
**开标签**本来就该多出来。改成只数**闭标签** `</script` 和 `<!--`（那才会掐断外层）。

### 7.4 卸载：**必须摘 DOM**，不能只是藏起来

那个游戏的 `gameLoop` 在 `gameState !== 'PLAYING'` 时**照样** `requestAnimationFrame`
排回去（靠这个在选机页 / 暂停页继续画星空）⇒ **循环一旦启动就永不停止**。

只把 iframe 藏起来的话，关掉弹窗之后它还在后台满帧跑，而且**页面上什么都看不见、
控制台也不报错**。唯一可靠的停法是**把 iframe 从 DOM 里摘掉**（文档销毁 ⇒ 循环消失）。

⇒ 这类「清理」**不是卫生问题，是功能正确性** —— 别把它当可选的收尾。
⇒ 三个收尾动作（摘 iframe / 收 wrap / 撤宽档）抽成一个 `stShooterReset()`：
   **分头写两遍就一定有一遍会漏**（同族：这个项目在「展开键有两个」上栽过）。

### 7.5 焦点：**时机**是关键，不是 API

游戏的键盘监听挂在**它自己那个 window** 上 ⇒ 焦点不进去，按 WASD **一点反应都没有**，
而游戏画面**看不出任何异常**（好好地显示着，就是不动）。

实测（`_probe-focus.js` 逐个试五种写法）：

| 写法 | 父页面 `activeElement` | 子文档 `hasFocus()` | 真发 keydown 谁收到 |
|---|---|---|---|
| 只在 `load` 里 `contentWindow.focus()` | `BODY` | `false` | 父页面 |
| 挂上去**立刻** `f.focus()` | `IFRAME` | `true` | **iframe** |

⇒ **修法是时机**：`f.focus()`（元素聚焦，规范里把元素设成 `activeElement` 的正路）
在 `appendChild` **之后立刻**调；`load` 里那次保留，只是字体到位后再确认一遍。
⇒ 只挂在 `load` 上会太晚 —— 那个页面里有一条 `@import` 拉 Google Fonts，
   `load` 被拖后好几秒，期间游戏已经在跑了（`readyState` 是 `interactive`）。
⇒ ⚠ **反向测试量出一个诚实的缺口**：时机对了之后，只留 `contentWindow.focus()`、
   把元素 `focus()` 拿掉，**87 条全绿** ⇒ **套件分不出这两个 API 的差别**。
   所以套件守的是「焦点进没进去」这个**行为**，不是「用了哪个 API」这个实现细节。
   ⇒ **探针的粒度要落在行为上**，落在实现细节上的探针会「注入之后全绿」而看着像没事。

### 7.6 已知依赖（写出来，不藏）

- **依赖 `cdn.tailwindcss.com`**：它是 iframe `<head>` 里的**阻塞脚本**，拉不下来游戏脚本
  就不执行。`game-verify.js` D 段第一条断言就是它，等不到会明说「多半是 CDN 没拉下来」。
  这是原文件就有的依赖，没去掉（去掉 = 重写整套 UI）。
- **游戏内分数没记进主页**：两边是独立文档，要通信得再开一条 postMessage 通道。
- 游戏逻辑**一行没改**。
